# Backend Architecture — NestJS / VSA

**Status:** approved module boundaries and core conventions; code examples are architectural targets, not implemented files.

## 1. Style and decision hierarchy

**NestJS Modular Monolith + Vertical Slice Architecture + Lightweight Clean Architecture.**

Exactly six business modules under `apps/api/src/modules/`:

1. `projects` (**including Git**)
2. `agents` (**including skills**, with distinct domain models and lifecycle)
3. `workflows`
4. `executions`
5. `environments`
6. `mcp` (independent registry and bindings)

Superseded: earlier proposals that separated `git` or `skills`, used Python/FastAPI, or mandated `command.ts` / `query.ts` files.

## 2. Canonical directory convention

```text
apps/api/src/
  modules/     # projects, agents, workflows, executions, environments, mcp
  platform/    # auth, database, secrets, queue, messaging, config, logging
  shared/

modules/{module}/
  application/
    features/{feature}/    handler and its tests; one use case each
    ports/                 interfaces the handlers need from outside
    <collaborator>.ts      rare, specifically named, last resort (rule 3)
  domain/
    entities/              aggregate roots and their child entities: classes; beside each entity its type-only companions <aggregate>-data.ts, <aggregate>-facts.ts and <aggregate>-<operation>-facts.ts
    errors/                the aggregate's error classes, one <aggregate>-errors.ts per aggregate
    value-objects/         classes that validate on creation; policies; rules. A value object's own validation error stays beside it
    repositories/          interfaces only
  entry-points/
    http/
      shared/              response shapes and problems used by several endpoints
      <caller>/            endpoints with their schemas, grouped by who calls them
    jobs/  schedulers/  startup/  consumers/
    contracts/             the driving adapter behind another module's `contracts/` interface: maps the call to a handler
  infrastructure/
    adapters/  repositories/
  contracts/
    index.ts               what other modules may use
    events/                integration events, when a module publishes any
  {module}.module.ts
```

An **entry point** is any code that receives outside input and calls a handler (an HTTP endpoint, job processor, scheduler, start-up routine or event consumer); clean architecture calls it an interface adapter and hexagonal architecture calls it a driving adapter.

The layers sit at the top of a module (clean architecture); the vertical slices are inside the application layer, one folder per use case ([ADR 0003](adr/0003-api-module-layout.md)). This replaces the earlier decision on Issue #30 that placed shared HTTP shapes in `contracts/http/`.

**Reference module.** `tests/architecture/fixtures/api/reference-module/` (the module `catalog`) is the complete approved layout in a few small files: an aggregate root with its data type, errors file and value object, a repository interface and its in-memory implementation, two features with their handlers (input and result types, no entity class returned) and a test with fakes, HTTP endpoints with a schema and a shared response shape, a port with its adapter, `contracts/`, and the module file. Every `architecture:api` check passes on it and its pinned records match it. Copy it when you add a module; the gate applies to any `src/modules/<module>/` without being edited ([Quality](../engineering/quality.md) §4).

**Secrets are a platform capability** ([ADR 0001](adr/0001-secret-store.md), Issue #57). `platform/secrets/` owns the `SecretStore` port, its PostgreSQL adapter, the AES-256-GCM code and the `secrets` table. A business module stores only the opaque reference. It injects `SECRET_STORE` from `platform/secrets/index.ts` (the port and its typed errors), and its `{module}.module.ts` imports `SecretsModule` from `platform/secrets/secrets.module.ts`. Nothing outside `platform/secrets/` imports any other file there, uses the Prisma `secret` model, or reads `secretsKey` from the configuration (only `platform/config/` and `platform/secrets/` do). `architecture:api` enforces these rules. Each secret carries its module's owner label, so a module can list its own unreferenced secrets (references only) and delete them (ADR 0001 amendment, Issue #76). A label the application layer uses is exported from the module's `application/ports/`, next to the port whose adapter stores those secrets; a label only an adapter uses stays a private constant in that adapter. The `secretsKey` and `secret` checks match the property name on any receiver, so a false positive on an unrelated `.secret` or `.secretsKey` is fixed by renaming that property, and one in prose text inside a string (for example "copy secrets") is fixed by rewording it; narrowing the check by receiver name would let a renamed receiver bypass it. The SQL check matches the `secrets` table after `FROM`, `INTO`, `UPDATE`, `JOIN`, `TABLE`, `TRUNCATE` or `COPY`, bare, quoted or schema-qualified (`"public"."secrets"`).

**No empty mandatory directories.** `handler.ts` is the default feature file; `input.ts`, ports, collaborators, value objects, the entry-point folders other than `http/`, and `contracts/events/` exist only when needed.

**A response shape used by several endpoints** of one module (e.g. the `Project` response used by `create-project` and `list-projects`) lives in that module's `entry-points/http/shared/`. A schema used by one endpoint stays beside that endpoint. `contracts/` is not used for HTTP shapes: it is self-contained, holds only `index.ts` and `events/`, and imports nothing from the module's `domain/` (rule 8).

## 3. Dependency rules and structure rules

### Dependency rules

- **Domain stays framework-independent.** `domain/` never imports NestJS, Prisma, database connections, Redis, BullMQ, Git CLI, Docker, or HTTP types.
- **Handlers own the orchestration of a use case.** They load, call the domain and save. They depend on domain abstractions and ports, never on concrete infrastructure implementations.
- **Entry points are thin:** validate and map input, invoke the handler, map output and errors. No business flows or transaction rules there.
- **Infrastructure implements interfaces.** Bind via NestJS DI tokens at the composition root; wiring dependencies allowed at module setup must be explicit and narrowly scoped.
- **Modules expose public contracts.** A module never imports a sibling's private `application/`, `domain/`, `entry-points/`, `infrastructure/` or repositories.
- **No cycles** across modules or architecture layers.
- Business-specific behavior never goes into `platform/` or `shared/` to bypass module boundaries.

```typescript
// Allowed: public publisher-owned contract in another module
import { ExecutionCompletedV1Schema } from '@modules/executions/contracts';

// Forbidden: bypassing another module's encapsulation
// import { PrismaExecutionRepository } from '../executions/infrastructure/repositories/...';
```

The `@modules/*` alias is conceptual; define aliases in tooling before using them.

### The thirteen structure rules

Rules 1 to 9 and rules 10 to 13 were approved by the operator on 2026-11-17 (Epic #160, [ADR 0003](adr/0003-api-module-layout.md)). How each is enforced is in [Quality](../engineering/quality.md) §5.

1. **Features are independent.** A feature never imports another feature of its module.
2. **Entry points call handlers; handlers never call each other.** Everything that receives outside input (HTTP endpoints, job processors, schedulers, start-up routines, event consumers) lives in `entry-points/`, is thin, and holds no business rules. The application layer knows nothing about HTTP, queues or timers. Entry points are what clean architecture calls interface adapters and hexagonal architecture calls driving adapters. A handler has one public method, `execute`; a second trigger with its own input is a second feature.
3. **Shared application logic is the exception.** When two features need the same logic, try in this order: (1) move it into the domain, onto the object it is about; (2) if it is an infrastructure capability, put it behind a port; (3) if the two features share most of their steps, they are one use case with several entry points, so merge them; (4) if it is a separate step that can happen later, request it as a job or event; (5) if what is left is small, repeat it; (6) only then extract a collaborator with a specific name into `application/`. Never a generic "shared", "common" or "utils" folder, and never one handler calling another.
4. **Behaviour lives on the object it is about.** An entity with a lifecycle is a class: non-public constructor, a factory to create and one to restore, methods for what can happen to it. It cannot be built in an invalid state. A rule about one object is a method on it, with outside facts passed as parameters.
5. **There is no `domain/services/`.** A rule that seems to belong to no object means a concept is missing: name it, usually as a policy or a value object, and put the rule there. A pure function beside the type it works on is the rare exception.
6. **The domain receives facts and never fetches them.** Nothing in the domain takes a repository or a port, or reads or writes. Handlers load, call the domain, and save. Business rules are never written in the database adapter.
7. **Validation has two homes.** A schema beside its endpoint validates the shape of a request and produces field errors; it contains no business rule of its own, and where it repeats a limit it takes it from the domain. Business rules are enforced by the entity or value object they belong to, so they hold for every entry point.
8. **`contracts/` is a module's public face** for other modules, and nothing else.
9. **Same role, same form** (API): state with rules or with dependencies gets a class; everything else is a function or plain data. The table is in §10. A record that has a rule (a limit, a format, a cut, a redaction) is not plain data: it becomes a value object class with a non-public constructor, and its limits are `static readonly` members of that class. A class is built through static factories that return the class: `of`, `create` or `from…` validate, `restore` rebuilds a value from storage without validating again. A factory enforces what was enforced before, at the same moment and with the same result. A factory's name says what it does: `of`, `create`, `from…` or `restore`, or a descriptive name such as `load` (redact, cut and keep what a Git host answered) or `afterWaiting`. The second form of factory is an instance method of an aggregate root that creates a child (a Run adding a Run step). There is no standalone factory class or function: it would be a stateless domain object, and a creation that outgrows its class signals a missing concept, which is named and given the rule. A list of allowed values is a union type derived from a list of literals, not a class. A public static method of an entity or value object is a factory and declares its own class as its return type; a private static may only prepare data for a factory. Every other rule is an instance method of the object it is about, and a policy is an instance built with its configuration (limits, lease, the time). A class has at least one instance member, so a class that is only a namespace is not allowed. No `factories/` directory exists, and no class only builds other classes.
10. **Handlers own their input and result.** Every handler declares its own input type and result type. A result is built from the entity's readable fields and contains ids, values and view types the application layer owns, and only what the callers of that handler use. An input holds plain data only: primitives, lists of allowed values and nested shapes the input declares, with no class from `domain/`, no worker protocol type and no entity data type; the handler builds the value objects and entities it needs from it, so domain rules run in the application layer and not in an entry point. An entity class never leaves the application layer, and a handler never builds an HTTP shape. There is no snapshot: an entity is read through its fields and restored with `restore` from its `<Entity>Data` (the file `<entity>-data.ts` beside it), and only the entity and the repository's implementation import that type; `application/`, `entry-points/`, `contracts/` and repository interfaces never do. A repository method returns the entity, a read model declared in the repository's own file (`RunStepView`, `RunDiffView`), or a value object the entity holds as a readonly field (`RunDiffState` of a Run diff), and never an `…Data` or facts type. A value object follows the same vocabulary: `restore(data)` rebuilds it, `toData()` gives its plain values, and its data type is named `<ValueObject>Data` (an `…Input` type stays only where `load` takes it from outside). A view shown whole by more than one feature is a named collaborator of `application/` (rule 3, last resort): a type and a pure mapping from the entity, with no rule and no repository or port call. What each kind of handler returns is in the table below.
11. **One aggregate root, one file, one repository.** Anything with its own repository is an aggregate root and lives in `domain/entities/`. A repository interface serves exactly one root.
12. **Aggregates refer to each other by id.** A root never holds or loads another root. A rule that needs facts from another aggregate receives them as values (consistent with rule 6).
13. **One concept per file.** An entity file holds the entity class and nothing else. Each value object, an aggregate's errors and its fact types have their own files. `domain/` exports no loose functions other than type guards; an unexported top-level function is allowed only as a technical helper of at most ten lines that names no domain type, and a rule never lives there. The domain imports no runtime module (`fs`, `dns`, `timers` and the like) and, from `crypto`, only `createHash` (deterministic, no I/O): time, randomness and files come in as values, and generating a key or reading a file is an adapter's work. There is no line limit; size is reported, not enforced.

Rules 10 to 13 apply to the API only, as rules 1 to 9 do.

### Rule 14: comments

**Comments explain why, briefly, and only when the code cannot.** Unlike rules 1 to 13, this rule is repository-wide: it covers every package and tests, not the API only. The full text, the planned enforcement and an example are in [Quality](../engineering/quality.md) §5 (rule 14) and in [AGENTS.md](../../AGENTS.md) §2a.

### What a handler returns (rule 10)

| Handler | Returns |
| --- | --- |
| A command the caller needs the result of | The ids and values the caller needs; the shared read model of the aggregate only where the response shows the aggregate whole (create a Project, connect, verify and fetch a Repository, set an Environment file) |
| A command with nothing to show | Nothing, or only the id of what it created |
| A query for one aggregate | A view type: the shared read model of the aggregate when several features show it whole (the Run, the Project, the Repository connection, the Environment file), otherwise one owned by the feature, built from the entity's readable fields |
| A query that combines or computes | A view type owned by the feature that produces it (a read shape is not a domain concept) |

The entry point (endpoint, job processor, scheduler, start-up routine or consumer) maps from the result to its own shape; the handler never does.

**The Run commands** answer with what the caller cannot know otherwise, and the caller reads the Run from `GET /api/runs/:runId`. Start a Run answers 201 with `{ id }`. Cancel answers 202 with `{ outcome }`: `cancelled` when the Run was cancelled at once, `cancel_requested` when the agent worker still has to confirm. Answer, resume, retry delivery, follow-up and bring up to date answer 202 with no body. Their errors are 404, 409, 422 and 429.

### Aggregate root, child entity or value object

The deciding question: **is there a rule that must hold at every moment across both objects?** If yes, they are one aggregate, and one of them is its root. If no, they are separate roots, and each refers to the other by id (rule 12).

Practical tests for a candidate root:

- It has its own id that other objects use to refer to it.
- It has its own repository.
- It is changed in its own transaction.
- Other aggregates refer to it.

A **child entity** has an identity only within its root and is created, changed and bounded through that root. A **value object** has no identity: it is defined by its values, is immutable (a change returns a new value) and validates on creation; where it owns no rule beyond its shape it may be a plain type (§10).

**An aggregate root is always a class in `domain/entities/`**; at minimum it can be restored from its `<Entity>Data`. A record with no behaviour that is not a root lives in `domain/value-objects/`. The data type and fact types of an aggregate are type-only files beside its entity (see "Direction of references" below), and its errors are in `domain/errors/`.

**When unsure, make them separate roots.** Joining two things into one aggregate needs a stated rule that spans them; keeping them apart needs none.

### Direction of references inside `domain/`

References point one way ([ADR 0003](adr/0003-api-module-layout.md) amendment): an entity may use value objects, errors and its companions; a value object may use smaller value objects; an error may use value objects; nothing under `value-objects/` or `errors/` imports from `entities/`, and `domain/` has no import cycle. A rule or policy that needs facts about an entity takes an input type it declares itself (the retention policy takes `RetentionFacts`, the sweep rules `RunSweepFacts`); the entity and the handlers map into it. A number shown in an error message is passed to the error by whoever raises it. A value object's own validation error (for example `InvalidProjectNameError`) stays beside it in `value-objects/`.

The type-only companions of an entity are recognised by file suffix: `<aggregate>-data.ts` (the shape the entity is restored from), `<aggregate>-facts.ts` and, when the facts are split by the operation they serve, `<aggregate>-<operation>-facts.ts` (for example `run-resume-facts.ts`). A companion exports types and interfaces only; every other file in `domain/entities/`, a `-snapshot.ts` file included, is an entity file with the existing checks. A `-data.ts` file is imported only by its own entity and by repository adapters of the same module, so a facts file or another entity declares its field types from the value objects instead of indexing the entity's data.

## 4. Feature boundaries and CQRS semantics

- Commands **change state**; queries **read state**. Keep the semantic distinction, but **no** mandatory command/query bus or `command.ts`/`query.ts` files.
- Default: one folder per use case in `application/features/`, one `handler.ts`. A command and a query with different behavior are separate features.
- Commands may persist aggregates and schedule external work through ports. Queries must not change business state.
- Queries may use a read repository port and return read DTOs directly, without reconstructing rich aggregates. The read model stays in the **same PostgreSQL** initially; no event sourcing or separate CQRS database.
- Interfaces: aggregate repositories in `domain/repositories/`; read repositories and non-domain abstractions in `application/ports/`. Implementations: `infrastructure/repositories/` or `infrastructure/adapters/`.
- **A store serves one root and touches its table only** (rule 11). An operation that needs two roots asks each store; a Project's existence, or the name of the Project that holds a remote, is a read of `ProjectRepository`, not a join in the Repository connection's store. Only an operation that must change two roots in one transaction goes through a module-owned transaction port in `application/ports/`, whose adapter runs a callback with transaction-bound stores; the callback is orchestration only, the rules stay on the entities, and the lock order is fixed and documented there (the parent before the child, for example the Project before its Repository connection). No operation in `projects` needs such a port: the Project never changes after it is created.
- **Contract naming (enforced by `architecture:api`):** an aggregate repository contract (interface, type alias or abstract class) is named `<Aggregate>Repository` and lives only in `domain/repositories/`; a read repository port is named `<Name>Reader` or `<Name>ReadRepository` and lives only in `application/ports/`. Every other contract that an `infrastructure/` class implements (`implements X`, or `extends` an abstract class) and that is declared in a business module (followed through re-exporting barrels) lives in `domain/repositories/` or `application/ports/`, never in `application/features/`, other `domain/` folders or the adapter file itself. Concrete classes such as `PrismaProjectRepository` are implementations, not contracts.
- Transport-specific request validation is local to the HTTP endpoint (a schema beside it in `entry-points/http/<caller>/`, rule 7). Handler input types are transport-independent, colocated in the handler or optional `input.ts`. No global DTO dump.
- **REST contract bridge:** Zod 4 schemas are authoritative for request and response data, converted to NestJS DTOs by `nestjs-zod` (v5-family) and documented via `@nestjs/swagger`. Run the version-appropriate `cleanupOpenApiDoc` step before emitting the canonical OpenAPI 3.1 JSON. Validate both request and response behavior where necessary. No parallel `class-validator` DTOs for the same endpoint.
- The OpenAPI document generates the browser client via `@hey-api/openapi-ts` (Fetch). Generation is reproducible and checked in CI; see [Bootstrap](../engineering/bootstrap-plan.md). The browser never imports private backend feature code.

## 5. PostgreSQL persistence and migrations

- **Prisma ORM + Prisma Migrate**, with version-compatible Prisma configuration and PostgreSQL driver adapter. Check the current Prisma major-version setup during scaffolding; do not paste legacy v6 `datasource.url` patterns into newer versions.
- The canonical Prisma schema and migration history live in `packages/database/prisma/`. Migrations are reviewed, versioned code: no unreviewed production `db push` or destructive reset. Local development generates migrations; deployment applies committed ones.
- `platform/database` creates and manages the Prisma connection; repositories receive it through DI. Concrete Prisma repositories live in the owning module's `infrastructure/repositories/`. `domain/` and handlers never depend on Prisma classes or generated database types.
- CHECK constraints and partial indexes are not modelled by Prisma; they live only in the migration SQL and are named in a `///` note on their model. With Prisma 7.10, `prisma migrate diff` proposes dropping neither (e.g. `runs_one_active_per_project_key`, the backstop of one active Run per project, Issue #96); the database integration test checks this and that the committed migrations keep the index. If a later Prisma version proposes such a drop, the author deletes that statement from the generated migration.
- **Restoring and writing an entity.** A repository maps each row to the entity's `<Entity>Data` field by field and calls `restore`; the entity copies the top-level arrays it is given and keeps nested values read-only, so neither the caller nor the stored record can change its state through them. There are two ways of writing. `Run` and `RepositoryConnection` are updated from their pending changes, because their writes are partial and run under concurrency (a lock, then only the fields an operation changed); their first insert is written from the entity's readable fields. Every other aggregate is written from the entity's readable fields, mapped explicitly. A Run's pending steps hold `RunStep` entities.
- Testcontainers-backed PostgreSQL integration tests cover repository behavior and migrations before Story 1. Simple CRUD does not justify a second ORM or separate query database.

## 6. Cross-module contracts & integration events

- The publishing module defines **one canonical, versioned Integration Event contract**, exported through its public `contracts/index.ts`.
- Prefer Zod runtime validation with inferred static TS types, plus a shared platform event envelope (e.g. `eventId`, `eventType`, `occurredAt`, optional correlation and causation IDs, `payload`).
- The handler publishes the event through the transactionally persisted outbox when the business change uses the same PostgreSQL transaction.
- Dispatcher + inbox give at-least-once, idempotent processing; multiple consumers need independent delivery tracking. See [System](system.md) §6.
- Consumers (`entry-points/consumers/`) validate/map received data and call a handler of their own module; never import another module's private handler as a shortcut.
- **No** `domain/events/` by default in the MVP.
- **Event naming and location (enforced by `architecture:api`):** each version of an event is one file `modules/<publisher>/contracts/events/<event-name>-v<n>.ts` (kebab-case name, version `n` ≥ 1, directly in `events/`). It exports only `<EventName>V<n>Schema` (the Zod schema) and/or `<EventName>V<n>` (the type), where `<EventName>` is the PascalCase file name, e.g. `execution-completed-v1.ts` → `ExecutionCompletedV1Schema` and `ExecutionCompletedV1`. The definition is local to that file: no re-export of another file's definition, no `export *`, no default export. A breaking change adds a new `-v<n+1>` file; the old version stays until its consumers have moved. `contracts/index.ts` re-exports the event for other modules.
- **One definition, one publisher:** once `<EventName>V<n>` or `<EventName>V<n>Schema` is published in a `contracts/events/` file, declaring that name anywhere else in `apps/api/src` (for example a consumer redefining the payload locally) is a competing definition and fails the gate. A published event leaves its publisher only under its own name and only through the publisher's `contracts/index.ts`: renaming re-exports (`export { ExecutionCompletedV1 as ExecutionCompletedEvent }`), alias declarations (`type ExecutionCompleted = ExecutionCompletedV1`, `const X = ExecutionCompletedV1Schema`, `interface X extends ExecutionCompletedV1 {}`, also through a namespace import such as `E.ExecutionCompletedV1`), `export default` of an event and re-exports by any other file (including `import * as E` + `export { E }`) (another module's `contracts/index.ts`, a consumer) fail; consumers import from the publisher's `contracts/index.ts`, never by deep-importing its `contracts/events/<file>`. The same `<EventName>` in the `contracts/events/` of two modules, in any versions, fails as a duplicate. An event-like declaration (`…Event`, `…EventSchema`) elsewhere in a module's `contracts/` is an unversioned event and fails too; the within-module HTTP/SSE shapes in `entry-points/http/shared/` (§2, e.g. an `ExecutionLogEvent` stream item) are outside `contracts/` and not subject to this. `contracts/events/` holds only event files (no `index.ts` barrel). Other versioned public types (e.g. a `ProjectSummaryV1` DTO) are not reserved.
- **Closed structurally (enforced by `architecture:api`):** an event file imports only from `zod`, so it cannot re-label a schema it imports; and a module's `contracts/` imports only its own module's `contracts/`, workspace packages and `zod`: no other module's `contracts/`, and nothing from `shared/` or `platform/` (a chain through them could carry a foreign event back in). So no republish form (a namespace, a destructuring, `export import`, a re-aliased namespace, a wrapped alias, a cross-module re-export) can reach another module, whatever its syntax. The cost is that one module's contracts never reference another's: a type two modules share lives with its owner and the other module declares its own. **Review-only:** wrapped aliases of a module's *own* events inside its own `contracts/index.ts` (`typeof XV1Schema`, `import('…').XV1`, `XV1 & {}`, `XV1Schema.extend({})`, `interface Y extends XV1 {}`) still pass the gate, since closing them needs type-aware analysis; a reviewer checks that `contracts/index.ts` exposes each event once, under its own name.
- An event contract crossing process boundaries is extracted to `packages/contracts` only when justified. **Never keep two competing definitions.** `packages/contracts` holds the worker protocol and the shared kernel below, and no Integration Event: a cross-process Integration Event needs a decision first, and this sentence is the gate for it. `architecture:monorepo` refuses an exported name shaped like an event version (`<Name>V<n>`, `<Name>V<n>Schema`) in `packages/contracts/src`.
- **Pure packages (Issue #275):** `@agentic-studio/log-redaction` is a dependency-free package of pure functions (the redaction rules and the Environment file's values to redact), kept in one place so `executions` and `environments` redact a log alike. The `domain/` of both modules may import it; it reads, writes and spawns nothing, and no other module needs a copy.
- **Shared kernel (Issue #101):** the provider vocabulary in `@agentic-studio/contracts` (`PROVIDERS`, `PROVIDER_NAMES`, `providerSwitchesSchema` / `ProviderSwitches`, `WorkerStatusReport`) is deliberately shared by the API and the agent worker, and the `executions` domain may import it directly instead of keeping its own copy. It holds plain values, types and Zod schemas only, no behaviour; anything else from that package stays in feature, contract or adapter code.

## 7. Worker, Git and privileged infrastructure

- `apps/agent-worker` runs on the host as the agent user, outside Studio's containers ([ADR 0002](adr/0002-agent-run-isolation.md)). It always calls the API, with a token limited to handling runs; the API never reaches into the host, and the worker has no access to the database, Redis or BullMQ. It operates through a narrowly defined CLI runner adapter in a working copy per run.
- A run is a sequence of non-interactive CLI steps. Each step streams events, ends with a structured result, and can be resumed by session id. An agent question pauses the run ("waiting for operator"); the operator's answer resumes the same session.
- **Non-agent background work** (e.g. cloning and fetching a repository) runs in BullMQ processors **hosted inside the API process**, through the platform queue capability in `platform/queue/`: a module injects the `JobQueues` port, registers a named queue with its processor during module initialisation, and enqueues jobs under deterministic ids (a duplicate waiting or running id raises `JobAlreadyActiveError`). Jobs run at most once (no automatic retries), can be cancelled and time-limited through an abort signal, and report failures to the owning module; jobs interrupted by a crash are handed to the owner's `reconcile` hook on startup and never re-run. Payloads carry identifiers only; keys live under `studio:queue`; BullMQ types stay inside `platform/queue/`. Reconciliation assumes a single API instance (the MVP deployment): it treats every job still active at startup as interrupted. `apps/agent-worker` remains reserved for CLI agent execution.
- The runner port is small and provider-agnostic; each provider (Claude Code CLI, Codex CLI) gets its own adapter. API/SDK runners are out of scope for MVP.
- Provider gate (canonical in [Security](../engineering/security.md) §2): the worker checks the fail-closed per-provider flag (`CLAUDE_CODE_ENABLED`, `CODEX_CLI_ENABLED`) before spawning any CLI subprocess, and never extracts, intercepts, shares or proxies subscription credentials.
- **Lookups (Issue #142).** Studio never reads the Git host for a Lookup (only an operator's merge or close reads it itself): `executions` records a `run_lookups` request (kinds `pull_request_state`, since Issue #145 `failing_check_logs` and since Issue #146 `review_comments`; later stories add kinds; at most one open request per Run and kind), any connected worker claims up to five over `POST /api/worker/lookups/claim` (a claim not answered within two minutes is handed out again) and answers with `POST /api/worker/lookups/:id/result` (a result of the kind, or a failure: `scope_mismatch`, `rate_limited` with how long to wait, or `failed`). The Run keeps the last known state in its `pr_*` columns, with the Pull request checks of the pull request's latest commit (`pr_checks`, Issue #145). A `failing_check_logs` result is not stored on the Run: it becomes the Run's one prepared Follow-up (`run_prepared_follow_ups`, a port of its own), which the operator reviews and sends through the normal Follow-up route with `source: "pull_request_checks"`; the lookup marks the Run as preparing (`pr_prepare_requested_at`, `pr_prepare_error`) without touching the state refresh's throttle. A `review_comments` lookup (Issue #146; `scope` and `since` on the lookup row) replaces the Run's one loaded set of Review comments (`run_review_comment_sets`, a port of its own: redacted and capped, validated by the shared contract on read, removed when a Follow-up prepared from it is sent); its state (loading, last error) is read from the lookups, not from Run columns. The page-open refresh is asked at most once a minute per Run, Refresh at any time, and an API schedule asks daily for Runs whose pull request is open or unknown.
- **Operator operations on a Run (Issue #167).** A Run changes at the same time by the operator and by the agent worker. What the operator triggers (answer, Follow-up, cancel, delivery retry, resume after the usage limit) is a method of the `Run` class: it checks its preconditions against the Run's own state and the facts passed in, refuses with a domain error, and records what changed. The handler calls `RunRepository.change` (or `changeSerializedWithClaims` for a resume, or the module's `RunTransactions` for a Follow-up, see below), which in one transaction loads the Run `FOR UPDATE`, calls the handler's pure callback, and saves the recorded changes. The row lock serializes the change with every other change of the Run: what the agent worker reports for the Run is a method of `Run` run through the same `change` (Issue #169), and the set-wide sweeps and the hand-out are single statements that wait for the lock and then re-check the row, so two simultaneous requests cannot both win. No version column and no retry loop are needed.
- **Worker-triggered operations on a Run (Issue #169).** What the agent worker reports for one Run (a state, including a delivery retry's outcome and a bring-up-to-date request that changed nothing; a Run step with its Question, step limit and usage; a heartbeat; the removal of a Working copy; the Environment file of a claim) is also a method of `Run`, which checks that the reporting worker holds the Run (a late report from a worker that lost its claim is refused with `RunNotHeldError`). The handler uses the same locked `change`. Two kinds of operation stay in the repository, each paired with a named rule in the domain that supplies its selection and its result, and a test that runs the store's statement over fixture rows and compares it with the rule: the hand-out of the next Run (`claimNext`, one atomic statement under the claim lock that locks the row it selects, waits for another transaction that holds it and re-checks it, so the queue order is strict and a cancelled Run is never claimed; `HandOutRule`) and the sweeps over many Runs (lost workers, `LostWorkerRule`; overdue steps, `OverdueStepRule`; Runs waiting too long, `LongWaitRule`; gone workers, `GoneWorkerRule`; the once-per-lease renewal, `LeaseRenewalRule`). The handlers build these rule objects and pass what they supply to the store.
- **Operations across aggregates (Issue #183).** No repository reads or writes another root's table, and no root holds or loads another (rules 11 and 12). The few operations that must change a Run and another root in one transaction go through the module-owned port `RunTransactions` (`application/ports/`): its adapter opens one transaction, locks the Run's row first, and hands the callback transaction-bound repositories; the callback only orchestrates (it loads, calls entity methods with facts passed as values, saves), and every rule stays on an entity. **Lock order, everywhere: the Run, then the lookup, then the other roots** (Review comments, prepared Follow-up, Run diff), so two operations on one Run run one after the other and cannot deadlock. The operations: the Follow-up (the Run's `followUp` takes what the selection of Review comments came to as values and returns what it used up; the set or the prepared Follow-up is removed in the same transaction); requesting a lookup (the lookup and the Run's pull request marks; the collaborator `RunLookupRequests`); answering a lookup (the lookup's own `complete` or `fail` decides, then the Run's pull request status, the prepared Follow-up or the Review comments are changed); reporting diffs (the Run's `assertDiffReportableBy`, then the Run diff). Handing out lookups stays one atomic statement of `RunLookupRepository.claim`, which joins the Run read-only for what the worker needs, paired with the named rule `LookupHandOutRule` and a test that runs the statement over fixture rows and compares it with the rule. The Run step is a child entity: only the Run creates one (`Run.reportStep` checks the number and the limit from its own `stepCount`), steps are stored in their own table and counted with every Run that is loaded, and listing them is a query. The Run log's events are append-only records, stored through the `RunLog` port (not an aggregate repository).
- **Run hand-out, reports, streaming and snapshots in `executions`.**
  - *Hand-out.* A Run with an agent session or a delivery retry goes only to the worker that last claimed it, because that worker alone has its Working copy. A Run holds a place while it is active, while a worker holds a `failed` Run for a retry, and while an answered Run waits in the queue; at most two places across the server and one per Project, and a Run's own place does not count against it. A lookup claimed for at least the lease goes back to `requested`; lookups whose rate-limit wait has not ended are skipped; a lookup is handed out only when its Run has a pull request and a known Run branch (oldest first, ties by id).
  - *Reports.* A `cancelled` report without a cancel request is refused. A step that ends `waiting_for_operator` after a cancel request ends the Run as `cancelled`. A `succeeded` report keeps its delivery. A bring-up-to-date Follow-up that changed nothing returns the Run to its earlier result. A rate-limited lookup returns to the queue; a failed lookup keeps the last known state and records the redacted reason; a repeated answer changes nothing.
  - *Review comments.* With `since_last_result` a comment is new when created after the end of the Run's latest part; a Run that has not finished counts every unresolved comment. They load only for a Run that can take a Follow-up now.
  - *Environment file snapshot.* The snapshot is deleted once the Run is final, except while a failed delivery can be retried or a Run can resume after the usage limit; otherwise on give-up or after retention. A resume goes only to the worker that holds the Working copy; a Follow-up takes the current snapshot, replacing the earlier one. Log redaction: lines that are not `KEY=VALUE` are redacted whole from 8 characters, known values under 4 characters are left out, and the values of commented-out pairs are redacted too.
  - *Streaming.* The run event stream opens with a `: connected` comment and sends `: keep-alive` every 15 seconds; a final Run ends with an `end` event, so a stream that closes without it was dropped. At most 5 streams per session and 50 in total (429 beyond); the session check is timed because a busy stream never idles.
  - *Request bodies.* Endpoints that type the body as `unknown` skip the global validation pipe; the endpoint's schema turns an invalid body into a 422, not a 400.
  - *Limits and retention.* The defaults of the Run limits (`STUDIO_RUN_STEP_MINUTES`, `STUDIO_RUN_MAX_STEPS` per part, `STUDIO_RUN_WAITING_DAYS`, `STUDIO_RUN_MAX_TOTAL_STEPS`, `STUDIO_WORKER_LEASE_SECONDS`, `STUDIO_RUN_SNAPSHOT_RETENTION_DAYS`) are in `.env.example`; Working copy retention is in the [deployment guide](../engineering/deployment.md#working-copy-retention-and-disk).
  - *Lease renewal.* At API start the held Run leases are renewed, so a short outage does not fail Runs with `worker_lost`; a gone worker is noticed one lease later. Renewal happens at most once per lease period, so an API that keeps restarting cannot keep a dead worker's Run alive. The sweeps run every half lease, at most every 30 seconds.
- The worker and its agents have **no access to the system Docker daemon or socket**, privileged Compose access, production DB credentials, Studio's files or unrestricted filesystem access. Agents may use the agent user's rootless Docker daemon ([Security](../engineering/security.md) §2).
- Docker Compose actions go through `apps/environment-controller`. It runs on the host as the Preview user and always calls the API, with its own token limited to Preview work ([ADR 0004](adr/0004-preview-isolation.md)); the API never reaches into the host.
- **The controller protocol (Issue #275).** The environment controller reaches the API only over `/api/controller/`, which `SessionGuard` opens to the controller token (`STUDIO_CONTROLLER_TOKEN`) and to nothing else: worker routes take only the worker token, every other route only a session, and an unset controller token answers 401. The routes are `POST operations/claim` (200 with the payload, 204 when there is nothing to do), `POST operations/:id/state`, `POST operations/:id/log` and `GET operations/:id/source`; their bodies are the shared contract `packages/contracts/src/controller-protocol.ts`, an invalid body is a 422, an unknown operation a 404 and an operation the controller does not hold (or that is final) a 409. A Preview operation (`PreviewOperation`, `environments`) is `build`, `stop`, `remove_data` or `state`: requested, claimed by one controller process, then succeeded or failed. The claim is one serialised transaction of `PreviewOperationRepository.claimNext`: a claim lock, then one selection statement with `FOR UPDATE SKIP LOCKED`, then the entity's `claim`, paired with the domain rule `PreviewOperationHandOutRule` and a test that runs the statement over fixture rows and compares it with the rule: the oldest `requested` operation of a Project with no claimed one. A log batch has a route-specific JSON parser, limited to the controller token, that covers the worst-case escaping of its 64 KiB. A partial unique index allows one claimed operation per Project. An `in_progress` report every 15 seconds is the heartbeat; the claim first fails every claimed operation whose last report is older than `STUDIO_CONTROLLER_LEASE_SECONDS` (default 60) with `controller_lost` (`failLost`, paired with `LostControllerRule`), and such an operation is never handed out again. A build is requested by the `request-preview-build` handler (the Preview bullets below): it snapshots the Preview settings, the commit whose Compose file was judged and the limits (`STUDIO_PREVIEW_MEMORY_MB`, `_CPU_PERCENT`, `_TASKS_MAX`, `_BUILD_MINUTES`). The claim of a build reads the Project's Environment file through `RUN_ENVIRONMENT_FILES`, keeps a snapshot in the secret store (owner `environments.preview-environment-file`) and hands the content to the holder only; the snapshot is deleted when the operation is final or the lease fails it, and a start-up sweep removes snapshots no operation references that are older than an hour. The source is `git archive` of the build's commit from the Clone, with `$GIT_DIR/info/attributes` set to `* -export-ignore -export-subst` first so the tree's own attributes cannot change what is archived, written to an owner-only temporary file under `<STUDIO_DATA_DIR>/tmp/preview-archives/` (at most 256 MiB; Git is killed above it), streamed with its `Content-Length` and deleted afterwards and by a start-up sweep. Log lines are redacted with the snapshot's values and the log rules (`packages/log-redaction`, the rules `executions` also uses), cut to 2048 bytes and stored under `STUDIO_PREVIEW_LOG_MAX_BYTES` (default 2 MiB); at the cap one notice line is stored, later lines are dropped and the answer says `truncated: true`. A re-sent `seq` is ignored.
- **The Preview and its build (Issue #278).** There is no `previews` table and no second aggregate: a Preview build is a `PreviewOperation` of kind `build`, and the Preview is a value derived from the Project's operations, `PreviewState.of({ configured, latestBuild, runningChange, latestChange })`.
  - `latestBuild` is the newest build by `requested_at`; at most one build is active (`requested` or `claimed`), and it is the newest. `runningChange` is the newest finished operation that changes what runs, by `finished_at` with ties broken by `id`: a succeeded build, a succeeded stop or `remove_data`, a failed build with `previewRemoved`, or a succeeded `state` check with `previewRemoved`. `latestChange` is the newest stop or `remove_data` by `requested_at`. `PreviewRunningRule.changesRunning` is that selection, paired with `PreviewOperationRepository.findPreviewFacts` by a fixture test. "Running" means what Studio asked for: the controller's resume handles a daemon restart, and the live runtime state is not read.
  - The state is, in order of precedence: `resetting_data` while a `remove_data` is requested or claimed; `stopping` while a `stop` is; `building` while the latest build is requested or claimed; `running` when `runningChange` is a succeeded build; `not_configured` without settings; `failed` when the latest build failed; otherwise `stopped` (settings that were never built are `stopped`). `PreviewState` also holds `changeActive` and the three refusals (`buildRefusal()`, `stopRefusal()`, `resetRefusal()`), each the domain error a handler throws: `PreviewBusyError` while a stop or reset is active, `PreviewBuildRunningError` while a build is, `PreviewNotRunningError` for a stop of a Preview that does not run. A failed build beside an earlier one that still runs leaves the Preview `running`, and the latest build still shows its failure. The `GET /api/projects/:id/preview` answer and the answer of a settings save both carry the state, the running build (`running.url` is `https://<hostname>/`, or `null` without a preview domain), the latest build and `controller.connected`; `PreviewStateReader` reads them for both.
  - **What a failed build leaves running.** A failure before `up` leaves the previous Preview running. A failure at or after `up` makes the controller roll back, which removes every labelled container of the Project, the previous Preview included; it reports `failure.previewRemoved: true` (also with `controller_stopped` during `up`), and the entity records it for a failed build only. When the controller loses its lease after `up`, the rollback still removes the previous Preview, but the API fails the build (`controller_lost` or `report_overdue`) with `previewRemoved` false. The state check closes that: a succeeded `state` operation that finds no labelled container running records `previewRemoved = true` (kind `state` only), `PreviewRunningRule` counts it as a change of what runs, and the Preview stops showing the old build as running. Sweep step 4 requests the check (see Sweeps).
  - **The build request** is `POST /api/projects/:id/preview/builds` (session and Origin, no body, 202 with the queued build). It checks, in this order: the Project exists (404), the settings exist (409 `preview-not-configured`), the Repository is ready (409 `preview-repository-not-ready` or `preview-unsupported-platform`), a controller is connected (409 `preview-controller-unavailable`), no build is active and no stop or reset is (409 `preview-build-running` or `preview-busy`), then `PreviewComposeJudge` reads the Compose file and validates it (422 `preview-refused` with the refusals, 502 `preview-source-unavailable`). The commit snapshotted on the build is the commit of that read, so the commit that was validated is the commit that is built, and no fetch happens first. A build carries its own snapshot of the settings, so settings removed between the read and the insert do not affect it. The save of the settings uses the same collaborator. The early check is cheap; the authoritative one runs in the request transaction (below), and the backstop is the partial unique index `preview_operations_one_active_build_per_project`, whose violation is the same 409. The shared steps live in the named collaborator `application/preview-build-requests.ts`, used by the build route and by Reset. Removing the settings is refused while a build is active (`PreviewBuildRunningError`, 409 `preview-build-running`) and while the Preview runs (409 `preview-running`); Stop lets the settings be removed.
  - **Presence.** Every controller call (claim, state report, log append) is recorded in memory (`CONTROLLER_PRESENCE`), so it is the view of one API instance and starts empty. `ControllerAvailability` is `connected` within one lease of the last call, and `knownAbsent` when it is not connected and the API has run for at least one lease.
  - **Sweeps.** `PreviewSweepsScheduler` runs `sweep-preview-operations` every `min(30 s, lease / 2)`, four steps, each statement paired with a rule and a fixture test: `failLost` (`LostControllerRule`, now periodic, so a restarted controller leaves the old build `controller_lost` after one lease), `failOverdue` (`OverdueBuildRule`: a claimed build whose `claimed_at` plus its build minutes plus 5 minutes has passed becomes `report_overdue`, which covers a hung operation whose heartbeat keeps the lease alive) and `failUnclaimed` (`UnclaimedOperationRule`: only while the controller is known absent, a requested operation older than `STUDIO_PREVIEW_UNCLAIMED_MINUTES`, default 5, becomes `not_claimed`). The snapshot of a failed claimed operation is deleted, as the claim does. Step 4, `requestStateChecks` (`StateCheckRule`, paired with `findStateCheckProjects`), inserts one `state` operation for each Project whose newest operation is a claimed build that failed with `controller_lost` or `report_overdue`; the state check is then the newest operation, so the step is idempotent. `not_claimed` and `report_overdue` are set by the API only, like `controller_lost`.
  - **The request transaction and the running limit.** Every operator build, stop and reset goes through `PreviewOperationRepository.request(projectId, decide)`, kind `atomic`: one transaction takes `pg_advisory_xact_lock(hashtext('studio.environments.requests'))`, reads the Project's facts and `findOccupyingProjects`, calls the pure `decide` and inserts what it returns, so requests of different Projects are serialized. The I/O of a build request (Project, settings, source, controller, `PreviewComposeJudge`) happens before it. A Project takes a place of the limit while its Preview runs or a build of it is requested or claimed (`PreviewRunningLimitRule`, paired with `findOccupyingProjects` by a fixture test); `PreviewStartLimit.of(max).refusal({ projectId, occupying })` refuses a Project that holds no place when `max` are taken, so a rebuild of a running Preview never takes a new one. `max` is `STUDIO_PREVIEW_MAX_RUNNING` (default 3, 1-50). The refusal is 409 `preview-limit-reached` with `running: [{ projectId, name, state }]`, the names read after the transaction through `RunPreviewSources.projectNames`. `GET /api/previews` answers `{ limit, previews: [{ projectId, state }] }`.
  - **Stop and Reset data (Issue #279).** `POST /api/projects/:id/preview/stop` and `POST /api/projects/:id/preview/reset-data` (session and Origin, no body, 202 with the Preview) need a connected controller (409 `preview-controller-unavailable`). Stop is accepted only for a running Preview (409 `preview-build-running`, `preview-busy` or `preview-not-running`). Reset is accepted in every state but while a build (409 `preview-build-running`) or a stop or reset (409 `preview-busy`) is active; it needs no settings. For a running Preview one transaction inserts `remove_data` and then a build made from the running build's own snapshot (commit, Compose file, service, port) with today's limits, requested one millisecond later so the hand-out rule runs it after the removal; the controller validates the file again. A partial unique index `preview_operations_one_active_change_per_project` allows one requested or claimed stop or `remove_data` per Project, and its violation is `PreviewBusyError`. `latestChange` on the Preview shows the newest stop or reset, so a failed one stays visible.
  - **Removal on disconnect.** `projects/contracts` holds `REPOSITORY_DISCONNECT_STEPS`, a list other modules add a `RepositoryDisconnectStep { name; run(projectId): 'done' | 'pending' }` to; `environments` adds its step when its driving adapter is built, so the start-up resume already runs it. `RepositoryCleanup` runs the added steps before it removes the Clone; `pending` or a throw leaves the Repository `disconnecting`, and Disconnect is never refused. `remove-preview-for-disconnect` follows `PreviewDisconnectRule`: no operation deletes the settings; no build ever claimed deletes the settings and the operations; a succeeded `remove_data` as the newest operation with nothing active deletes the settings, the operations and their lines; otherwise it inserts a `remove_data` unless one is active, and is pending. Without a controller the removal fails as `not_claimed` and the next retry inserts it again. `RepositoryDisconnectsScheduler` (`projects`) runs `resume-disconnects` every 30 s. Project deletion does not exist and is out of scope.
  - **The rebuild after a merge through Studio.**
    - **Direction.** `executions` tells `environments` through `environments/contracts` (`MERGED_RUN_PREVIEWS`), whose driving adapter maps to `record-merge-rebuild` and `get-preview-of-merge`. No outbox exists and none is needed, and polling `executions` would be a timer reading another module's tables. `ExecutionsModule.register(projects, environments)` imports the module, which exports the symbol.
    - **When it is called.** `MergeRunHandler` calls `merged({ projectId, runId, mergedCommit, mergedAt, fetchStartedAt })` right after it stored the approval with its Clone fetch start, so the first merge, a reconcile and the re-entered `finishAfterMerge` all take the same path. The call is wrapped in `try/catch` and its result ignored; the adapter never throws either. A merge is never delayed, failed or undone by the Preview, and nothing is called when the fetch did not start or from `close-pull-request`.
    - **The aggregate.** `PreviewMergeRebuild` (table `preview_merge_rebuilds`, one row per Project) is stored only while the Preview is `running` or `building`: a merge never starts a stopped, failed or unconfigured Preview, and the page shows "behind". A newer merge replaces the row, so the latest Run wins and a failure clears. `run_id` has no foreign key into `executions`, and `project_id` cascades with the Project.
    - **The rule.** `MergeRebuildRule.decide({ state, runningCommit, source, rebuild, now })` returns `wait` (a build or a change is active, the Clone is not ready, or the Clone does not hold the merge yet), `drop` (the Preview is no longer `running`, or the running commit is the Clone's commit) or `build`, and `give_up` once a wait lasted 30 minutes after `recordedAt`, with the last reason. The Clone holds the merge when its commit is the merged commit or its last fetch (`PreviewSourceStatus.ready.fetchedAt`) is not before `fetchStartedAt`.
    - **The release.** `PreviewMergeRebuildsScheduler` runs `release-merge-rebuilds` every 5 s without overlap. The handler loads the rows, reads the source status and the state, applies the rule and requests the build through `PreviewBuildRequests` (the same request transaction and refusals as the operator's route): the build is of the Clone's Integration commit, is stored with `started_by_run_id`, and the row is deleted. A 422 `preview-refused` or an unreadable file fails the row at once with the reason; a missing controller, a build, a change or the limit are waits. The timer carries out a request a merge recorded and never creates one, so "nothing else starts a build" holds. A failed row is removed once the operator requests a newer build or the Preview stops.
    - **The answers.** A build carries `startedBy` (`{ kind: 'operator' }`, Reset included, or `{ kind: 'merge', runId }`); the Preview carries `behind` (the Clone is ready and `running?.commit ?? latestBuild?.commit` differs from its commit) and `mergeRebuild` (`waiting` or `failed`, with a reason and `since`). The single-Run answer carries `previewAfterMerge: { projectId, state }` only when its latest approval was carried out, read through `forMerge(projectId, runId, mergedCommit, mergedAt)` (`PreviewAfterMergeRule`: `not_configured`, `not_started`, `waiting`, `building`, `running`, `failed` or `replaced`; a Run with no row and no build of its own reads `replaced` when any build was requested at or after `mergedAt`, else `not_started`); a Preview that cannot be read leaves it out.
    - **Disconnect.** The Preview's disconnect step deletes the Project's row first.
  - **The build log is read by polling**, not by a stream: `GET /api/projects/:id/preview/builds/:buildId/events?after=0&limit=500` (at most 1000) answers `{ events, next?, final, truncated }`. A Preview log is at most 2 MiB, and the Run stream's internals are private to `executions`. Lines are redacted when they are appended, so the route only reads; `redacted` says the text holds the marker. `final` is read before the lines, so a final build's lines are all stored; the client reads on from `next` until `final` is true with no `next`. An unknown id, an operation that is not a build and another Project's build are the same 404 `preview-build-not-found`.

- **The `environments` module** owns a Project's Preview settings, the Preview and its states, and builds and their logs. It does not own Runs, the Project's Clone or Git. It learns that a Run was merged through its own public face, not through `executions`': the module order is `projects` <- `environments` <- `executions`, so `executions` tells `environments` and no cycle exists (see "The rebuild after a merge" above). A merge made on the Git host does not start a build; after a fetch the Preview page says it is behind and offers "Rebuild".
- **The `workflows` module** ([ADR 0007](adr/0007-workflows.md)) owns the Workflow definition and decides which Phase comes next. `executions` owns the Run and its Run steps and reports each result; it imports nothing from `workflows`. A Run with a Workflow starts through `workflows`: it resolves the Workflow at the definitions commit and asks `executions`, through its public face, to create the Run with its ordered Phases; `executions` reports each Run step result through a port or event that `workflows` handles to decide the next Phase, and a Project default that names a Workflow is resolved the same way. `workflows` reads Workflow files of the Clone through the public face of `projects`, as `agents` does; it judges the agents its Phases name through the public face of `agents` and Provider availability through the public face of `executions`; none of the modules imports another's private files. A Phase is carried out as ordinary Run steps, so the Run's limits, state and delivery stay with `executions`. The exact format and limits belong to the format ticket (#345).
  - **As built: reading Workflows** (#346). `workflows` has two features, `read-workflows` (`GET /api/workflows`) and `read-workflow` (`GET /api/workflows/:name`), over one collaborator that reads the `workflows/` folders of the Clone at the last fetched commit through `projects`, judges each with `validateWorkflowFolder`, then judges the agents the phases name through the public face of `agents` (`AGENT_STANDINGS`: valid or not, and the Provider) and the Providers through the public face of `executions` (`PROVIDER_AVAILABILITIES`, the list the agent workers report). A Workflow is valid when its folder and every agent its phases name are valid, and usable when it is valid and every Provider its phases use is available now; the reason names the phase and the Provider. The judged folders are kept per commit (the four latest) with the same read budget, list bound (200) and fail-closed behaviour as the skills; the agents and the Providers are judged again on each request. `GET /api/agents/:name` also answers `usedByWorkflows`, which `agents` computes itself from the `workflows/` entry files at the same commit (`workflowAgentNames`), so `agents` never imports `workflows`. Publishing Workflow files stays refused until the editor Story.
- Git belongs to `projects`; other modules consume its public interfaces, not its adapter or repositories. The agent worker pushes run branches through the agent account, not through the adapter ([Security](../engineering/security.md) §4).
- External Git/Docker/CLI operations cannot be rolled back by a DB transaction: expose explicit states, timeouts, error handling and reconciliation.
- **The `agents` module** (Epic #298, [ADR 0005](adr/0005-agent-definitions-in-git.md)) owns the list of agents, the validation of a definition, drafts and publishing. A definition is a folder in the definitions Repository, so the module keeps no copy of it in the database except the pointers and drafts: which Repository it is, each Project's default agent and unpublished changes. It does not own the Repository connection, the Clone or Git, Runs, or the worker's delivery.
  - **How other modules take part.** `projects` supplies reading from and writing to the Clone through its public `contracts/` face; `agents` never imports the Git adapter. `executions` records what a Run used (the agent, the commit, the model and a copy of the instructions) through the public face of `agents`, which resolves a chosen agent at a commit into its validated definition. The module order is `projects` <- `agents` <- `executions`; none of them imports another's private files.
  - **Validation** refuses unknown front matter keys and any key that asks for tools, permissions, hooks or MCP servers, applies limits on file count, size per file and size per folder, and refuses a path that leaves the folder. An invalid agent is listed with its reason and cannot be chosen. The limits are fixed in the validation's code, not in this document.
  - **The definition format** (Issue #300) is written and checked by one pure package, `packages/agent-definitions` (`@agentic-studio/agent-definitions`), which the API and the web app share: it imports only `yaml`, its own files and the zod-free subpath `@agentic-studio/contracts/providers` (the Provider ids and models), no Node module, and reads no file system; `architecture:monorepo` enforces it, and also that the subpath file imports nothing. The package re-exports `PROVIDERS`, `PROVIDER_MODELS`, `MODEL_DEFAULT` and `Provider`, so the web app takes them from it and never imports the contracts. `validateAgentFolder(name, entries)` takes `{ path, kind, size, content? }[]` with paths relative to the folder and answers `{ ok: true, definition }` or `{ ok: false, problems }`; `findAgentFolders(repositoryEntries)` groups a Repository tree into agent folders, so the list, the editor and the hand-over to a Run judge a folder the same way. A problem is `{ code, path, key?, message }`: the message quotes at most the offending key or path, never a value or file content.
    - **Workflows** ([ADR 0007](adr/0007-workflows.md)) are judged by the same package: `validateWorkflowFolder`, `findWorkflowFolders` (only under `workflows/`) and the pure `checkWorkflowAgents`, with the reasons in `WORKFLOW_PROBLEM_CODES`. The format (the folder `workflows/<name>/` with the one entry file `WORKFLOW.md`, its keys, items and order rules) is described in the package README and fixed by the validation's code and fixtures.
    - **Layout.** An agent is the folder `agents/<name>/` of the definitions Repository, and its entry file is `agents/<name>/AGENT.md`. Studio's skills are the separate Skill definitions of `skills/<name>/` ([ADR 0006](adr/0006-skill-definitions.md)), validated and delivered on their own; anything else outside `agents/` and `skills/` is ignored.
    - **Entry file.** UTF-8 text: YAML front matter between two `---` lines, then the instructions in Markdown. The front matter is one YAML mapping (core schema; duplicate keys, aliases, custom tags and non-text keys are refused). Required keys: `name`, `description` (one line of 1 to 500 characters) and `provider` (one of `PROVIDERS` in the contracts). Optional: `model`, which defaults to `default` ("the CLI's default") and must be in `PROVIDER_MODELS[provider]`, the one list in `packages/contracts/src/providers.ts` (re-exported by the contracts index), whose values are those of the Provider compliance records. A `name` matches `^[a-z0-9][a-z0-9-]{0,63}$` and equals the folder's name; the names `default-claude-code` and `default-codex` (one per Provider, the built-in Default agents) and `definitions-repository` (a fixed path of the agents API) are kept by Studio (`RESERVED_AGENT_NAMES` in `limits.ts`), so a folder with one of them is `name_reserved`. The description is refused when it is blank, longer than 500 characters, or holds any control character, NEL (U+0085), U+2028 or U+2029. **Consumers use the parsed fields, above all `definition.instructions`, and never hand the raw `AGENT.md` to a CLI**: a CLI's own parser may cut the front matter at a different line than this one does.
    - **Refused keys.** Any other key is `unknown_key`. A key that asks for tools, permissions, hooks, MCP servers, memory or isolation is `forbidden_key`, a separate reason: `FORBIDDEN_KEYS` in `limits.ts` lists them, and a key is compared after lower-casing and removing `-` and `_`, so `allowed_tools` and `Allowed-Tools` are caught too. The validation fails closed: what it does not know is refused.
    - **Limits** are exported constants in `packages/agent-definitions/src/limits.ts`: `MAX_INSTRUCTIONS_BYTES` (64 KiB), `MAX_FRONT_MATTER_BYTES` (8 KiB), `MAX_FILES` (100), `MAX_FILE_BYTES` (1 MiB) and `MAX_FOLDER_BYTES` (5 MiB). A `size` that is not a whole number of bytes of zero or more is `size_invalid` (the entry file is also measured by its text). A path that is absolute, has a `..`, `.`, empty or backslash segment, or a control character is `path_outside_folder`; an 8.3 short name such as `PROGRA~1` (`^[^.~]{1,6}~\d+(\.[^.]{0,3})?$`, any case) is `short_name`; any `.git` segment, or a lookalike that Git or another file system reads as `.git` (`.GIT`, `.git.`, `git~1`, a zero-width character inside), is `nested_git`; two paths that differ only in case are `duplicate_path`; a symbolic link is `symlink_refused` and any kind other than file and directory is `kind_refused`.
    - **No CLI settings in any form.** Inside an agent folder, any path segment that starts with `.` (`.claude/`, `.codex/`, `.mcp.json`, `.agents/`) and any file named, in any case, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, `AGENTS.override.md` or `SKILL.md` is `cli_config_path` (`CLI_DISCOVERED_FILES` in `limits.ts`); names are first normalised like the `.git` lookalikes (zero-width characters and BOM removed, trailing dots and spaces stripped, case folded). Agent CLIs discover settings, hooks, MCP servers, skills and memory from these places, and a definition carries no settings in any form (security.md).
    - **Reasons.** `PROBLEM_CODES` lists every one, each with a failing fixture in the package's tests (`entry_missing`, `entry_unreadable`, `front_matter_*`, `key_missing`, `key_invalid`, `provider_unknown`, `model_unknown`, `name_invalid`, `name_mismatch`, `name_reserved`, `unknown_key`, `forbidden_key`, `instructions_too_large`, `too_many_files`, `file_too_large`, `folder_too_large`, `path_outside_folder`, `nested_git`, `symlink_refused`, `kind_refused`, `duplicate_path`, `size_invalid`, `cli_config_path`, `short_name`).
  - **Publishing** makes one commit and pushes it as a fast-forward only; when the Repository moved since the draft began, it is refused and the difference shown. A draft reaches no agent.
  - **Default agents.** One built-in Default agent per Provider exists without a Repository, and each Project can name its own default agent.
  - **The definitions Project (Story #301).** `projects.kind` is `code` (every earlier Project, the default) or `definitions`, set when the Project is created and never changed: no update route takes it, and the `projects_kind_check` constraint keeps the list. A partial unique index (`projects_one_definitions_key`, `UNIQUE (kind) WHERE kind = 'definitions'`) makes at most one, so a second create answers 409 `definitions-project-exists`, also for parallel creates. `POST /api/projects` takes `kind` (default `code`); every Project answer carries it.
    - **Refusals.** `projects` publishes `PROJECT_KINDS` (`kindOf(projectId)`, `null` for an unknown id, and `definitionsProjectId()`) through its `contracts/`. The handlers of Run start and list, of Preview settings (save and remove), build, stop and reset, and (inside `projects`) of the Environment file (set, read, remove) each check the kind first and answer 409 `definitions-project` with a `refused` member (`run`, `preview` or `environment_file`). No module reads another module's tables for it.
    - **The worker pin.** The Run claim and the lookup claim handlers ask `PROJECT_KINDS.definitionsProjectId()` and pass the id (or `null`) to the repository, whose claim statement adds `AND r.project_id <> $id` only when it is not `null`. A hand-inserted Run of a definitions Project is therefore never handed out, and `executions` reads no `projects` table.
    - **The Agents route.** `GET /api/agents/definitions-repository` (session and Origin only; the worker and controller tokens are refused) answers `{ project: null }` or `{ project: { id, repository } }` with `repository` null until one is connected, else its state, Integration branch, last fetched commit (`headSha`) and `lastFetchedAt`. It reads through `DEFINITIONS_REPOSITORIES` of `projects/contracts`; the connection steps, Fetch and Disconnect are the existing `projects` routes with that id, and a Disconnect leaves the Run records alone.
  - **The agents list and detail (Story #302).** `GET /api/agents` and `GET /api/agents/:name` (session and Origin only; the route inventory refuses the worker and controller tokens) show the agents Studio knows. No table holds them: each request is computed from the definitions Project's Clone at the last fetched commit, so a fetch that brings new commits shows on the next request.
    - **Reading the Clone.** `projects` publishes `DEFINITIONS_FILES` through its `contracts/`: `snapshot()` (the Repository state and last fetched commit, or `null` when no definitions Repository is connected), `listTree(commit, { whole?, directory? })` (`{ path, kind, size }` for everything under `agents/`, under `skills/` with `directory: 'skills'`, or with `whole` for the whole tree, at most `DEFINITIONS_TREE_MAX_ENTRIES`, with `truncated`) and `readFiles(commit, paths, maxBytes)` (each file `found` with its text, `too_large`, or `missing`, with its `size` in bytes). They run through the Git adapter's `listTreeAtCommit` (`ls-tree -r -l`) and `readFilesAtCommit` (`ls-tree` and `cat-file blob`), from Git's object store, with no checkout and no working-tree change; a path that names no regular file is `missing`. They take no per-project lock (they read objects Git never rewrites, so a running fetch neither delays them nor is delayed) and have their own 10-second budget. A Clone that cannot be read answers `repository_not_ready`, `unsupported_platform` (the API is not on Linux), `commit_missing` (the Clone holds no such commit) or `failed`. `agents` never touches Git or the file system; for agents it takes the tree, reads only each `AGENT.md` (up to `MAX_FILE_BYTES`; over it, or not UTF-8 text, the package gives the problem) and judges each folder with `findAgentFolders` and `validateAgentFolder`, and in no other way. Every other file of an agent contributes its size only; skills are read as the Skills bullet says.
    - **One use case.** The list and the detail share their steps, so they are one feature, `read-agents`, with two entry points. Since a commit never changes, the judged list of a commit is kept in memory for the four latest commits asked for (least recently used out first), so a page refetching on focus starts no Git process; a new commit is a new key, and nothing is stored in the database. An entry file over the size limit is never read and gets `file_too_large` only.
    - **Answer.** `GET /api/agents` answers `{ commit, repository, truncated, baseRules, agents }`. `commit` is the commit the agents were read at, `null` when none were. `repository` is `null` without a definitions Repository, else `{ state, note }` where `note` is `null` for a `ready` Repository and otherwise says why the agents are the last known ones or none (a Repository that is not ready with a Clone shows its commit's agents with the note; one without a Clone, or a Clone that cannot be read, shows only the built-in agents with the reason). `baseRules` is `{ version, text }`, plain text. Each agent is `{ name, description, provider, model, source, usable, problems }`; `source` is `built_in` or `definitions`, and a refused agent has `usable: false`, `description`, `provider` and `model` null, and each problem as `{ code, path, key, message }`. `GET /api/agents/:name` answers `{ commit, repository, agent }` where `agent` adds `instructions` (plain text, empty for a built-in or a refused agent) and `files` (`{ path, size }` of every file of the folder, empty for a built-in); an unknown name is 404 `agent-not-found`. The fixed `definitions-repository` route is registered first, and that name is reserved, so no agent has it. Rows are unique by `source` and `name`: a folder named like a built-in agent is listed (refused) beside it, and `GET /api/agents/:name` for that name answers the built-in.
    - **Skills (Story #329).** `GET /api/skills` and `GET /api/skills/:name` (session and Origin only) show the skill folders (`skills/<name>/`) of the same commit through the feature `read-skills`, judged by `validateSkillFolder` and memoised per commit like the agents; the Draft is never read. The list answers `{ commit, repository, truncated, skills: [{ name, description, valid, problems }] }` with at most 200 skills, and the detail `{ commit, repository, name, description, valid, problems, instructions, files }`; an invalid skill has a null description and its problems, a name that is not a valid skill name is a 404 `skill-not-found` before any lookup. The entry file and every Markdown file of a folder are read, since the validation looks for shell lines in them. A folder the declared count and sizes already refuse (`too_many_files`, a file or the folder too large) is judged from the tree alone, with no read and no "cannot be read" reasons. One list reads at most `MAX_READ_PATHS` (500) files and `MAX_READ_BYTES` (16 MiB): skills are taken in name order up to the last one read in full, and `truncated` is set when the budget or the 200 bound cuts the list. The detail reads only its own folder, so a skill beyond the cut still has one. The tree is listed for `skills/` only (`listTree` takes a `directory`), so a large `agents/` folder cannot cut the skills off.
    - **Skills an agent names (Story #330).** An agent lists skills in the optional front matter key `skills` (see the package README). `GET /api/agents` and `GET /api/agents/:name` answer `skills: string[]` (the names as listed; empty for none, for a built-in agent and for a front matter that cannot be read), and `GET /api/skills/:name` answers `usedBy: string[]` (the agents at the same commit whose front matter lists it, valid or not, sorted). The agents and skills readers (`application/agents-reader.ts`, `application/skills-reader.ts`) judge an agent with `checkAgentSkills` against the skills of the same commit: named skills are read on demand when the list was cut, so a named skill is never missing because of the budget, and what each named skill turned out to be is kept per commit (up to 200 unique names read on demand; beyond that, or when the skills listing is itself cut, the skill counts as invalid, the same on every request), and a skill that cannot be judged makes the agent invalid with `skill_invalid`. Only a transient read failure is not kept. The skill detail also answers `usedByTruncated`, true when agents beyond the listed ones were not checked. The list, the detail, the choice of an agent for a Run (`agent_not_usable`) and the Project default-agent preselection all go through this one judgement; a Run keeps its recorded commit, so a later change to a skill does not affect it.
    - **Browsing the Repository (Story #306).** `GET /api/agents/definitions-repository/files` and `GET /api/agents/definitions-repository/files/content` (session and Origin only; the route inventory refuses the worker and controller tokens) let the operator read every file of the definitions Repository, so the editor can show a tree and a file. They are two features in `agents` (`list-agent-files`, `read-agent-file`) over the same `DEFINITIONS_FILES` reads, with no table and no checkout, and they judge nothing: the validation marks come from `GET /api/agents`.
      - **Tree.** `GET /api/agents/definitions-repository/files` answers `{ commit, repository, truncated, entries }` for the whole Repository at the last fetched commit, with `commit` and `repository` as in the agent list. Each entry is `{ path, kind, size, agent, skill, openable }`: `kind` is `file`, `symlink` or `submodule` (links and submodules are listed and never read; any other kind is left out), `size` is 0 for a link and a submodule, and `agent` names the agent folder the entry belongs to (from `findAgentFolders`), `null` for the rest, `skill` names the skill folder it belongs to (from `findSkillFolders`), `null` for the rest, and `openable` says whether the content route reads it (a regular file within the 1 MiB limit whose path the route accepts, so a link, a submodule, an over-limit file or a path longer than 255 characters or with a control character is listed but not openable). At most 2,000 entries are listed, in path order, and `truncated` says when more exist (also when Git's own listing was cut).
      - **Content.** `GET /api/agents/definitions-repository/files/content?path=&commit=` answers `{ commit, path, kind: 'text', content }`, `{ commit, path, kind: 'binary', size }` or `{ commit, path, kind: 'too_large', size }`. The limit is `MAX_FILE_BYTES` (1 MiB): a larger file is not loaded. The limit counts the raw bytes Git writes; then the bytes are checked once with a fatal UTF-8 decoder: a NUL byte or invalid UTF-8 is `binary` with the real size (a 600 KB non-UTF-8 file is `binary`, never `too_large`), and valid UTF-8, also text that contains U+FFFD, is `text`. The answer is a union on `kind` (`text` has `content`; `binary` and `too_large` have `size`). `commit` is optional and defaults to the last fetched commit; when given it must be a full lower-case hex id (40 or 64 characters) the Clone holds. The path is checked in the entry point with the shared path rules of `@agentic-studio/contracts` (`environmentFilePathProblem`: no `..`, no leading `/`, no backslash, no empty or `.git` segment, at most 255 characters): a bad path or commit id is 400 (the web uses `openable` so it never offers such a path). No regular file at the path (a missing path, a folder, a link or a submodule), or no commit to read, is 404 `agent-file-not-found`; a commit the Clone does not hold is 404 `agent-commit-not-found`; a Clone that cannot be read here (not Linux, or Git failed) is 503 `agent-files-unreadable`.
      - **Tests.** The Git adapter's whole-tree listing, the file sizes and the commit-missing error have Linux tests that run in CI (they skip on other platforms); the HTTP cases run in the integration suite.
    - **The Draft (Story #307).** The one Draft of the definitions Repository holds the operator's unpublished changes to its files. It reaches no agent: the agents list, `AGENT_RESOLUTION` and the Run's hand-over read only the Clone, and a test pins that a Draft write changes none of them. It is the `AgentDraft` aggregate (`agent_drafts`, one row, `id = 1` by a CHECK constraint, with `base_commit`, `version` and `updated_at`; and `agent_draft_files`, a row per changed file with `path` (unique), `change` (`added`, `modified` or `deleted`), `content` (bytea, null exactly for a deleted file, by a CHECK constraint), `size`, `moved_from` and `updated_at`), restored and saved by `PrismaAgentDraftRepository`, which holds no rule.
      - **Rules (on the entity).** The base commit is set by the first change, to the commit the Repository holds then, and is dropped when the last change goes (also by reverting the last change). Every write raises `version` by one, a discard too. A write is saved only while the stored version is the one it loaded: `save` is a version-conditional update (which also takes the row lock; the migration seeds the one row), so `version` strictly increases and no write is lost. The write features repeat the whole load, change and save up to three times when they lose a race, and then answer 409 `agent-draft-conflict`; for one path the last write wins. At most 1 MiB per file (`MAX_FILE_BYTES` of the shared package, by constant), 10 MiB for the whole Draft and 200 changed files; each refusal is a 422 with its own problem type (`agent-draft-file-too-large`, `agent-draft-too-large` and `agent-draft-too-many-files`, with `size` and `limit`). The path follows the shared path rules (no `..`, no leading `/`, no backslash, no empty or `.git` segment, at most 255 characters; a bad path is 400) and stays inside the Repository. A path that is a symbolic link or a submodule at the base commit can be neither written nor deleted (422 `agent-draft-path-not-writable`); a path may not be a file where a folder is or the reverse (422 `agent-draft-path-conflict`). A move is a delete of the old path (or dropping it, when only the Draft holds it) plus an add of the new one, linked by `moved_from` for display; moving onto an existing path is refused (422 `agent-draft-path-taken`) unless the Draft deletes that path. A move carries a base file's stored bytes (`DEFINITIONS_FILES.readBlobs`), so a binary file moves unchanged; a base file over the limit cannot be moved (422 `agent-draft-move-unsupported`).
      - **Reading the base.** A write is judged against the whole tree of the Draft's base commit (the current commit while the Draft is empty), read through `DEFINITIONS_FILES`' `listTree` with `whole`. A tree that cannot be read whole (not Linux, no Clone, the commit is gone, or the listing was cut at its bound) refuses the write with 503 `agent-files-unreadable`; no commit at all is 409 `agent-draft-no-base`, and a base commit the Clone no longer holds is its own 409 `agent-draft-base-missing` (the Draft can then only be discarded). `AgentDraftBaseReader` does this read for the save, move and delete features.
      - **Routes** (session and Origin only; the route inventory refuses the worker and controller tokens), all under `/api/agents/definitions-repository/draft`. `GET` answers `{ baseCommit, currentCommit, version, files: [{ path, change, size, movedFrom, skill }], problems, skillProblems, judged, notJudgedReason, movedUpstream }` (`skill` is the skill folder a path is in, `null` for any other), with `currentCommit` the commit the Repository holds now (`null` when none). `GET …/files/content?path=` answers the same union as the Repository file route (`text`, `binary` or `too_large`, with `commit` the base commit): the Draft's own content for an added or modified file, the base commit's for a file the Draft does not change, 404 for a file the Draft deletes. `PUT …/files` takes `{ path, text }` or `{ path, contentBase64 }`, `POST …/files/move` takes `{ from, to }`, `DELETE …/files?path=` marks the path deleted in one call (a content change is dropped, and a file only the Draft holds simply disappears), `POST …/files/revert` with `{ path }` drops the Draft's change at the path (an added file goes, a modified file reverts, a deleted file comes back; for a moved file the new path goes and the original comes back; nothing is read from the Repository), and `DELETE` of the Draft discards everything. Every write answers the new Draft, with the raised `version`; the web compares it to say the Draft changed elsewhere. The save route accepts a JSON body of up to two file limits (a parser of its own in `app.ts`; it runs before the guards, so it serves only a request with the Studio origin and a session cookie, and any other request gets the 100 KiB default); a larger body is 413, and a text whose escaped form is longer is sent as base64.
      - **Problems.** One function, `judgeDraftState` (in `application/agent-draft-reader.ts`, used by `AgentDraftReader.read` and `.judge`), overlays the Draft on the base tree (an added or modified file replaces its base entry, a deleted file leaves it), groups the result with `findAgentFolders` and `findSkillFolders` (so a new folder is found too) and judges, on that state, every skill folder the Draft touches with `validateSkillFolder` (through the skills reader's folder judgement), every agent folder it touches with `validateAgentFolder`, and every agent that names a touched skill; the judged agents are then checked with `checkAgentSkills` against the skills as the Draft leaves them (an agent that names a skill missing from the Draft gets `skill_missing`, one naming an invalid skill `skill_invalid`). Entry and Markdown files are read from the Draft when the Draft holds them and from the base commit otherwise. An agent problem is `{ agent, code, path, key, message }` and a skill problem (`skillProblems`) `{ skill, code, path, key, message }` with a code of `SKILL_PROBLEM_CODES`; `path` is relative to the Repository root (the folder itself for a folder problem). A file with a forbidden key is saved and flagged, never refused: Publish refuses while there are problems (see Publishing below). A folder the Draft does not touch and that names no touched skill is not judged. The agents that name a touched skill are found from what the base agents name, read once per base commit and kept (the four latest bases), so a read of the same Draft starts no Git process for agents beyond the touched ones and those naming a touched skill; that first read and the skills read are bounded by the skills list's path and byte limits. Bytes are read as the Clone read does: NUL or invalid UTF-8 is no text. A Draft that could not be judged (the Clone cannot be read or its tree was cut, `notJudgedReason: clone_unreadable`; or the judgement is over those limits, which stays so until the Draft shrinks, `over_limits`) answers `judged: false` with empty `problems` and `skillProblems`, never as a clean Draft; Publish refuses it (503 `agent-files-unreadable`, or 503 `draft-not-judged` for the over-limits case) and pushes nothing.
      - **Moved upstream.** When the current commit differs from the base, `movedUpstream` lists, in path order, the Draft's paths (a deleted file's too) whose blob id or Git mode (the executable bit) differs between the two commits. `projects` publishes `blobIds(commit, paths)` on `DEFINITIONS_FILES` for it: the object name and executable bit of each regular file (`null` and `false` for any other path), from `ls-tree -l` through the Git adapter's `blobIdsAtCommit`, with no checkout and without reading any file, so two commits hold the same content at a path exactly when the names are equal. A path absent from both commits is not moved upstream; one that appeared or disappeared there is.
      - **Publishing (Story #308).** `POST /api/agents/definitions-repository/draft/publish` takes `{ message, baseCommit, version }` (strict; the request names no author) and answers `{ commit }` (session and Origin only; the route inventory and the token matrix refuse the worker and controller tokens). The message is 1 to 2,000 characters with no NUL, and the first line, the subject, is not blank (`PublishMessage`).
        - **Flow (`PublishAgentDraftHandler`).** In this order: no commit identity in the settings is 503 `publish-not-configured`; a bad message is 400 on `message`; an advisory lock (`studio.agents.publish`, `pg_try_advisory_xact_lock` in a transaction held for the whole publish, taken without waiting; `PrismaPublishLock` behind the `PublishLock` port) refuses a second publish with 409 `publish-running`. Under it: a `version` or `baseCommit` that is not the stored Draft's is 409 `agent-draft-conflict`; an empty Draft is 409 `nothing-to-publish`; the Draft's base is read as for a write (503, 409 `agent-draft-base-missing`), and a Repository that holds another commit than the base is 409 `repository-moved`; any problem of a skill the Draft touches, or of an agent it touches or that names a touched skill (the same judgement as `GET …/draft`), is 422 `publish-problems`, with the agent problems in a `problems` member and the skill problems in a `skillProblems` member. Then `DEFINITIONS_PUBLISH.publish({ baseCommit, changes, message, identity })` of `projects`: a changed file carries its bytes from the Draft (a deleted one `null`), a modified file keeps the executable bit the base has (read through `blobIds`) and an added one is a plain file. `repository_moved` (also when the push was rejected as not a fast-forward) is 409 `repository-moved`, `write_refused` is 409 `write-refused` with a message that says the Deploy key needs write access on the Git host, any other failure is 502 `publish-failed` (503 `agent-files-unreadable` for a Repository that is not ready or a platform that is not Linux). A refusal leaves the Draft and its bytes as they were. Before the base is read, a changed path outside `agents/` and `skills/` is 422 `publish-path-outside-definitions`; the judgement (`AgentDraftReader.judge`) says why when nothing was judged: a Clone that cannot be read is 503 `agent-files-unreadable`, a Draft over the limits of one judgement is 503 `draft-not-judged` (its own text: the Draft is too large to be checked, split it), and neither is ever "no problem". The bytes are read after the judgement and the Draft's version is checked again, so the bytes pushed are the bytes judged. After the push the Draft is discarded only if it is still at the published version; a Draft saved meanwhile is kept, with its old base, which is the published commit's parent and still in the Clone. A publish of it answers 409 `repository-moved` until the operator discards it, and it cannot be published again (there is no rebase). The adapter also checks that the remote it pushes to is the definitions Repository's own.
        - **In `projects`.** `PublishDefinitionsHandler` needs a `ready` Repository of the definitions Project whose Clone is at the base, builds the call with the Deploy key's credentials and the Integration branch, and after the push moves the Repository's commit on (`RepositoryConnection.recordPublished`, from the base only, keeping the fetch time). The Git adapter's `publishCommit` builds the commit with a temporary index (`read-tree`, `hash-object -w --no-filters --stdin`, `update-index -z --index-info`, `write-tree`, `commit-tree -p <base>`), pushes it, and then `update-ref refs/heads/<branch> <commit> <base>` in the Clone; see [Security](../engineering/security.md) section 4 for its limits. It runs under the project's lock, so it never overlaps a fetch.
        - **After success.** The Clone's Integration branch and the Repository's commit are the new commit, the Draft is discarded by one conditional discard at the published version, with no retry (a newer Draft is kept) and the agents list, whose judged list is kept per commit (#313), reads the new commit on its next request. A Run that started earlier keeps the commit it recorded, and so do its Follow-ups; a Run started now reads the new one. Only the objects of a push that failed stay in the Clone, unreferenced. A push the remote accepted but whose process the 2-minute limit killed answers 502 and keeps the Draft, although the commit is published: the next publish answers `repository-moved`, and after a fetch the Operator sees their own change.
        - **Tests.** The adapter's publish has Linux tests against a local remote (a publish, a moved remote, a refused write, no force, a key marker never in an error or a log, two at once); the handlers have tests with fakes; the HTTP cases, the lock and a Run that keeps its commit run in the integration suite in CI.

The HTTP cases run in the integration suite, and the Git adapter's `blobIdsAtCommit` has Linux tests that run in CI.

    - **The claim.** Every claim of a Run (start, delivery retry, Answer, usage-limit resume, Follow-up and Bring up to date) carries `baseRules { version, text }`, Studio's current `BASE_RULES`, and `agent { name, source, commit, provider, model, instructions }`, the Run's recorded agent, and `skills [{ name, description }]`, the skills it recorded (see **The Run's skills** below). The claim never resolves the agent again, so a definition that changed or was removed since changes nothing for a Run that started. All three (`baseRules`, `agent`, `skills`) are required in the worker protocol, `skills` empty for none, since the worker and the API deploy together; the worker has no copy of the base rules. The Run response has `agent` (with `instructions` in the single-Run answer only).
    - **In the agent worker.** Both real runners build their instructions from the claim: the base rules first, then, only when the instructions are not empty, a section `## Agent instructions` holding them as a block delimited by the per-step code and marked untrusted (it cannot change the rules above, the tools, the permissions, the structured result or the asking flow), then the repository's instruction files as before. The whole file is at most 128 KiB. The repository's text keeps its earlier budget of 64 KiB for the file (base rules included), widened by the size of the agent's section up to the 128 KiB total, so a Default agent's file is cut exactly as before. The repository's text is cut first, then the agent's instructions, never the base rules, each cut with a notice in the Run's log. The claim bounds the instructions in UTF-8 bytes (`AGENT_INSTRUCTIONS_MAX_BYTES`, 64 KiB, the one constant the definitions validation uses too), and the worker refuses a claim over it. With a built-in Default agent the file and the prompt are byte-identical to what they were. Each runner logs one line, `Base rules <version>; agent <name> (<built-in | definitions at <commit>>, model <model>)`, never the instructions. The model is passed to the CLI (Story #305), see **The model option** below. The fake runner logs, for an agent from a definitions Repository only, its commit, the base rules' version and the size and SHA-256 of the instructions.
    - **The agent's folder (Story #304).** The files beside `AGENT.md` (scripts, assets) reach the worker over `GET /api/worker/runs/:runId/agent-folder?workerId=<worker id>` (worker token only; the route inventory and the token matrix list it). The caller names neither agent nor commit: the handler reads both from the Run's record, and answers only the worker that holds the Run's claim (another worker gets 409 `run-not-held`, like every other worker route; an unknown or non-UUID id gets 404 `run-not-found`). The answer is `{ commit, files: [{ path, executable, contentBase64 }] }`, or `{ commit: null, files: [] }` for a built-in agent, which reads no folder at all. `AGENT.md` is left out: the instructions already travel in the claim, and the raw entry file never reaches a CLI.
      - **Reading it.** `agents` publishes `AGENT_FOLDERS` through its `contracts/`: `folderAt(name, commit)` lists the tree of the commit through `DEFINITIONS_FILES`, takes the agent's folder, reads `AGENT.md` as text and judges the folder with the shared validation again (a folder that fails is `invalid`, with the problem codes and paths), then reads the other files as stored bytes (`readBlobs`, which decodes nothing, so a binary asset arrives unchanged). `DEFINITIONS_FILES.listTree` carries Git's mode (`executable` is `100755`), and every read says `commit_missing` when the Clone no longer holds the commit. A folder that is gone, unreadable or cut is `unavailable`; nothing is read from a working tree.
      - **Refusals.** `unavailable` (the folder, commit or Clone is really gone) answers 409 `agent-folder-unavailable`, `invalid` answers 409 `agent-folder-invalid`, a listing that was cut (the folder may be partial) answers 409 `agent-folder-cut`, and a Git read that failed now (a timeout, a memory kill) answers 503 `agent-folder-read-failed`, which the worker reports as `preparation_failed` with a try-again reason, never as a lost folder; the worker fails the Run before any agent starts, with the failure code `agent_folder_unavailable` (the cut listing too, with its own reason) or `agent_folder_invalid` (two new fixed codes of the Run, listed in the OpenAPI document and in the `runs_failure_code_check` constraint).
      - **In the worker** (`src/agent-folder.ts`). Before every Run step (start, answer, Follow-up, usage-limit resume, Bring up to date) the worker fetches the folder again, validates it with the shared package (`validateAgentFiles`: path, kind, duplicate and size rules, plus a refusal of `AGENT.md` and of a commit other than the Run's recorded one, base64 that is not canonical), deletes `<run directory>/agent/` and writes it fresh: files `0644`, or `0755` when the Git mode was `100755`, directories `0755`, owner and group the worker's own, every path joined below `agent/`, files created exclusively. An earlier folder stays when a hand-over is refused; nothing is written then. The worker keeps no copy anywhere the agent user can write, starts no process, and runs, sources and changes the mode of nothing else. The folder sits in the Run's directory beside the Working copy, in no directory a CLI discovers by itself (not under `.claude`, `.codex`, `CODEX_HOME`, the plugin directory, or any skills or agents directory, and not on the path from the Working copy to the root), and no CLI option names it (no `--add-dir`, no writable root).

A built-in Default Run, and an agent with no files, get the file and the prompt they always had, byte for byte. What the agent can run: under Claude Code its command tool runs Python and Node scripts of the folder, while shell scripts stay blocked as repository scripts are (the managed allow list has no `sh` or `bash`); under Codex the sandbox runs them. No managed setting was changed for this ([Security](../engineering/security.md) §2).
      - **Never committed or pushed.** Before the push the worker asks Studio for the folder again and compares the blob ids (SHA-1 and SHA-256) of its non-empty files with every object the Run branch adds beyond its diff base (`git rev-list --objects`, so merge commits count, also a copy staged in a Bring up to date resolution). A match, under any name or path, also in a commit a later one reverted, stops the delivery before anything is pushed: the Run fails `delivery_failed` with the file named. The check fails closed: a folder that cannot be fetched, a Git failure, or a list longer than 8 MiB (which the process runner would cut silently) stops the delivery too. The fake runner has a scenario for it (`[fake:copy-agent-file]`) and, for an agent with files, logs each file's relative path, mode and SHA-256, never content.
    - **The Phases of a Run (Task #347, [ADR 0007](adr/0007-workflows.md)).** A Run's work is recorded per Phase, an ordered part of a Run with an agent: the `run_phases` table (`id`, `run_id`, `position`, unique per Run and counted from 0) holds the Run's agent record, its agent session (`session_ref`) and the Run-step allowance bookkeeping (`steps_before_part`, the Run steps the Run had taken when the Phase's current part began); each `run_steps` row names its Phase (`phase_id`). The `runs` table keeps its limits copied at start (`limit_max_steps` is the allowance of each part of a Phase, `limit_max_total_steps` bounds the whole Run) and gains `current_phase` (the position of the Phase the claim, the session and the allowance read) and `has_session` (whether the current Phase holds a session, written with it: the partial unique index of one active Run per project cannot read another table). A Run started with an agent has exactly one Phase, position 0; a Run started with a Workflow has one per Phase (see below). `executions` knows a Phase only as an ordered part of a Run with an agent and imports nothing from `workflows`. The domain `Run` still answers `agent`, `claim.sessionRef` and `progress.stepsBeforePart` for its current Phase, so every claim (start, delivery retry, Answer, usage-limit resume, Follow-up, Bring up to date) fills `agent`, `skills` and `sessionRef` from the current Phase and its content for a one-Phase Run is what it was; the result route stores the reported session on the current Phase. The single-Run answer gains `phases` (in order: `position`, the agent's `name`, `source`, `commit`, `provider`, `model` and `skills`, and `stepsUsed`, without instructions); the Runs list and every other field keep their meaning. The migration `run_phases` is a one-way door: it gives every earlier Run one Phase from its columns, sets the Phase of every Run step and then drops the moved columns from `runs`; `run-phases-migration.integration.test.ts` seeds a database at the previous migration with Runs in every state and checks nothing was lost. The agent worker keeps no agent or session state per Run of its own (it resumes the `sessionRef` the claim names), so it needed no change.
    - **A Run with a Workflow (Story #348, [ADR 0007](adr/0007-workflows.md)).** The start accepts `workflow` (a name) in place of `agent`; with neither an agent, a Workflow nor a provider, the Project's default (`projects.default_agent` or `default_workflow`, at most one, stored by name only) is started. `executions` defines the port `WORKFLOW_PLANS` in its `contracts/` and imports nothing from `workflows`; `workflows` implements it (`DefinitionsWorkflowPlans`, provided by `WorkflowPlansModule`, which `AppModule` gives to `ExecutionsModule`). `resolve(project, name)` reads the Workflow at the definitions Repository's last fetched commit and answers the plan (name, commit, items) or `unknown` or `not_usable` with a reason; `next(plan, position, outcome)` is pure over the recorded plan and answers the next Phase or the end. The start then reads each Phase's agent at that same commit (`AGENT_RESOLUTION.resolveAt`), judges the Providers against the agent workers' report, and refuses with `workflow_unknown` or `workflow_not_usable` (409, with the reason); a Workflow with a review Phase or a Checkpoint is refused as not usable ("review Phases and Checkpoints are not supported yet") until their tickets are in. **The record:** `runs` gains `workflow_name`, `workflow_commit` and `workflow_items` (the items as recorded: ids, kinds, agents, Phase instructions, Checkpoint texts), all null for an agent Run; one `run_phases` row per Phase is written at start with its `item_id`, `kind` (only `work`), `state` (`pending`, `running`, `done`, `failed`), the agent snapshot and, once a Run step of the Phase is done, its `summary`. A Run with an agent keeps exactly one Phase with no item. The domain `Run` keeps the current Phase's agent, provider, session and step allowance as before and gains `currentPhase` and the Phase list (every Phase, not only the ones up to the current). **The order:** `ReportRunStepHandler` asks `WORKFLOW_PLANS.next` in the transaction that stores a done result of a Workflow Run's Phase (never for an agent Run); for a next Phase the Run goes back to `queued` released by its worker, with `current_phase` moved and `has_session` recomputed from the new Phase in the same statement, and `runs.phase_pending` set, which makes a Run between two Phases hold its place (the unique index of one active Run per project, the places counted for the limit) and go only to the worker that has its Working copy, as an answered Run does; the operator's cancel request ends it `cancelled` instead; a resent report of the result is acknowledged. Each Phase gets `limit_max_steps` Run steps for its part (`steps_before_part` of the new Phase is the Run's step count when it is reached) and `limit_max_total_steps` bounds the whole Workflow: a step beyond it, or a Phase that would start beyond it, fails the Run with `step_limit`. **The claim:** for an agent Run it is exactly what it was. A Workflow Run's claim gains `phase` (`position`, `itemId`, `count`, `final` as the Workflow decides it from the recorded plan, the item's `instructions`, and for a Phase after the first `previous`: the item, the agent and the summary the Phase before reported); a Phase after the first is claimed as kind `next_phase`: no clone, a new agent session for that Phase's agent and Provider, or, in a Follow-up round, the Phase's own earlier session resumed with the Follow-up's text; skills and the agent folder are rebuilt from the Phase's agent before every step. A Follow-up to a finished Workflow Run starts again at Phase 0 (every Phase `pending`), resuming each Phase's session as it is reached; Bring up to date works in the last Phase's session; a usage-limit resume resumes the current Phase; every Provider the Phases use must be available for a Follow-up. **The operator API:** the single-Run answer gains `workflow { name, commit, items }` (null for an agent Run) and, per Phase in `phases`, `itemId`, `state` and `summary`; every Run answer gains `workflowName` (null for an agent Run); the Project answers `defaultWorkflow`, and `PUT /api/projects/:id/default-agent` takes `agent` or `workflow`. The migration `workflow_runs` is additive.
    - **The Run's skills (Story #331, [ADR 0006](adr/0006-skill-definitions.md)).** At a Run's start the names of the agent's skills (the front matter's list, in its order) are stored on the Run's Phase (`run_phases.agent_skills`, a list of names, empty for a built-in agent and for an agent with none) next to the commit the Run already records; the single-Run answer's `agent` gains `skills: string[]`. Every later step, Follow-ups included, uses those names at that commit and never reads the agent's entry file for them again, so a skill that changed or was removed since changes nothing for a Run that started. `agents` publishes `AGENT_SKILLS` through its `contracts/`: `describe(names, commit)` answers each skill's name and description and `files(names, commit)` its files (entry file included), both read at the given commit through `DEFINITIONS_FILES` and judged by `validateSkillFolder` (the entry file and every Markdown file are read as text, the rest as stored bytes, with the executable bit from the tree).
      - **The claim carries `skills: [{ name, description }]`** for a start, a resume and a delivery retry, read at the recorded commit and judged with the shared validation (the Run's order). A skill that is gone, invalid or refused fails the Run before any agent starts with the fixed code `skills_unusable` (`runs_failure_code_check`, the OpenAPI document and the web's messages carry it); a read that failed now (Git failed) fails it as `preparation_failed` with a try-again reason, as for the agent's files. For a delivery retry the delivery fails with `delivery_failed` (the code every delivery failure carries), and the reason says the skills could not be checked.
      - **`GET /api/worker/runs/:runId/skills?workerId=<worker id>`** (worker token only) is modelled exactly on the agent folder's route: the caller names neither a skill nor a commit, only the worker that holds the Run's claim is answered (409 `run-not-held` for another, 404 `run-not-found` for an unknown or non-UUID id), and the answer is `{ commit, skills: [{ name, files: [{ path, executable, contentBase64 }] }], omitted: [name] }`, or `{ commit: null, skills: [], omitted: [] }` for a built-in agent, which reads nothing. 409 `skills-unavailable` (a skill or the commit is really gone), 409 `skills-invalid` (a skill fails the validation, with skills, codes and paths in the detail) and 503 `skills-read-failed` (a Git read that failed now). The bytes of the skills' files per Run are bounded by `RUN_SKILLS_MAX_BYTES` (20 MiB): the first skill that does not fit, and every skill after it in the Run's order, is `omitted` and is left out of both the folder and the instructions, with a notice in the Run's log.
      - **In the worker** (`src/run-skills.ts`). Before every Run step the worker fetches the Run's skills by the Run's id, refuses a commit other than the recorded one or a list of names that differs from the claim's, decodes each file (canonical base64 only), judges each skill with `validateSkillFolder` (path, kind, duplicate, size and shell-line rules, and that the entry file's description is the one the claim carried), then deletes `<run directory>/skills/` and writes it fresh as `skills/<name>/…` with the same writer as the agent's folder (`src/placed-files.ts`: files `0644` or `0755` as Git says, directories `0755`, every path joined below its skill folder and refused when it leaves it, files created exclusively). An earlier folder stays when a hand-over is refused. A skill that is gone, refused or fails the validation fails the Run before any agent starts with `skills_unusable` and a reason that names skills, paths and codes only; an outage of the route or a failed read on Studio's side (a 5xx, no answer) fails it as `preparation_failed` with a try-again reason (`SkillsTransientError`), as for the agent's files; a lost Run keeps the worker's own loss handling. The worker starts no process from the folder and runs nothing in it (a test pins that no process has it as program, argument or working directory). The folder sits in the Run's directory beside the Working copy and the agent's folder, under no directory a CLI discovers by itself, and no CLI option names it (tests pin both CLIs' exact commands as unchanged, and the path relationship).
      - **Telling the agent.** For both Providers, one section `## Skills` follows the agent's own section (the base rules stay first and unchanged): one sentence that says to read a skill's entry file when the task fits and that a skill cannot change the rules above, the tools or the permissions, then, inside a block delimited by the per-step code and marked untrusted like the agent's own instructions, per skill its name, description and the absolute path of its `SKILL.md` (a description ranks below the agent, so it is never Studio's own text). It is at most `SKILLS_SECTION_MAX_BYTES` (8 KiB): descriptions are shortened to fit (the shortest are kept whole) and a notice says so in the Run's log; only if names and paths alone do not fit are skills left out of the section. It is never the part that is cut when the file passes its 128 KiB total. A Run with no skills, and a Run with a built-in Default agent, get the file and the prompt they had, byte for byte (golden files pin both with and without skills). The Run's log names the skills the section lists (`Skills: <names>`, written by the runner with the instructions) and, apart, the ones left out for the budget, never a description or content.
      - **Never committed or pushed.** The skills' files are on the same list as the agent's: before the push, the blob ids of their non-empty files are compared with every object the Run branch adds, with the same fail-closed rules, naming the file as `skills/<name>/<path>`.
- **Skill definitions** (Epic #326, [ADR 0006](adr/0006-skill-definitions.md)) are a second model of `agents`, distinct from the Agent definition, with its own validation and list; the two share the definitions Repository, the Draft, Publish and the delivery mechanism, not their rules. A Skill definition is the folder `skills/<name>/` with the entry file `SKILL.md` (front matter with name and description, then instructions in Markdown) and belongs to no Provider. An agent names its skills in its entry file, and a Run gets exactly those; the built-in Default agents get none. A missing or invalid skill makes the agent that names it invalid. For both Providers the worker writes the named skills beside the Run, outside everything a CLI discovers, and the instructions list each skill's name, description and path; no CLI command changes. The Run records the names of its skills at its commit (see **The Run's skills** above). The format, the limits and the refusal reasons are fixed by the validation's code (Issue #328), not here.
- `mcp` owns reusable server definitions/bindings.

### The `projects` module: behaviour of the Repository connection

Rules live on the `RepositoryConnection` entity and `RepositoryLifecycle` (which transitions are allowed lives there only); handlers order the steps. Every state-changing write of a background job is conditional on the Repository still being in the state the job started from, so a late write changes nothing.

- **Lifecycle.** A Repository starts in `awaiting_key` (SSH) or `connecting` (HTTPS); `awaiting_host_key` is reached through Verify, and a verified SSH Repository goes to `connecting`; `connecting` ends `ready` or `failed` (a clone result); `ready`, or `failed` with a Clone, goes to `fetching` and back to `ready` or `failed` (a fetch result); `failed` takes a new attempt (a Retry); any state goes to `disconnecting`, which forgets its key material and is then removed. The state is the last operation, not whether a Clone exists (`hasClone`).
- **Connect.** Order: input (field errors on every platform), platform, the store's transition (the real duplicate guard: unique indexes on the Project and on the remote's identity decide simultaneous connects), then the job. Over HTTPS the Repository is `connecting` and the clone is scheduled; over SSH it is `awaiting_key` with the Project's Deploy key and nothing is scheduled. A Retry of a failed Repository replaces it and keeps its Deploy key (and pinned host key while the host stays the same); otherwise a new key is generated and an unused key deleted. If the job cannot be scheduled after the transition, the attempt is failed again (keeping the failure a same-settings Retry replaced, else "could not be started") and the error is rethrown, so nothing stays `connecting`. A Deploy-key delete failure is logged (redacted), not thrown, and triggers an immediate sweep; the key is deleted once past the grace period. The Project must exist before a key is created.
- **Verify (SSH).** A trusted host (`STUDIO_SSH_KNOWN_HOSTS` or pinned) is cloned at once. Another host: Studio retrieves its host key in the request (time-limited); any `GitOperationError` of that scan fails the Repository, otherwise it waits in `awaiting_host_key`. With `acceptHostKeyFingerprint` the value must equal the pending key's fingerprint exactly. Starting the clone is a separate step: the Repository becomes `connecting` (pinning a confirmed key) in one conditional write, then the clone is scheduled; if that fails the Repository is `failed` again, as in Connect. With no trusted key a job fails with `host_key_mismatch` before Git runs (host-key rules: [Security](../engineering/security.md) §4).
- **Clone and Fetch jobs.** A clone job removes any leftover Clone, inspects the remote (so `branch_not_found` names the remote's default branch), clones, then marks `ready` or `failed`. A fetch fetches the Integration branch into the existing Clone, then marks `ready` with the new commit and time. A failed fetch keeps the Clone and its previous commit, except `size_limit`: the adapter removes the Clone, and only a Retry repairs it (`hasClone` is false). If a Fetch job cannot be scheduled the previous state is restored. `reconcile` at start-up fails every Repository still `connecting` or `fetching` as `interrupted`; a killed fetch leaves the Clone usable. An SSH job reads the Deploy key from the secret store for this job only. A non-Git error is unexpected: the queue stores `unknown`.
- **Disconnect.** The only destructive action. Order: project id and platform, the Repository becomes `disconnecting` from any state (the guard that keeps a running job from writing `ready` or `failed`; the Project's existence is checked only when no row is found), the job is cancelled and waited for (its id is free and no late write can touch a new Repository), then the cleanup steps in order: the Clone (only through the Git adapter's `removeClone(projectId)`, which derives the path from the project id and checks it is inside the data directory), the Deploy key (secret first, then reference, public key, host key), and the record last. A failing step is logged (redacted) and leaves the Repository `disconnecting`; a repeated Disconnect and start-up (the `resume-disconnects` feature) retry. Disconnect is never refused as busy. Zero rows deleted means a concurrent cleanup finished first.
- **Start-up recovery** (`RepositoryStartupRecovery`, when the repository queue is reconciled: after the Git adapter's sweep, before the worker starts): interrupted Repositories fail, `disconnecting` ones resume, then orphaned Deploy keys and Environment file contents are swept.
- **Sweeps.** A secret is orphaned when the process stops between storing it and saving its reference, or a delete fails. Candidates are secrets under the owner label older than the grace period (by the secret store's clock; both grace periods default to one hour); a secret any record references is never deleted. A kept Deploy key is saved by a Retry only while its Repository still references it (`keepsDeployKey`), so a key found unreferenced is never saved again. Deletes are logged by secret id only; a sweep never throws.
- **Environment file.** Content goes to the secret store; the Project keeps the reference (path, size, time) and the replaced content is deleted; removing the file deletes its content from the secret store, and Runs claimed earlier keep their own snapshot. When the Clone is ready, a path tracked at the Integration branch's current commit is refused (the worker re-checks against the Run's start commit). A Run reads the content again if it was replaced between row and secret (twice at most). Only a `ready` Repository is a Run start point.
- **Git adapter.** Operations on one project are serialized by an in-process lock (one API process). Any failure beyond the port's typed errors and `AbortError` becomes `GitOperationError('unknown')`; the raw error goes, redacted, to the server log. If the API process dies, the detached Git process group is orphaned until Git ends; start-up removes stale per-operation directories (with any SSH key) and partial Clones. Remote address checks and pinning: [Security](../engineering/security.md) §4. `scanHostKey` runs `ssh-keyscan` in the same isolated environment within the caller's timeout (verify: 30 s), preferring ed25519, then ECDSA, then RSA.
- **Test seam.** `ProjectsModuleOptions.platform` is settable only from code (`main.ts` passes none); HTTP suites use it to prove the 501 path on a Linux runner. It can only make the Linux-only guard refuse more. A provider override would need a second way to build the app for those suites alone, so the option stays.
- **Persistence.** `head_sha` is set exactly while a usable Clone exists. Only a `disconnecting` Repository is deleted. The `connect` step is one atomic database step; `change` locks the row (`FOR UPDATE`), its callback does no I/O, and a domain refusal rolls back, so a late job write waits for a Disconnect and then finds the state it left. A Project never changes after creation, so no operation needs a transaction across the Project and Repository stores.
- **Value objects.** `RepositoryUrl` identity is the lower-cased host plus path without scheme, user, default port, trailing `/` or `.git`, so https, ssh and scp-like forms of one repository are one remote; a non-default port stays and the path keeps its case. `ProjectName` is NFC-normalized and its length counted in code points, matching PostgreSQL `char_length`.

## 8. Test requirements

- Unit: domain behavior (entity and value-object rules, transitions) needs no database, container or fake of a port; handler behavior and error cases use controlled fakes of the ports.
- Integration: repositories, API validation/auth, PostgreSQL transaction behavior, outbox/inbox, Redis/BullMQ where used (Testcontainers when appropriate).
- HTTP integration tests that build the whole app (`AppModule`, real database client) live in `apps/api/src/__tests__/`, outside `src/modules/`: building the app reaches the database client, which `architecture:api` forbids for anything under `application/`, tests included. Unit tests of a feature stay beside its handler in `application/features/<feature>/` with fakes of the ports.
- Contract: REST DTO/schema compatibility and event versions.
- Architecture: full dependency graph and structural rules in **`architecture:api`**.
- Security/reliability: authorization failures, duplicate events, retry, cancellation, filesystem/working-copy isolation, privileged-action rejection.

Preferred runner: **Vitest**; supporting tools: `@nestjs/testing`, Supertest, Testcontainers. No global coverage percentage target at bootstrap; prioritize meaningful business cases. Architecture tests block merge once CI is implemented.

See [Quality](../engineering/quality.md) and [Security](../engineering/security.md).

## 9. Avoid overengineering

No mandatory generic `BaseRepository`, mediator/message bus for every feature, separate event-sourced models, mandatory extra layers, one module per table, domain events by default, or six microservices. Introduce abstractions where there is a tested reason.

## 10. Code conventions

**Same role, same form** (rule 9). State with rules or with dependencies gets a class; everything else is a function or plain data. A file holds one concept (rule 13): a file under `domain/value-objects/` holds one class or one record, plus the lists of allowed values, union types, type guards and typed-id brands that describe it; a class may keep its own input, stored and options types (named after the class) and its own validation error beside it.

| Role | Form |
| --- | --- |
| Aggregate root; child entity; value object that owns rules; policy | Class (a root at minimum can be restored from its data) |
| Handler; endpoint, job processor, scheduler, start-up routine, consumer | Class with injected dependencies |
| Adapter, repository implementation | Class implementing an interface |
| Port, repository contract | Interface |
| Error | Class extending `Error` |
| Record with a rule (limit, format, cut, redaction) | Value object class: private constructor, `static readonly` limits, factories (`of`, `create`, `from…`, or a descriptive name) that validate and `restore` that does not; an aggregate root creates its children through an instance method |
| Policy or rule (hand-out, sweep, retention, lease) | Class built by a factory from its configuration; its checks are instance methods, not statics |
| List of allowed values | Union type derived from a list of literals |
| Record with no behaviour; data crossing a boundary | Plain type |
| Pure helper | Function (not in `domain/`: rule 13 allows only type guards there, plus an unexported technical helper of at most ten lines with no domain type; the rule goes on the object it is about) |

Naming follows §4 (repository and port contracts: `<Aggregate>Repository`, `<Name>Reader`) and §6 (events: `<EventName>V<n>`).

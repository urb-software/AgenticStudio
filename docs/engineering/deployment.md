# Deployment: server setup and isolation boundary checks

How Studio is put on its server so that the isolation model of [ADR 0002](../architecture/adr/0002-agent-run-isolation.md) holds: Studio under the system Docker daemon, which only root controls; agents and the agent worker as an ordinary user with its own rootless Docker. Introduced by #107.

**Status (2026-11-16).** There is no target server yet (operator decision on #107). The setup script, the boundary checks and Studio's production images (#132) are built and tested in CI (job `deploy:server`, see [What CI covers](#8-what-ci-covers)). Running them on the server, repeating the rootless Docker trial there, the first real Runs and the branch protection check are tracked in #130.

All host names, accounts, domains and addresses below are placeholders.

## 1. The two sides of the boundary

| | Studio's side | The agent side |
| --- | --- | --- |
| Runs | PostgreSQL, Redis, the reverse proxy, API, web as a Compose stack | The agent worker and the agents it starts (provider CLIs, their Git and Docker commands) |
| As | Containers of the **system** Docker daemon (root only); the API, web, reverse proxy and migrations run as uid 10001 (`STUDIO_CONTAINER_UID`) with a read-only root filesystem | The **agent user** (default `agent`, uid/gid 2001, `AGENT_UID`): not in the `docker` group, no `sudo`, no password, no cron, at or SSH login; everything it runs is under its user manager |
| Docker | `/var/run/docker.sock`, root only | Its own **rootless** daemon at `/run/user/<uid>/docker.sock`, a systemd user service |
| Configuration | `/etc/agentic-studio/.env` (root, 0600) in `/etc/agentic-studio/` (root, 0700) | `~agent/.config/agentic-studio-worker/.env` (agent, 0600) |
| Data | `/var/lib/agentic-studio/data` (uid 10001, 0700, inside root-only `/var/lib/agentic-studio`; the API's `STUDIO_DATA_DIR`), `/var/lib/agentic-studio/proxy` (uid 10001, 0700: the proxy's certificates and ACME account), Docker volumes | `~agent/.local/share/agentic-studio-worker` (Working copies, per-project caches) |
| Code | The production images ([Production images](#production-images)); Compose files and the `Caddyfile` in `/opt/agentic-studio/` (root, 0700) | `/opt/agentic-studio-worker/` (root-owned, readable, not writable by the agent user) |
| Network | Container network `172.31.250.0/24` with fixed addresses (PostgreSQL `.10`, Redis `.11`, API `.12`, web `.13`, reverse proxy `.20`; other containers from `.128/25`); only the reverse proxy publishes host ports (80 and 443, IPv4) | Calls the API through the reverse proxy's worker port, `http://172.31.250.20:8080`, with the worker token; a firewall rule rejects its traffic to Studio's container network, except that port. Like any host process it reaches the proxy's published ports, never the API, web, PostgreSQL or Redis directly |

The environment controller runs on the host as the **Preview user** ([ADR 0004](../architecture/adr/0004-preview-isolation.md)), not in this stack: [Previews: the Preview user and the controller](#previews-the-preview-user-and-the-controller).

The worker always calls Studio; Studio never reaches into the host. The operating-system boundary is the security boundary; the CLIs' hooks and permission rules are guardrails on top of it ([Security](security.md) §2).

**No production credentials on the server**, on either side: no production database, cloud or deployment credentials, and no operator Git credentials. Studio holds only its own secrets and the projects' Deploy keys; the agent side holds the provider CLI logins, the Agent account's token (limited to the managed repositories) and the worker token. Assume an agent can read everything the agent user can.

## 2. Prerequisites

- **Ubuntu 24.04 LTS on native Linux** (a VM or a dedicated machine), with systemd and cgroup v2 (the Ubuntu 24.04 default). The script refuses other distributions. WSL is not an isolation boundary with default settings ([trial](../architecture/adr/0002-trial-rootless-docker.md#security-finding-wsl)).
- Outbound HTTPS to `download.docker.com`, `nodejs.org`, the npm registry and Docker Hub.
- A clone of this repository owned by root and writable by root only, in a directory whose parents up to `/` are too (the script refuses anything else, because root builds the worker from it), for example `git clone https://github.com/<owner>/AgenticStudio.git /usr/local/src/agentic-studio`. The script deploys the agent worker from this checkout's `HEAD`.
- Operator prerequisites on the Git host: the **Agent account**, with access limited to the managed repositories, and **branch protection** on their integration branches so the Agent account cannot merge or push to them.

## 3. The setup script

```bash
sudo /usr/local/src/agentic-studio/deploy/setup-server.sh           # every step
sudo /usr/local/src/agentic-studio/deploy/setup-server.sh --list    # what each step changes
sudo /usr/local/src/agentic-studio/deploy/setup-server.sh --only worker,service
```

It is safe to run again: each step checks the current state and reports `unchanged` or each change, and the last lines give the number of changes and the remaining manual steps. Run it again after `git pull` to update the agent worker (`--only worker,guardrails,service` is enough).

**Refusals.** Before any change, and again at the end, it refuses to continue if the agent user or the Preview user is in the `docker` group, has passwordless `sudo` rules, or can run `sudo -n true`; if the agent user or the Preview user is in the proxy group, or the two share any group; if the Preview uid or gid is held by another account; if `PREVIEW_UID` is below 2000 or equals the agent's uid, or the proxy gid is held by a group of another name; it also refuses a distribution other than Ubuntu 24.04 and the systemd steps without systemd and cgroup v2.

| Step | What it does |
| --- | --- |
| `preflight` | Root, Ubuntu 24.04, supported architecture, no per-user directories in `/etc/environment`, the agent user checks above (also no `lxd`, `incus-admin`, `libvirt` or `disk` group), and a checkout only root can change. Changes nothing. |
| `packages` | Base packages (`uidmap`, `slirp4netns`, `dbus-user-session`, `fuse-overlayfs`, `iptables`, `quota`, `git`, `curl`, ...); Docker's official apt repository with its signing key's fingerprint checked; `docker-ce`, the Compose and Buildx plugins and `docker-ce-rootless-extras`; enables the system Docker daemon. |
| `node` | The official Node.js 24 binary tarball (the version CI uses) into `/usr/local`, checked against its SHA-256 pinned in the script per version and architecture (a different `NODE_VERSION` needs `NODE_SHA256_X64`/`NODE_SHA256_ARM64` with it); pnpm through corepack. |
| `user` | Creates the agent user with the fixed uid/gid `AGENT_UID` (default 2001, outside the range ordinary users and images commonly use; an existing agent user below 2000 is refused), home directory, no password, no `sudo`, a subordinate uid/gid range; makes its home directory inaccessible to other users. |
| `preview-user` | The Preview user (default `preview`, uid/gid `PREVIEW_UID` 2002; refused below 2000 and equal to the agent's uid) with home 0750, no password, no `sudo`, a subordinate uid/gid range, and the group `previewproxy` (gid `PREVIEW_PROXY_GID`, default 2003; refused when another group holds that gid). It is in no root-equivalent group (`docker`, `lxd`, `incus-admin`, `libvirt`, `disk`, `sudo`), **not** in the proxy group (the setgid socket directory makes membership unnecessary) and shares no group with the agent user. |
| `logins` | Nothing of the agent user or the Preview user may run outside its user manager, which is bound to its firewall: both go into `/etc/cron.deny` and `/etc/at.deny`, get `DenyUsers` in `/etc/ssh/sshd_config.d/60-agentic-studio.conf` (only when sshd is installed; checked with `sshd -t`, then reloaded), and logind kills their session processes at logout (`KillUserProcesses=yes`, `KillOnlyUsers=agent preview` in `/etc/systemd/logind.conf.d/60-agentic-studio.conf`). The operator still works as them through `sudo -iu agent` and `sudo -iu preview`. |
| `layout` | Studio's root-only directories and files (table above; `data/` and `proxy/` owned by uid 10001), `.env` from [`deploy/studio.env.example`](../../deploy/studio.env.example) only when it does not exist, the Compose files, the [`Caddyfile`](../../deploy/Caddyfile) (0644, readable by the proxy container, inside the root-only directory), `/usr/local/sbin/agentic-studio-compose`, `/usr/local/bin/agentic-studio-check-boundary` and `/usr/local/bin/agentic-studio-check-preview`. The Preview side is written **as the Preview user**: `~/.config/agentic-studio-controller/.env` (0600, from [`apps/environment-controller/.env.example`](../../apps/environment-controller/.env.example), the API through the proxy's worker port, the data directory and the proxy group filled in, an **empty token**) and `~/.local/share/agentic-studio-controller` (0700). The worker's `.env` gets `STUDIO_API_URL=http://172.31.250.20:8080` (the proxy's worker port). On the agent side, **as the agent user** (root never writes into its home): the worker's directories and its `.env` from [`apps/agent-worker/.env.example`](../../apps/agent-worker/.env.example). |
| `worker` | The agent worker's code from `HEAD` into `/opt/agentic-studio-worker`, installed with dependency install scripts disabled and built there; root-owned, world-readable. Skipped when that commit is already built. |
| `controller` | The environment controller's code from `HEAD` into `/opt/agentic-studio-controller` (root-owned, world-readable, not writable by the Preview user), installed with dependency install scripts disabled and built there. Skipped when that commit is already built. |
| `guardrails` | Studio's managed guardrails for the provider CLIs (Issue #134), from the built worker's guardrails folder ([`managed-files.txt`](../../apps/agent-worker/guardrails/managed-files.txt) says which file goes where): `/etc/claude-code/managed-settings.json`, `/etc/codex/managed_config.toml`, `/etc/codex/requirements.toml` and the guard script `/usr/local/lib/agentic-studio/guardrails/claude-guard.mjs` (run by `/usr/local/bin/node` from the `node` step); `root:root`, files 0644, directories 0755; a symbolic link in a file's place is replaced. It refuses while `/etc/claude-code/managed-settings.d`, `/etc/claude-code/managed-mcp.json` or `/etc/codex/config.toml` exists (the CLIs would merge them into the policy; review them and remove them). The agent worker compares them with its own copies before every Run step and refuses a provider whose files are missing or changed ([Security](security.md) §2). Run it after every `worker` step. |
| `firewall` | `agentic-studio-agent-firewall.service`: an `iptables` rule rejecting the agent user's traffic to Studio's container network, except TCP 8080 on the reverse proxy's address (the worker port). Without it, the agent user could reach the API, PostgreSQL and Redis at their container addresses even though no host port is published. **Fail closed:** the unit fails unless the rules are verified in place; a drop-in makes the agent user's manager (`user@<uid>.service`: its services, rootless Docker and the worker) `Requires=`, `BindsTo=` and `After=` it, so the agent side never runs without it; `agentic-studio-agent-firewall-verify.timer` checks the rules every minute and, if they were flushed, stops the firewall unit and with it the agent side. Starting the agent side again (`systemctl start user@<uid>.service`, or a re-run of the script) re-applies them. |
| `preview-firewall` | The same fail-closed firewall for the Preview user (`agentic-studio-preview-firewall.service`, chain `AGENTIC-STUDIO-PREVIEW`, verify timer, `user@<uid>` bound to it): on Studio's network only the reverse proxy's port 8080 is open, which serves the controller's API; everything else there is rejected. |
| `limits` | A drop-in for the agent user's slice (`user-<uid>.slice`): `MemoryMax` (default 75%), `TasksMax` (4096), `CPUWeight` (50, below the default 100); cgroup delegation to user managers so rootless Docker's container limits work; a disk quota if configured and available ([Disk quota](#disk-quota)). The same for the Preview user's slice: `MemoryMax` (`PREVIEW_MEMORY_MAX`, default 50%), `TasksMax` (`PREVIEW_TASKS_MAX`, 4096), `CPUWeight` (`PREVIEW_CPU_WEIGHT`, 50). Builds run below the Preview user's `app.slice` (with the daemon), outside the Previews' slices, so this slice and the per-build bound on `app.slice` (set by the controller) are their bounds. |
| `rootless` | An AppArmor profile for `rootlesskit` (Ubuntu 24.04 restricts unprivileged user namespaces), linger for the agent user (its services run without a login session), and its rootless Docker daemon as a systemd user service. The Compose plugin is the system one, available to every user. |
| `preview-rootless` | Linger and the rootless Docker daemon of the Preview user; `~/.config/docker/daemon.json` with `{"dns":["<resolver>"]}` (`PREVIEW_DNS`, else the first non-loopback IPv4 nameserver of `/run/systemd/resolve/resolv.conf`, else `/etc/resolv.conf`; the setup fails if there is none); the root-owned egress script `/usr/local/lib/agentic-studio/preview-egress-rules` ([`deploy/preview-egress-rules.sh`](../../deploy/preview-egress-rules.sh), 0755, with the resolver filled in); and the drop-in `~/.config/systemd/user/docker.service.d/60-agentic-studio-egress.conf` with `ExecStartPost=<script> apply` (the rules are applied in the daemon's network namespace after every start, and a failure fails the start) and `OOMPolicy=continue` (the controller bounds the Preview user's `app.slice` per build, not this unit; if the kernel picks the daemon instead of a build, the daemon must not stay stopped), and a second `ExecStartPost` starts the controller after every start of the daemon (the controller requires the daemon and is stopped with it; an automatic restart of the daemon would not bring it back). Every run re-applies the rules and reads them back. |
| `preview-proxy-dir` | `/etc/tmpfiles.d/agentic-studio-preview-proxy.conf` with `d /run/preview-proxy 2750 preview previewproxy -`: the directory of the Preview sockets exists at every boot (before any user manager) and now, **setgid**, owned by `preview:previewproxy`. It holds nothing but the controller's bridge sockets (no controller socket, no admin socket). |
| `service` | `/etc/systemd/user/agentic-studio-worker.service` ([template](../../deploy/systemd/agentic-studio-worker.service)), enabled for the agent user, started (restarted) only once its worker token is filled in; an `ExecCondition` skips the unit (inactive, not failed) at every boot while `STUDIO_WORKER_TOKEN` in its `.env` is shorter than 32 characters. It reads the worker's own `.env` and talks to the rootless Docker daemon only. |
| `controller-service` | `/etc/systemd/user/agentic-studio-controller.service` ([template](../../deploy/systemd/agentic-studio-controller.service)), enabled for the Preview user only (`ConditionUser`), started (restarted) only once its `STUDIO_CONTROLLER_TOKEN` is filled in; an `ExecCondition` skips it (inactive, not failed) at every boot while the token in its `.env` is shorter than 32 characters. `ExecStart` runs the controller through `env`, which sets `STUDIO_CONTROLLER_ENVIRONMENT=production`, `HOME`, `XDG_RUNTIME_DIR` and the rootless `DOCKER_HOST` after the `.env` is read, so the file cannot override them. |

**Configuration.** The variables at the top of the script can be overridden through the environment: `AGENT_USER`, `PREVIEW_USER`, `PREVIEW_UID`, `PREVIEW_PROXY_GID`, `CONTROLLER_CODE_DIR`, `PREVIEW_MEMORY_MAX`, `PREVIEW_TASKS_MAX`, `PREVIEW_CPU_WEIGHT`, `PREVIEW_DNS`, the four directories, `NODE_VERSION`, `STUDIO_NETWORK_SUBNET`, `STUDIO_PROXY_ADDRESS` and `STUDIO_PROXY_WORKER_PORT`, `AGENT_MEMORY_MAX`, `AGENT_TASKS_MAX`, `AGENT_CPU_WEIGHT`, `AGENT_DISK_QUOTA_GB`. The container network, its dynamic range and the fixed addresses must stay equal in `studio.env.example`, the Compose files, `setup-server.sh` and `check-boundary.sh`, and the worker port in `setup-server.sh` and the `Caddyfile`; a test checks the defaults.

**Rollback of the Preview side.** As the Preview user `systemctl --user disable --now agentic-studio-controller docker` and `dockerd-rootless-setuptool.sh uninstall`; as root `systemctl disable --now agentic-studio-preview-firewall-verify.timer agentic-studio-preview-firewall`, remove `/usr/local/sbin/agentic-studio-preview-firewall`, its three units, `/etc/systemd/system/user@<puid>.service.d/60-agentic-studio-firewall.conf`, `/etc/systemd/system/user-<puid>.slice.d/50-agentic-studio.conf`, `/etc/tmpfiles.d/agentic-studio-preview-proxy.conf`, `/etc/systemd/user/agentic-studio-controller.service`, `/opt/agentic-studio-controller`, `/usr/local/lib/agentic-studio/preview-egress-rules` and `/usr/local/bin/agentic-studio-check-preview`; `loginctl disable-linger preview`; take the user out of `/etc/cron.deny` and `/etc/at.deny`; `userdel -r preview` removes the Preview side with its data and Previews; `groupdel previewproxy`.

**Rollback.** The script touches application data nowhere. To undo it: `systemctl disable --now agentic-studio-agent-firewall-verify.timer agentic-studio-agent-firewall` (this stops the agent side too) and remove `/usr/local/sbin/agentic-studio-agent-firewall`, its three units and `/etc/systemd/system/user@<uid>.service.d/60-agentic-studio-firewall.conf`; as the agent user, `systemctl --user disable --now agentic-studio-worker docker` and `dockerd-rootless-setuptool.sh uninstall`; `loginctl disable-linger agent`; remove `/etc/systemd/user/agentic-studio-worker.service`, `/etc/systemd/system/user-<uid>.slice.d/50-agentic-studio.conf`, `/etc/systemd/system/user@.service.d/50-agentic-studio-delegate.conf` and `/etc/apparmor.d/usr.bin.rootlesskit` (then `systemctl daemon-reload`); remove the agent user from `/etc/cron.deny` and `/etc/at.deny` and remove `/etc/ssh/sshd_config.d/60-agentic-studio.conf` and `/etc/systemd/logind.conf.d/60-agentic-studio.conf`; remove `/opt/agentic-studio-worker`, `/usr/local/sbin/agentic-studio-compose`, `/usr/local/bin/agentic-studio-check-boundary`, the managed guardrails (`/etc/claude-code/managed-settings.json`, `/etc/codex/managed_config.toml`, `/etc/codex/requirements.toml`, `/usr/local/lib/agentic-studio/`); `userdel -r agent` removes the agent side with its data. Studio's directories, the packages, Docker's apt source and Node.js in `/usr/local` are removed by hand when no longer wanted; `/etc/agentic-studio` and `/var/lib/agentic-studio` hold Studio's configuration and data.

## 4. Manual steps

The script never writes a secret value. It prints the steps below; each value goes in exactly one root-only or agent-only file.

1. **Studio's configuration**, as root, in `/etc/agentic-studio/.env`:
   - `POSTGRES_PASSWORD` (`openssl rand -hex 32`) and `DATABASE_URL` with the same password and the host `postgres`.
   - `REDIS_PASSWORD` (`openssl rand -hex 32`; Redis requires it) and `REDIS_URL` as `redis://:<REDIS_PASSWORD>@redis:6379`. Neither ever goes to the agent side.
   - `STUDIO_OPERATOR_PASSWORD_HASH`: the operator password's Argon2id hash, generated on the operator's workstation with `pnpm --filter @agentic-studio/api run auth:hash-password` (README, "Operator login"), in single quotes.
   - `STUDIO_SECRETS_KEY`: the secret store's master key (`openssl rand -base64 32`). Store a copy off the server at once, separately from the database backups (README, "Secrets key").
   - `STUDIO_WORKER_TOKEN`: the worker token (`openssl rand -base64 32`).
   - `STUDIO_API_IMAGE` and `STUDIO_WEB_IMAGE`: the production images ([Production images](#production-images)).
   - `STUDIO_OPERATOR_GITHUB_LOGIN` (optional, Issue #146): your own GitHub login. The Review comments you wrote on a pull request are then listed first and selected when you load them on the Run page; everyone else's stay unselected. Matched exactly, ignoring case; unset, nothing is preselected and the page says how to set it.
   - `STUDIO_MERGE_TOKEN` (optional): the Merge credential, a fine-grained token of your own GitHub account, limited to the managed Repositories, with write access to **Pull requests** and **Contents**, and read access to **Checks** and **Commit statuses** (Studio reads them before it merges). Studio uses it only when you merge or close a Run's pull request, never from a worker route. One line, no whitespace, 20 to 255 characters; any other value stops the API at start-up with an error that names the setting and never its value. Empty or unset turns merging and closing off, and the Run page says so. Never put it in the agent worker's `.env`: the worker refuses to start with it, and `secrets-unreachable` fails.
   - `STUDIO_PREVIEW_DOMAIN` (optional, Issue #276): the DNS name Previews are served under, such as `preview.example.test`. A Project's Preview gets the hostname `preview-<first 12 hex digits of the project id>.<domain>`, which stays the same when the Project is renamed. The domain must not be Studio's own hostname (`STUDIO_DOMAIN`) or a name under it, so a Preview never shares an origin with Studio ([Security](security.md) section 5); any other value, or that one, stops the API at start-up with an error that names the setting and never its value. Empty or unset shows no hostname, and the Preview page says why. Setting it also turns on the reverse proxy's Preview site (Issue #277) and then needs `STUDIO_PREVIEW_PASSWORD_HASH`, the certificate and the DNS record ([Previews: domain, certificate, password](#previews-domain-certificate-password)); the bridges and the socket directory come with the Preview controller (#285, #286).
   - `STUDIO_PREVIEW_PASSWORD_HASH` (Issue #277; needed with `STUDIO_PREVIEW_DOMAIN`): the Preview password's bcrypt hash, in single quotes. Compose refuses to start and names it when the domain is set without it. Like every secret here it never goes to the agent side (`secrets-unreachable` checks it).
   - `STUDIO_DOMAIN`: the web app's public domain (the API's `STUDIO_ORIGIN` becomes `https://<STUDIO_DOMAIN>`), and `STUDIO_TLS`: the ACME account email ([Reverse proxy and TLS](#reverse-proxy-and-tls)).
2. **The agent worker's configuration**, as the agent user, in `~/.config/agentic-studio-worker/.env`: the same `STUDIO_WORKER_TOKEN`; `STUDIO_AGENT_GIT_NAME` and `STUDIO_AGENT_GIT_EMAIL` (the Agent account's commit identity); `STUDIO_AGENT_GITHUB_TOKEN`, the Agent account's token limited to the managed repositories. A fine-grained token needs **Pull requests: read and write**, **Contents: read and write** and **Metadata: read**: the worker pushes run branches and opens and updates draft pull requests, and it also reads each pull request, its branch position and the account's own login (`GET /user`) to show the pull request's state on the Run page (Issue #142; reads only, the daily refresh included). For the pull request's checks (Issue #145; reads only) it also needs **Checks: read** (check runs), **Commit statuses: read** (combined statuses) and **Actions: read** (the log of a GitHub Actions job, read only when the operator chooses "Send failing checks to the agent"). Without them the page says GitHub did not tell the checks, or that a log was unavailable, and everything else keeps working. For the pull request's Review comments (Issue #146; reads only, when the operator chooses "Load review comments") the same **Pull requests: read** covers the comments and the review threads (one GraphQL read). Leave `CLAUDE_CODE_ENABLED` and `CODEX_CLI_ENABLED` at `false` ([Enabling a provider](#6-enabling-a-provider)).
3. **The provider CLIs**, as the agent user: install each CLI with its provider's official installer, then log it in interactively with the operator's subscription login, as the CLI runner stories describe (Claude Code: #105, Codex: #106). Never copy a login from another machine or user. Configure the agent user's own Git credentials for fetching the managed repositories.
4. **Project test dependencies**, as root, only when the operator's projects need them: for example Playwright's browser libraries, `npx --yes playwright@<version> install-deps chromium` with the version the project pins.
5. **Start Studio**, as root: `agentic-studio-compose up -d --wait`. The `migrate` service applies the database migrations first and the API starts only after it succeeded ([Migrations](#migrations)); while either image variable is empty, only PostgreSQL and Redis start.
6. **Start the worker**, as the agent user (for example `sudo -iu agent`, with `XDG_RUNTIME_DIR=/run/user/$(id -u)`): `systemctl --user restart agentic-studio-worker`, then `journalctl --user -u agentic-studio-worker`.
7. **Run the boundary checks** as the agent user: `agentic-studio-check-boundary` must end with `RESULT: PASS` ([Boundary checks](#5-boundary-checks)).
8. **Previews** (optional; needs `STUDIO_PREVIEW_DOMAIN`, see below): set the controller token **on both sides**, start the controller, and run `agentic-studio-check-preview` as the Preview user ([Previews: the Preview user and the controller](#previews-the-preview-user-and-the-controller)).

### Production images

Studio's API and web run from two images built from this repository (#132), from the repository root:

```bash
docker build -f apps/api/Dockerfile -t registry.example.com/agentic-studio-api:<tag> .
docker build -f apps/web/Dockerfile -t registry.example.com/agentic-studio-web:<tag> .
```

Build them on the server (as root, from the root-owned checkout) or push them to a registry the server pulls from, then set `STUDIO_API_IMAGE` and `STUDIO_WEB_IMAGE` in `/etc/agentic-studio/.env` and run `agentic-studio-compose up -d --wait` again; the registry and tags are placeholders. Both images: a multi-stage build on a Node.js base image pinned by digest (the Node.js version CI uses), `pnpm install --frozen-lockfile` with dependency install scripts limited as in CI (`allowBuilds` in `pnpm-workspace.yaml`), production dependencies only in the final stage, no secret and no `.env` file in any layer ([`.dockerignore`](../../.dockerignore)), `USER 10001:10001`. The API image adds `git` and an SSH client (Repository features) and holds the Prisma migrations; the web image is Next.js's standalone server, built without the `/api` rewrite (the reverse proxy routes `/api`). Compose runs every Studio container with a read-only root filesystem, all capabilities dropped (the proxy keeps only binding ports) and `no-new-privileges`.

### Migrations

The one-off `migrate` service ([`compose.server.app.yaml`](../../deploy/compose.server.app.yaml)) runs `prisma migrate deploy` from the API image, the command `pnpm db:migrate:deploy` runs in development, with only `DATABASE_URL` in its environment; the API `depends_on` it with `service_completed_successfully`, so every `agentic-studio-compose up` applies the committed migrations of the image's version before that API starts. A failed migration leaves the API stopped: read `agentic-studio-compose logs migrate`. Migrations are forward only; take a database backup ([Backups](#7-backups-and-restore-drill)) before switching to an image with new migrations.

### Reverse proxy and TLS

The `proxy` service (Caddy, image pinned by digest, configured by [`deploy/Caddyfile`](../../deploy/Caddyfile)) is the **only service with host ports**: 80 and 443, IPv4 only. It serves `https://<STUDIO_DOMAIN>` with a certificate from Let's Encrypt (`STUDIO_TLS` = the ACME account email; the domain must point at the server and ports 80 and 443 be reachable; certificates are kept in `/var/lib/agentic-studio/proxy`) and sends `/api` straight to the API and everything else to the web app. It neither buffers nor compresses responses, so live Run logs (`GET /api/runs/:runId/events/stream`) stream as they come. `STUDIO_TLS=internal` uses Caddy's own CA instead, for tests only. The agent worker uses a second listener, plain HTTP on port 8080 of the proxy's fixed address inside Studio's network (not published), for `/api` only.

**Trusted proxy (login rate limit).** The API trusts `X-Forwarded-For` only from the proxy's fixed address (`API_TRUSTED_PROXIES=172.31.250.20`, set by the Compose file; a value in `.env` is ignored), and Caddy sets that header from the connection itself, ignoring any incoming one. The network's gateway (`172.31.250.1`) is never trusted: every host process reaching a published port or the proxy's worker port, the agent user included, arrives from it. So each client has its own login rate-limit bucket by its real address: the operator's from outside, the agent user's (and any other host process's) as the gateway. A misled agent can exhaust only its own bucket, and a forged `X-Forwarded-For` does not change it. The ports are published on IPv4 only because Docker relays IPv6 clients through its userland proxy, from the gateway's address. Only ports 80 and 443 of the proxy, and SSH, are reachable from outside.

### Previews: domain, certificate, password

The `proxy` service serves Previews on `preview-<12 hex>.<preview domain>` when `STUDIO_PREVIEW_DOMAIN` is set: `agentic-studio-compose` then adds `compose.preview.yaml` ([`deploy/compose.server.preview.yaml`](../../deploy/compose.server.preview.yaml)), which gives the proxy the domain, the password hash, [`Caddyfile.preview`](../../deploy/Caddyfile.preview) (read-only, imported by the Caddyfile), the socket directory `/run/preview-proxy` (read-only; Docker creates an empty one until the Preview server setup, #286, does) and the supplementary group `PREVIEW_PROXY_GID` (default `2003`, which must equal the group #286's setup creates for the sockets). The proxy keeps uid 10001, no capabilities beyond binding ports, a read-only root filesystem and `no-new-privileges`. Without the domain there is no Preview site, mount or group. Do these in order:

1. **DNS:** an `A` record `*.<preview domain>` pointing to the server's IPv4 address, with no `AAAA` (the proxy is IPv4 only). Prefer a preview domain under a different registrable domain from Studio's.
2. **Certificate:** a wildcard certificate for `*.<preview domain>` from your own DNS-01 tooling (the proxy has no DNS module). Put `fullchain.pem` and `privkey.pem` in `/var/lib/agentic-studio/proxy/preview-tls/`: directory `0700`, files `0600`, owner `10001:10001`. Without them Caddy refuses to start and `up -d --wait` fails. Renew before expiry: replace the files, then `agentic-studio-compose restart proxy`, which briefly interrupts Studio.
3. **Password:** generate a long random value (for example `openssl rand -base64 24`) and keep it in your password manager. Hash it with `docker run --rm -it <pinned caddy image> caddy hash-password` (the image is in `compose.server.app.yaml`), and put `STUDIO_PREVIEW_PASSWORD_HASH='<hash>'` in `/etc/agentic-studio/.env`. The user name is always `preview`. To rotate, replace the hash and run `agentic-studio-compose up -d --wait`.
4. **Only then** set `STUDIO_PREVIEW_DOMAIN` and run `agentic-studio-compose up -d --wait`.
5. **`PREVIEW_PROXY_GID`** changes only together with the setup script's `PREVIEW_PROXY_GID`.

How the route behaves (header rules, the "not running" answer, other hostnames) is in [Security](security.md) section 5. Known gaps: no rate limit on the Preview password (stock Caddy has none); manual certificate renewal with a proxy restart; a Preview cannot use HTTP `Authorization` itself, because the proxy strips it after the password check.

### Previews: the Preview user and the controller

The Preview user ([ADR 0004](../architecture/adr/0004-preview-isolation.md)) runs two things as ordinary user services of its own user manager: its **rootless Docker daemon**, in which every Preview is built and run, and the **environment controller**, which fetches operations from Studio's API and drives that daemon. It is as separate from the agent user as both are from Studio: its own uid, group, home (0750), subordinate ids, daemon, firewall, limits and `.env`; neither is in the other's group, and neither can reach the other's socket, data-root or files.

**Boot order.** Both firewalls come before any user manager and do not wait for the system Docker daemon: they are `uid-owner` rules in `OUTPUT`, which Docker does not touch, so the order between them and the system daemon does not matter. Then `systemd-tmpfiles` (the socket directory), then `user@<Preview uid>` (bound to its firewall), then the rootless daemon (its `ExecStartPost` applies the egress rules; the daemon does not start without them), then the controller (`Requires`, `After` and `PartOf` the daemon). When the daemon restarts, the controller restarts with it and starts nothing before it has read the rules back; `restart: "no"` keeps the daemon from starting containers first.

**Egress rules.** Preview containers and builds may reach the internet, and DNS only at the resolver in `daemon.json` (and slirp4netns's own, `10.0.2.3`). In the daemon's network namespace the chain `DOCKER-USER` rejects, on the output interface `tap0`, the private ranges (10/8, 172.16/12, 192.168/16, 169.254/16, 100.64/10) and every global IPv4 address of the host (read at each apply, so Studio's containers, the proxy, PostgreSQL, the host's addresses and the host's loopback behind `10.0.2.2` are unreachable), and an IPv6 default route is removed. `preview-egress-rules verify` (run by the controller before every build and up, and by the checks) exits 0 only when exactly the expected rules are in place, in order, and no IPv6 default route exists. The rules guard the containers; the Preview user owns the namespace and its daemon, which is why the trust boundary is the user (ADR 0004).

**The socket directory.** `/run/preview-proxy` is `preview:previewproxy` with mode 2750 and the setgid bit: the controller's `socat` bridges create their sockets there as the Preview user, and the sockets belong to the proxy group (`chown(sock, -1, PREVIEW_PROXY_GID)` succeeds without the Preview user being a member). The proxy container joins the group through `group_add` (`PREVIEW_PROXY_GID` must match the Compose setting, [Previews: domain, certificate, password](#previews-domain-certificate-password)) and mounts the directory read-only.

**Manual steps**, after the setup script and with Studio running:

1. Generate a token (`openssl rand -base64 32`), **never the worker token**, and put it in `/etc/agentic-studio/.env` as `STUDIO_CONTROLLER_TOKEN` (root) and in `~preview/.config/agentic-studio-controller/.env` as `STUDIO_CONTROLLER_TOKEN` (Preview user, 0600). The same value, in these two files only; the API refuses a controller token equal to the worker token.
2. As root: `agentic-studio-compose up -d --wait` (the API reads the token), then `deploy/setup-server.sh --only controller-service`: the controller starts once its token is set.
3. As the Preview user (`sudo -iu preview`): `agentic-studio-check-preview --claim` must end with `RESULT: PASS`.

The controller's unit runs as production (`STUDIO_CONTROLLER_ENVIRONMENT=production`): the fake runtime, a non-rootless Docker and another egress script are refused. It has no Studio-side variable, no worker token and no agent credential in its environment, and needs at least `STUDIO_CONTROLLER_MIN_FREE_GB` (2 GiB) free where it builds. The unit sets no `RestrictNamespaces` and no seccomp filter, because the controller enters the daemon's namespaces.

**Images, the build cache and disconnect.** The controller removes the labelled images of a Preview when its data is reset or its Repository is disconnected, and the dangling ones after every build. Pulled base images stay: to prune them by hand, as the Preview user run `docker image prune --all` (it removes every image no container uses, also those a later build would pull again). After every build the controller prunes the Docker build cache to `STUDIO_CONTROLLER_BUILD_CACHE_MAX_GB` (default 10) in the controller's `.env`. Disconnecting a Repository waits for the controller: it asks for the Preview's data to be removed and stays `disconnecting` until the controller has done it, retrying every 30 seconds, so a stopped controller delays the disconnect. `STUDIO_PREVIEW_MAX_RUNNING` (default 3) in the Studio `.env` limits how many Previews run at the same time.

### Working copy retention and disk

Each Run has a Working copy on the agent side (`<STUDIO_WORKER_DATA_DIR>/runs/<runId>`, a clone of the Project's cache with the Run's changes) and a stored agent session. A Follow-up needs both, so how long they are kept decides how long a Run can be continued. **Studio decides**, from what it knows of each Run; the agent worker removes a Working copy only when Studio says so (and directories for no known Run, as before), together with what belongs to it on the agent side. Exactly, in this order: the Run's containers, networks and volumes (through its Compose project); then the session files the provider CLIs keep for the Working copy under the agent user's home, found only from the Working copy's path and the session id Studio recorded, and never through a symlink (Claude Code: the directory `~/.claude/projects/<the Working copy's path, every character that is not a letter or digit as a dash>`; Codex: the session file `~/.codex/sessions/<yyyy>/<mm>/<dd>/rollout-<time>-<session id>.jsonl`); then the Run's directory. If the containers cannot be removed the Working copy stays and the next hourly pass tries again. After a removal pass the worker also rewrites Studio's Codex configuration, which drops the Codex trust entry of the removed Working copy (the entries are rebuilt from the Working copies that remain). Logins, settings and other sessions are never touched. Claude Code's small per-path state outside its projects directory (for example its entry for the path in `~/.claude.json`) is not removed. Removing the session files is best effort: a failure is logged and never keeps the Working copy. The worker's own retention settings `STUDIO_WORKER_RETENTION_DAYS` and `STUDIO_WORKER_RETENTION_MAX_PER_PROJECT` no longer exist (Studio decides; a value left in the worker's `.env` is ignored). The periods are the API's settings, in `/etc/agentic-studio/.env` (defaults in `deploy/studio.env.example`):

| Run | Kept until |
| --- | --- |
| Active (queued, preparing, running) or waiting for the operator | Never removed. |
| Finished, with an open or draft pull request, or one whose state Studio does not know | The earlier of `STUDIO_RETENTION_OPEN_PR_IDLE_DAYS` (30) days without activity on the Run (a Run step, an Answer or a Follow-up) and `STUDIO_RETENTION_AFTER_PR_END_HOURS` (24) hours after the pull request was merged or closed (or found missing). A pull request whose state could not be read counts as open, so a Git host outage never removes anything. |
| Finished, without a pull request | `STUDIO_RETENTION_DAYS` (7) days from its latest result, and beyond the newest `STUDIO_RETENTION_MAX_PER_PROJECT` (10) such Runs of a Project. The limit counts only these Runs and never removes a Run with a pull request. |

The agent worker applies the answer at start and hourly, so a Working copy can outlive its date by up to an hour. After removal the Run stays in Studio with its conversation, log, stored diff and pull request link; only continuing it is no longer possible, and the Run page says so. The Run page shows "Open to Follow-ups until <date>" while it can be continued; the date moves with activity.

**What this means for disk size.** A Run with an open pull request can keep its Working copy for up to 30 days, so plan for roughly *(Runs under review at once + Runs of the last week without a pull request, at most 10 per Project)* × *(a repository's checkout, with its build output and dependencies)*, plus one cache per Project. Lengthening `STUDIO_RETENTION_OPEN_PR_IDLE_DAYS` raises the number directly; merging or closing pull requests frees their Working copies within a day. Rootless Docker images and volumes of kept Runs are in the agent user's home too ([Disk quota](#disk-quota)).

**Disk figures and the free-space guard.** The worker measures its data directory at most every ten minutes and reports, with its status, the bytes in Working copies and in caches (a file shared by a clone and its cache counts once), how many Runs it keeps, and the free and total space. The Executions page shows them. `STUDIO_WORKER_MIN_FREE_GB` (default 10, in the worker's `.env`; 0 turns it off) is the free space the worker keeps: below it the page warns, and the worker prepares no new Run, which fails with `preparation_failed` and a detail naming the free space. Follow-ups, answers and deliveries of existing Runs are not blocked. Free space by merging or closing pull requests, lowering the periods above, or removing what is not Studio's from the disk.

### Disk quota

The `limits` step sets a disk quota only when `AGENT_DISK_QUOTA_GB` is set and user quotas are switched on for the filesystem holding the agent user's home directory; otherwise it reports that none was set. To switch them on for ext4: add `usrquota` to that filesystem's options in `/etc/fstab`, remount it, run `quotacheck -cum <mount>` and `quotaon -u <mount>`, then run the script again with `AGENT_DISK_QUOTA_GB=<GiB>`. The agent user's rootless Docker images and volumes are in its home directory, so the quota covers them.

## 5. Boundary checks

[`deploy/check-boundary.sh`](../../deploy/check-boundary.sh), installed as `/usr/local/bin/agentic-studio-check-boundary`, runs as the agent user after every server change (packages, users, Docker, firewall, Compose files) and implements the checks of [Security](security.md) §9. Each check prints `PASS`, `FAIL` or `SKIP` with one line of detail; the last line is `RESULT: PASS` (exit 0), `RESULT: PASS WITH SKIPS` (exit 0; not a complete server check) or `RESULT: FAIL` (exit 1). It prints no secret; attach its output, redacted of host names, to the server change.

| Check | Must |
| --- | --- |
| `processes-in-user-manager`, `no-studio-container-as-agent` | Every process of the agent user runs under `user@<uid>.service` (except the check's own session); no system Docker container runs as its uid. |
| `not-root`, `not-in-docker-group` | Run as the agent user, which is in none of the root-equivalent groups `docker`, `lxd`, `incus-admin`, `libvirt`, `disk` (the setup script refuses them too). |
| `studio-config-unreadable`, `studio-data-unreadable` | Fail to read `/etc/agentic-studio`, its `.env`, `/opt/agentic-studio`, `/var/lib/agentic-studio` (with `data/` and the proxy's certificates in `proxy/`) and Docker's volumes. |
| `secrets-unreachable` | Fail to read the master key or a Deploy key; no Studio variable (`DATABASE_URL`, `REDIS_URL`, `REDIS_PASSWORD`, `STUDIO_SECRETS_KEY`, `STUDIO_OPERATOR_PASSWORD_HASH`, `STUDIO_MERGE_TOKEN`, `POSTGRES_PASSWORD`) in its environment or the worker's `.env`. |
| `system-docker-unreachable`, `system-containerd-unreachable` | Fail to reach the system Docker socket (`curl --unix-socket`, `docker -H`); the system containerd socket (`/run/containerd/containerd.sock`) is not writable. |
| `sudo-needs-password` | `sudo -n true` fails. |
| `studio-stack-running` | Positive control: Studio's public health route through the reverse proxy's worker port (`STUDIO_API_URL` + `/api/health`) answers 200, so the refusals below are not just a stopped stack. A stopped Studio makes the run fail. |
| `studio-postgres-unreachable`, `studio-redis-unreachable` | Fail to connect to `127.0.0.1:5432`/`6379` and to the containers' addresses. |
| `studio-app-direct-unreachable` | Fail to connect to the API and web directly: `127.0.0.1:3001`/`3000` and their containers' addresses (`.12:3001`, `.13:3000`); only the reverse proxy is open to the agent user. |
| `no-wsl-escape` | No WSL interop and no Windows drive mount. |
| `cgroup-v2`, `agent-user-limits` | cgroup v2; the agent user's slice has a `MemoryMax` and a `TasksMax`. |
| `managed-guardrails`, `managed-guardrails-locked` | Every file in the worker's `managed-files.txt` is installed as a real file, `root:root 0644`, with every directory up to `/` root-only, and the same SHA-256 as the worker's copy (`WORKER_CODE_DIR`, default `/opt/agentic-studio-worker`); the paths it lists as `absent` (`/etc/claude-code/managed-settings.d`, `/etc/claude-code/managed-mcp.json`, `/etc/codex/config.toml`) do not exist; `/usr/bin/env` and `/usr/local/bin/node` (the hooks' launcher and interpreter) are real root-owned files; the agent user can write or replace none of them. |
| `rootless-docker`, `rootless-container-limits`, `rootless-compose` | The agent user's own daemon answers, is rootless on cgroup v2 with the systemd driver; a container started with `--memory` and `--pids-limit` gets them; a Compose stack starts and stops. |
| `worker-token-works`, `worker-token-nothing-else` | A read-only worker route answers 200 with the worker token and 401 without it; operator routes (`GET /api/projects`, `/api/runs`, `/api/auth/session`, `/api/providers`: 401; `POST /api/projects`: 401 or 403) refuse it. The token is read from the worker's `.env` and sent on stdin to `curl`, never on a command line. |

| `preview-files-unreadable`, `preview-docker-unreachable`, `preview-sockets-unreachable`, `worker-token-not-controller` (group `preview`) | The Preview user's home, the controller's `.env` (the controller token) and its data directory are refused; its rootless Docker socket and data-root are refused (`curl --unix-socket`, `docker -H`; an absent runtime directory is a `FAIL`, it refuses nothing); the agent user is not in the proxy group and cannot list `/run/preview-proxy` (with the group it could reach a Preview's socket and skip the Preview password); the controller's claim route answers 401 to the worker token. |

`--skip <group>` leaves out a group (`identity`, `processes`, `studio-files`, `docker-socket`, `sudo`, `studio-network`, `host`, `cgroup`, `guardrails`, `rootless`, `preview`, `api`) and reports it as `SKIP`, ending with `RESULT: PASS WITH SKIPS`; a server check counts only as `RESULT: PASS`. The settings at the top of the script (directories, the container addresses, `CHECK_IMAGE`, `WORKER_CODE_DIR`) can be overridden through the environment.

### Preview checks

[`deploy/check-preview.sh`](../../deploy/check-preview.sh), installed as `/usr/local/bin/agentic-studio-check-preview`, runs as the **Preview user** after every server change. Same output as the boundary checks (`PASS`, `FAIL`, `SKIP`, `RESULT:`), the token sent on standard input of `curl` and never printed. `--skip <group>` leaves out a group (`identity`, `refused`, `cgroup`, `egress`, `internet`, `controller`, `api`); `--claim` also claims an operation.

| Group | Checks |
| --- | --- |
| `identity` | Not root; in none of `docker`, `lxd`, `incus-admin`, `libvirt`, `disk`, `sudo`, the proxy group or the agent's group; `sudo -n` refused; home 0750 or tighter; linger on. |
| `refused` | Refused: the system Docker and containerd sockets, the agent's socket and data-root, the agent's home and worker `.env`, Studio's configuration, Compose files and state, and Studio's PostgreSQL, Redis, API and web (the Preview user's own firewall). |
| `cgroup` | cgroup v2; `cpu memory pids` delegated to the user manager; the slice has its limits; a scope with `MemoryMax=64M` and `TasksMax=20` gets them and an unbounded allocation in it is killed (a limit that bites); with `MemoryMax` set at run time on the Preview user's `app.slice` (which holds the rootless daemon and the build steps; the controller bounds it per build) to what it uses plus 512 MiB, a build whose `RUN` step holds about 1.2 GB (below the user slice's limit) fails with an OOM kill inside it (the slice's `oom_kill` counter rises), the rootless daemon is active afterwards, and the property is restored. |
| `egress` | The egress script is `root:root 0755`; the rootless daemon is rootless on cgroup v2 with the systemd driver; `daemon.json` names the resolver the rules allow; `verify` passes inside the namespace; from a **Compose project network** and from a **build `RUN` step**, the proxy, PostgreSQL, the host's non-loopback address (a listener the check starts) and `10.0.2.2` are blocked. |
| `internet` | A container reaches public HTTPS (skippable where the machine has no internet). |
| `controller` | The unit is enabled; `.env` is 0600 and the data directory 0700, both the Preview user's; `STUDIO_CONTROLLER_ENVIRONMENT` is `production` (and runtime, rootless flag and egress path stay at their defaults), the unit's `DOCKER_HOST` is `unix://$XDG_RUNTIME_DIR/docker.sock`, no `RestrictNamespaces`, `NoNewPrivileges=yes`, `KillMode=mixed`; `/run/preview-proxy` is `preview:previewproxy 2750`; at least 2 GiB free; the controller is active (`SKIP` while the token is empty). |
| `api` | The controller token is accepted by a controller route (an operation that does not exist: 400, 404 or 409, not 401; 401 without the token); the claim route answers 200 or 204 (with `--claim` only: a claim would take a queued operation); the worker route and the operator routes answer 401 to it. |

## 6. Enabling a provider

Enabling a provider is a separate operator action ([Security](security.md) §2), never done by the script:

1. The provider's compliance record under [`provider-compliance/`](provider-compliance/) is `Approved` and still applicable; moving to this server is a revalidation trigger in both records (#130).
1. The managed guardrails are in place (`agentic-studio-check-boundary` passes `managed-guardrails`); otherwise the worker reports the provider unavailable ("managed guardrails missing or changed: <path>").
2. As the agent user, set `CLAUDE_CODE_ENABLED=true` or `CODEX_CLI_ENABLED=true` (only the exact value `true` turns it on) in `~/.config/agentic-studio-worker/.env`, then `systemctl --user restart agentic-studio-worker`.
3. When the approval no longer applies, set it back to `false` and restart the worker before any further Run.

## 7. Backups and restore drill

Backups are kept **off the server** (ADR 0002), so that a compromised or wiped server can be rebuilt.

- **Database.** As root, `agentic-studio-compose exec -T postgres pg_dump -U studio -d agentic_studio -Fc > agentic-studio-<date>.dump`, then copy the dump off the server and delete the local copy. The stored secrets in it are encrypted: **a backup is useless for them without the master key**.
- **Source code in the database.** Since Issue #144 the database also holds each Run's latest diffs: excerpts of the managed repositories' source (the changed lines with some context), redacted like the Run log and bounded by the agent worker's diff limits (`STUDIO_WORKER_DIFF_*` in its `.env`: by default 256 KiB per file and 2 MiB per diff, two diffs per Run). They stay until the Run is deleted with its project. Treat database backups like the repositories themselves: keep them where only the operator can read them.
- **Master key.** `STUDIO_SECRETS_KEY` is backed up once, separately from the database backups (for example in the operator's password manager), never next to them.
- **Configuration.** The rest of `/etc/agentic-studio/.env` can be recreated; the operator password hash and the worker token can be generated again.
- **Not backed up.** Clones and Working copies are recreated from the Git hosts (a Run whose Working copy is gone cannot be continued: [Working copy retention](#working-copy-retention-and-disk)); the agent side's CLI logins and the Agent account token are issued again.

**Restore drill**, on a throwaway Ubuntu 24.04 machine, after the first real Runs and then on a schedule the operator sets: run the setup script; fill in `.env` with the backed-up master key and new values for the rest; `agentic-studio-compose up -d --wait postgres`; `agentic-studio-compose exec -T postgres pg_restore -U studio -d agentic_studio --clean --if-exists < agentic-studio-<date>.dump`; start the rest; sign in and check that Projects and their Repositories are there and a stored secret can be used (a fetch with a Deploy key). Record the date and result. Then destroy the machine.

## 8. What CI covers

The CI job `deploy:server` (`.github/workflows/ci.yml`) runs on every code change:

- `shellcheck` on both scripts, the tests and the smoke helper `apps/agent-worker/scripts/smoke-guardrails.sh`.
- [`deploy/tests/compose-server.test.mjs`](../../deploy/tests/compose-server.test.mjs) (`docker compose config` only): only the reverse proxy publishes host ports (80 and 443, IPv4), the API trusts the proxy's address only (whatever `.env` says), the `migrate` service runs before the API with the database URL only, every Studio container runs as uid 10001 with a read-only root filesystem and no capabilities, the web container gets no Studio secret, and the network defaults, the worker port and the Caddyfile's routes agree across files.
- [`deploy/tests/preview-proxy.test.mjs`](../../deploy/tests/preview-proxy.test.mjs) (Issue #277; Docker, root or `sudo -n`): Caddy from the pinned image with the real `Caddyfile` and `Caddyfile.preview` and the Compose hardening flags, on `127.0.0.1`, in front of stand-ins (Studio's api and web with counters; Preview sockets of uid 2002, group 2003, mode 0660 in a 0750 directory, [`preview-standin.mjs`](../../deploy/tests/preview-standin.mjs)). A throwaway wildcard certificate and a random password per run. It proves: Studio's host reaches api and web and never a socket; the password is asked first (401, nothing upstream); the Preview sees no `Authorization`, no Studio cookie and no client address header, also when forged, over HTTP/1.1, HTTP/2 and WebSocket; a missing or stale socket answers "not running" and a re-created one serves again without a restart; other hostnames get 404 with no prompt; hosts never cross (counters, 421 on an SNI and Host mismatch, http only redirects); a user outside the group cannot connect; Previews off still serves Studio; Studio under the preview domain still reaches the web app.
- [`refuse-distro.sh`](../../deploy/tests/refuse-distro.sh) in a Debian container: the script refuses and changes nothing.

## Known gaps

- **One bucket for every host process.** Every process on the server reaches Studio from the network's gateway, so they share one login rate-limit bucket (the operator signing in through an SSH tunnel to the server too); the operator from outside keeps their own.
- **Preview password** (#277): no rate limit (stock Caddy has none); the wildcard certificate is renewed by hand and needs a proxy restart; a Preview cannot use HTTP `Authorization` itself.
- **IPv4 only.** The firewall rule is `iptables` only; Studio's container network has no IPv6. Add an `ip6tables` rule if IPv6 is ever turned on for it.
- **The CLI runners** are being built (#105, #106); the install and login steps above follow them.
- **Managed guardrails and the provider CLIs** (#134): the real-CLI behaviour (Studio's hook blocking, planted user-level hooks and rules ignored) is evidenced by the controlled smoke on the test worker, not by CI, which runs the stub CLIs.
- **On-server verification** (#130): the setup and boundary checks on the target server, the rootless Docker trial repeated there, one real Run per enabled provider, the branch protection check and the compliance records' revalidation note.

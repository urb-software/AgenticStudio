# Security Guardrails — AI Agent Studio

**Status:** design-time minimum controls and threat model. Permission enforcement, secret stores, sandboxing, allowlists and negative tests are **not yet implemented**; they are prerequisites for real unattended CLI agent execution.

## 1. Threat model and trust boundaries

The system runs code and tools against potentially hostile repository content. Key threats:

- Prompt injection in repository files, Issues, README files, logs, MCP tool responses, fetched documentation, and in Review comments and check logs from the Git host (Pull request checks).
- Data exfiltration via shell, logs, arbitrary HTTP/network egress, commit contents, agent-visible environment variables.
- Cross-project filesystem escape, symlink traversal, path confusion, rogue working copies, Git credential misuse.
- Docker privilege escalation, unapproved Compose actions, host access, untrusted Preview content.
- Unsafe dependency installation, arbitrary shell hooks, malicious configuration.
- Duplicated jobs/events, replay, stale authorization, unintended merges, destructive migrations.

**Trust boundaries:** operator's admin session; Studio UI/REST API; PostgreSQL/Redis; untrusted project repository; agent runner; MCP servers; environment-controller; Docker host; exposed Preview origin. Credentials and authority stay narrow across each boundary.

## 2. Agent execution policy

Run isolation model: [ADR 0002](../architecture/adr/0002-agent-run-isolation.md).

- Each run has an **assigned project, working copy, branch, approved tool set, time/resource budget and explicit run identity**.
- **Where runs execute.** Studio (web, API, database, secrets, repository copies) runs in containers under the system Docker daemon, which only root controls. The agent worker and the agents it starts run on the host as an ordinary user, the **agent user**: never in the `docker` group, no passwordless `sudo`, no access to Studio's files. This operating-system boundary is the security boundary.
- **Working copy per run.** Each run works in its own clone, made from a per-project cache at the exact commit Studio recorded, on a branch named for the run; the agent definition, task and logs sit beside it, outside the repository. A working copy is an organization mechanism, **not a sandbox**. Enforce filesystem permissions and the user boundary between the agent user and Studio; how runs are kept apart from each other is set in [ADR 0002](../architecture/adr/0002-agent-run-isolation.md). Test path traversal and symlink escape.
- **Docker.** The agent worker and the agents **never obtain privileged Docker host access**: no access to the system Docker daemon or its socket (`/var/run/docker.sock`), no `docker` group membership, never a privileged container. Agents may use a **rootless Docker daemon owned by the agent user** for Compose stacks, integration and end-to-end tests; it grants nothing beyond the agent user's own rights. It is separate from the `environment-controller`, which runs in the Preview user's own rootless daemon and manages project Preview stacks ([§5](#5-environments--docker-compose), [ADR 0004](../architecture/adr/0004-preview-isolation.md)).
- **The worker always calls Studio**; Studio never reaches into the host. The worker's token is limited to handling runs.
- CLI **hooks and permission rules are guardrails** against destructive mistakes, **not the security boundary**; the user boundary must hold without them.
- **Content from the Git host never reaches an agent automatically** (refinement of Epic #139, 2026-11-16). Review comments and the logs of Pull request checks reach an agent only as a Follow-up the operator sends: the operator triggers loading the content, sees it, can edit it, and sends it. Comments by the operator's own Git host account are preselected; comments by anyone else are shown separately, collapsed and unselected. All of it, like everything Studio shows from an agent, is displayed as plain text.
- **What a run takes from the repository's configuration** ([ADR 0002](../architecture/adr/0002-agent-run-isolation.md#run-decisions-2026-11-15), operator decision 2026-11-15). Nothing from the repository that executes code or changes permissions is loaded: no hooks, no MCP servers, no settings files. A run uses only the text of the repository's instruction files (`CLAUDE.md`, `AGENTS.md`); imports inside them are followed only within the working copy.
- User/project code runs with the least capabilities possible: restricted host mounts, file access, process execution, network egress and inter-project access, per task.
- No production credentials or production data for coding agents, and none anywhere on the server; separate development/test accounts and databases.
- Configure execution timeout, cancellation, CPU/RAM/storage limits and output-size/log quotas; repeated operations are idempotent where appropriate.
- **Run limits as built (Issue #100).** The agent worker stops a Run step at its time limit (SIGINT to the step's process groups, then SIGKILL after the grace) and refuses a step beyond the maximum; Studio backs the time limit with a sweep (the step's limit plus 5 minutes) and cancels Runs left waiting for the operator too long. The **delivery** after a step (commit, push, draft pull request) is not under the step clock: it is bounded only by the worker's own Git and GitHub call timeouts, and an operator's cancel lets it finish so the Run records what it pushed.
- No unapproved MCP tools and no configuration changes outside permitted boundaries.
- **Claude Code runner as built (Issue #105).** The worker starts the CLI only through its spawn boundary, with exactly the options of the [compliance record's Mode](provider-compliance/2026-11-14-claude-code-cli.md#mode) (`--setting-sources user`, `--strict-mcp-config`, prompts disabled, a bound on turns, Studio's settings and instructions files, the result schema), standard input closed, and a minimal environment: only `PATH`, `HOME`, `USER`, `LOGNAME`, `LANG`, `LC_ALL`, `TZ`, `XDG_RUNTIME_DIR`, `DOCKER_HOST` (never the system socket), plus `TERM=dumb`, the step's `TMPDIR` inside the Run's directory and the Run's `COMPOSE_PROJECT_NAME`. Nothing that would override the subscription login (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_USE_*`) and none of the worker's own settings reach it. The CLI version is checked at worker start (supported `>=2.1.325 <2.2.0`); any other version leaves the provider unavailable with the reason. The instructions file holds Studio's base rules, then the Run's agent instructions (from the claim, in a delimited untrusted block), then the text of `CLAUDE.md` and `AGENTS.md` read from Git at the start commit, in delimited untrusted blocks, imports followed only inside the repository. ### CLI usage and provider terms — MVP decision (canonical)

- The MVP integrates the **official Claude Code and Codex CLI binaries**, not direct model API calls.
- Before implementing the agent worker, validate that the intended headless execution and authentication flows comply with each provider's **current** terms. A non-interactive CLI command existing does not establish permission for every form of subscription-based automation; consumer subscriptions are not unrestricted programmatic API access.
- The worker must **not extract, intercept, share, or proxy subscription credentials**.
- A small runner interface isolates provider-specific CLI execution. API/SDK runners (calling a model API or provider SDK directly instead of the CLI binary) are **out of scope for MVP**; they may be considered later if provider policy or product needs require it. Running the official CLI binary with an API key or other supported credentials is still a **CLI runner** and in scope; the authentication method is part of each provider's validation.
- **Acceptance gate:** automated execution for a provider stays disabled until its intended authentication and execution model is validated. Validation is per provider; approval for one never implies approval for the other.

#### Provider compliance decision records

Validation produces a durable, auditable decision, not an informal "validated". Technical Tasks **B6** (Claude Code CLI) and **B7** (Codex CLI) each produce a dated record under `docs/engineering/provider-compliance/` (template in that folder's `README.md`) documenting:

- Provider and CLI version.
- Terms and documentation reviewed: source URLs, version or effective date where available, review date.
- Selected authentication method.
- Permitted execution mode and relevant restrictions.
- Evidence from a controlled headless execution test.
- Decision (`Approved`, `Rejected`, or `Needs Clarification`) and the operator who accepted it.
- Next review date and triggers for earlier revalidation.

A provider is enabled in the agent worker only when its task is complete with an `Approved`, still-applicable record.

#### Runtime enforcement: per-provider enablement flags

The provider gate is a **runtime authorization requirement**, not only an instruction to coding agents. The agent worker reads one operator-controlled flag per provider from its deployment configuration:

```text
CLAUDE_CODE_ENABLED=false
CODEX_CLI_ENABLED=false
```

- Both default to disabled. **Fail closed:** only the exact value `true` enables a provider; missing, empty, malformed or `false` means disabled.
- Each provider needs its own flag enabled; enabling one **never** enables another.
- Before spawning any provider CLI process, the worker checks the flag and rejects the execution if disabled. Rejection is an explicit execution failure with a clear, non-sensitive error, not a silent skip.
- Only the trusted operator/deployment configuration sets these values. They **cannot be overridden** by an execution request, workflow definition, agent configuration, MCP response, or model-generated instructions.
- The operator enables a provider only after its compliance record is `Approved` and still applicable. Setting the flag does **not** itself constitute compliance, legal or terms approval.
- If approval is revoked or no longer applicable (e.g. the review date passes or a revalidation trigger occurs), the operator disables the flag before any further executions.
- Required negative tests: [Quality](quality.md) §10.

### Agent and skill definitions

Decided in the refinement of Epic #298, 2026-11-25 ([ADR 0005](../architecture/adr/0005-agent-definitions-in-git.md)). An Agent definition is the text and files an agent is given. It is more powerful than any repository content, so these rules hold:

- **The definitions Repository is never the target of a Run, and the Agent account has no access to it.** Starting a Run on it is refused, as are Preview settings, builds, stop and reset, and an Environment file, each in its own handler with a 409 `definitions-project`; the Run and lookup claims join on `kind = 'code'`, so no claim can name it (a test pins this with a hand-inserted row). Only the operator, through Studio or their own Git, changes what agents are told.
- **The base rules cannot be overridden.** Studio's built-in text (when to ask, the structured result, Follow-ups, bringing a branch up to date) is always given first. A definition's instructions come after it and cannot edit, remove or outrank it.
- **A definition may not carry tools, permissions, hooks or MCP servers, in any form.** An unknown front matter key is refused, as is any key that asks for one of these. Limits on file count, size per file and size per folder apply, and a path that leaves the folder is refused; the limits are fixed in the validation's code. An invalid agent is listed with its reason and cannot be chosen.
- **Scripts never run by themselves.** The CLIs' inline shell execution in definitions stays switched off. An agent runs a script only through its normal command tool, under the same guardrails and operating-system user as any other command.
- **The agent's files are delivered outside everything a CLI discovers (Story #304).** The worker writes the files beside `AGENT.md` to `<run directory>/agent/`, rebuilt from Studio's copy before every Run step, never from the Repository's working tree and with no cache the agent user can write. The place is outside the Working copy and under no `.claude`, `.codex`, `CODEX_HOME`, plugin, skills or agents directory, and no CLI option names it, so neither CLI reads a file there unless the instructions name it (a test pins the path relationship and the options of both CLIs). Files are `0644` (`0755` where Git says `100755`), the worker's own; the worker validates the hand-over with the shared package, path rules included, before it writes, and a failure writes nothing and fails the Run (`agent_folder_invalid`; `agent_folder_unavailable` when the Clone no longer holds the commit) before any CLI starts. **What the agent can do with them, as checked against the managed rules:** Claude Code's managed `Read`, `Glob` and `Grep` allow rules reach `agent/` (the guard hook blocks no read), and its shell allows `python3`, `node`, `npm`, `pnpm` and the like on a path there, but no `sh`, `bash` or direct execution of a script, as for any script of the repository; `Write`, `Edit` and `MultiEdit` refuse the folder (`blockWritesOutsideWorkingDirectories` and the hook), though the shell, as the same operating-system user, could still change it, which the rebuild before the next step undoes. Codex's `workspace-write` sandbox reads and runs outside the Working copy and writes only inside it. No managed setting was changed for this.
- **Studio's skills are guidance, not code to run (Epic #326, [ADR 0006](../architecture/adr/0006-skill-definitions.md)).** A Skill definition is validated like an agent: unknown front matter keys are refused, a key that asks for tools, permissions, hooks, MCP servers, memory or isolation is refused for its own reason, and a skill with an inline shell line is refused; the exact limits belong to the validation's code (Issue #328). Its scripts and assets are allowed in what the operator published, but never run by themselves: an agent runs one only through its normal command tool, under the same guardrails and operating-system user as any other command. The worker delivers the named skills outside everything a CLI discovers (the rule for an agent's files above), rebuilt from Studio's copy before every Run step and never committed or pushed. A missing or invalid skill fails closed: the agent that names it cannot be chosen. **The repository's own skills are unchanged**, as are their rules above; Studio's skills rank above them and below the chosen agent. No managed setting or CLI option is added for this.
- **Studio's skills reach a Run as files beside it, not through a CLI (Story #331).** The worker writes the skills the Run's agent named to `<run directory>/skills/<name>/`, rebuilt from Studio's copy before every Run step with the writer of the agent's folder: fetched by the Run's id only (the worker names neither a skill nor a commit, and only the worker that holds the Run's claim is answered), judged again by `validateSkillFolder` with the description the claim carried, files `0644` (`0755` where Git says `100755`), every path joined below its skill folder, nothing cached and no process started from the folder (a test pins it). The place is outside the Working copy and the agent's folder and under no `.claude`, `.codex`, `CODEX_HOME`, plugin, skills or agents directory a CLI discovers, and no CLI option names it, so neither CLI reads a file there unless the instructions name it; the exact command of both CLIs is pinned as unchanged, so neither compliance record is amended. A skill that is gone, refused or fails the validation fails the Run before any agent starts (`skills_unusable`); a failed read on Studio's side fails it as `preparation_failed`, as for the agent's files. The skills' bytes per Run are bounded (20 MiB; skills past it are left out, with a notice) and so is the section of the instructions (8 KiB). The list of skills (name, description, path) sits in a block delimited by the per-step code and marked untrusted, like the agent's own instructions, with Studio's sentence about reading an entry file outside it; skills rank after the agent's instructions (ADR 0006), and the worker refuses a description that differs from the claim's. **Same-user boundary (ADR 0002):** during a step the agent user could rewrite the folder; the next step rebuilds it, and what the files can do is bounded by the guardrails as for the agent's own files (above).
- **The write Deploy key is limited to the definitions Repository.** It lives on Studio's side, is stored like any other Deploy key ([ADR 0001](../architecture/adr/0001-secret-store.md)) and never reaches the agent side, a Run's directory, an environment variable of an agent, a response or a log. The Merge credential is not used for publishing. Publishing is a fast-forward push only.
- **A draft reaches no agent.** Only a commit on the definitions Repository's Integration branch is delivered. A Run uses the commit it started with, and its Follow-ups use the same one. The Draft (Issue #307) is rows of the `agent_drafts` and `agent_draft_files` tables, read by no route a worker or an agent can call: the agents list, the resolution of an agent for a Run and the Clone's file tree read only the Clone, and a test pins that Draft writes change none of them. The Draft's routes answer the operator session only, writes need the Studio origin, the save route's 2 MiB body is read only for a request with the Studio origin and a session cookie (any other request gets the 100 KiB default), and its limits (1 MiB per file, 10 MiB in all, 200 files, and the shared path rules) bound what a request can store. A symbolic link or a submodule of the base cannot be written, so a Draft never turns one into content. Its text is plain data to display, never to render, run or follow. A file with a forbidden key, in an agent or in a skill, is stored and flagged, since only Publish decides what an agent is told; a Draft's skill never reaches the skills list, a Run or the worker, and a test pins it.
- **A model is chosen from a fixed list per Provider.** The lists are in the [Claude Code](provider-compliance/2026-11-14-claude-code-cli.md#mode) and [Codex](provider-compliance/2026-11-14-codex-cli.md#cli-version-and-command) compliance records; any other value is refused. The agent worker checks the value against the list itself and fails the Run `model_not_allowed` before the CLI starts, whatever the API sent; the option is added exactly as the records state (`--model <value>`, no other form). A model the CLI refuses fails the Run `model_refused`. **Not tested:** that a resumed Codex session keeps the agent's model (`--model` before `resume` is not documented by the provider); the operator smoke `apps/agent-worker/scripts/smoke-codex-model.mjs` is to confirm it and has **not been run yet**, so the record keeps saying "not tested".

## 3. Secrets and credentials

- Use a dedicated secret-management mechanism with scoped, revocable credentials. **Never commit `.env` secrets, auth/session tokens, CLI credentials, private keys or MCP secrets.**
- DB/Git definitions store secret references where appropriate, **not secret values**.
- **Chosen mechanism ([ADR 0001](../architecture/adr/0001-secret-store.md)):** Studio-held secrets, such as the private half of a Project's Deploy key, are encrypted in PostgreSQL (AES-256-GCM) behind the `SecretStore` port, with a key-version field per record. The master key comes from the environment (`STUDIO_SECRETS_KEY`, 32 random bytes, base64) and never enters the database, Git, logs or API responses. Key rotation tooling and an external secret manager are deferred.
- Inject only the necessary secret values at the point of authorized use; minimize lifetime and visibility.
- **What an agent run can see ([ADR 0002](../architecture/adr/0002-agent-run-isolation.md)).** Everything the agent user can read is visible to the agent: its own provider CLI logins (subscription login, or an API key as fallback), the agent account's token and the worker's token. These are accepted risks, so each is kept narrow and revocable: the agent account's token is limited to the managed repositories, the worker's token to handling runs.
- **Environment files hold test values only** ([ADR 0002](../architecture/adr/0002-agent-run-isolation.md#run-decisions-2026-11-15), operator decision 2026-11-15). Studio places one per project in the working copy, and the agent can read it, so it never holds production credentials or any value that must stay hidden from the agent. How it is handled (Issue #104): the content lives in the `SecretStore` (owner `projects.environment-file`) and no operator endpoint returns it; the path is a relative path inside the repository, never inside `.git` and never a path tracked at the integration branch's commit (checked when saved) or at the Run's start commit (checked by the agent worker); at a claim Studio copies it into a Run-scoped secret (owner `executions.run-environment-file`, deleted once the Run is final; a failed delivery that can be retried keeps it, so the retry's reports are redacted too, until the Run is delivered, the retry is given up, or `STUDIO_RUN_SNAPSHOT_RETENTION_DAYS` (default 7) pass) and sends it only to the claiming worker, which writes it owner-only (0600) into the Working copy without following symlinks, lists it in the Working copy's `.git/info/exclude` and the Run file's `studioPaths` (so it is never committed or pushed), never passes it to the runner, and removes it with the Working copy.
- **Follow-ups and the Environment file** (Issue #141, coordinator decision on review S3 of #150). When an agent worker claims a Follow-up, or the usage-limit resume inside one, Studio deletes the Run's earlier snapshot and snapshots the Project's **current** Environment file into a Run-scoped secret, exactly as at a Run's start, and sends it in that claim only. The worker removes every Studio-placed file from the Working copy (the earlier path too), then writes the new file the same way as at the start (owner-only, never through a symlink, excluded from commits); when the Project has no file now, the Follow-up runs without one and the Run page says so. Log redaction uses that snapshot, and it is deleted when the Run is final again under the rule above. No retention period is extended.
- **What an agent run cannot see.** Studio's files and secrets: the `SecretStore` contents and master key, Deploy keys, the operator password hash, sessions, and the database and Redis credentials; the system Docker daemon; production credentials, which never exist on the server.
- Redact secrets and sensitive commands/paths from logs, error messages, SSE payloads, CI artifacts, PR descriptions and agent handoffs.
- **Run logs are redacted before storage, best effort** (Issue #99). One module (`executions/domain/value-objects/log-redaction.ts`) replaces with `••••••[redacted]`, before a Run event is stored: the secret values known to be available to the Run (its Environment file snapshot's values, #104: the value of every `KEY=VALUE` line, dotenv style, and every other non-comment line of at least 8 characters whole; the values of commented-out `KEY=VALUE` pairs too), credential-bearing URLs (userinfo), `Authorization`/`Bearer` values, common token shapes (GitHub tokens, `sk-…` keys, AWS access key ids, JWTs) and private key blocks. The structured result of a Run step gets the same redaction on its free-text fields (never its enum fields) before it is stored, and again when it is shown (for rows stored before). Known values shorter than 4 characters are not replaced (they would wreck the log). It cannot be complete: an agent can print what it can read in a shape no pattern knows (encoded, split across events, or a key printed line by line in separate events), and the worker cuts a text over 16 KiB before Studio redacts it, so a secret straddling that cut can leave its first part unredacted. So the log is readable by the operator only, the live stream is built on the stored (redacted) log, and the Environment file story repeats that agents can print what they can read.
- **Run diffs get the log's redaction** (Issue #144). The agent worker diffs the Working copy after every Run step's result in a temporary index (the real one is untouched), with no external diff driver or textconv, and leaves out every Studio-placed path (the Environment file even when the agent committed it; Studio also drops a file at that path). Studio redacts every patch, and the reason a diff could not be computed, with the same module before storing them (`run_diffs`, `run_diff_files`, removed with the Run), within the worker's diff limits; the Run page shows them as plain text only. The large body of the diff route (`RUN_DIFF_REQUEST_MAX_BYTES`) is parsed only for a request with the worker token. The same limits as the log apply: a secret in a shape no pattern knows stays visible, so diffs, like logs, are for the operator only, and database backups now hold source excerpts (deployment guide, Backups).
- External or provider session credentials are not copied to other agents unless explicitly supported and authorized.
- Scan source/commits/PRs for secret leaks; test that run logs cannot disclose protected values.

### Dependency supply chain

- **Release age (Issue #30 decision 4):** `pnpm-workspace.yaml` sets `minimumReleaseAge: 10080` (7 days). pnpm refuses to resolve a version younger than that, and `pnpm install --frozen-lockfile` (local and CI) refuses a lockfile entry younger than that, so a fresh compromised release cannot slip in through an update or a hand-edited lockfile.
- **Exclusions** live in `minimumReleaseAgeExclude`, as exact `name@version` entries only (never a bare name or a range), each with a comment.
- **Urgent security fix younger than 7 days:** the implementer adds the exact patched version to `minimumReleaseAgeExclude` with a comment naming the advisory (GHSA/CVE), the tracking Issue and a removal date (at most the day the version turns 7 days old), bumps the dependency, and states the exclusion in the PR's review notes. The independent reviewer checks the advisory and the exact version; the operator's merge is the approval. Once the version is 7 days old, the entry is removed in a follow-up.

## 4. Git, branch and merge protection

- Each run works in its own working copy and branch ([ADR 0002](../architecture/adr/0002-agent-run-isolation.md)) and does not write to another run's working copy.
- Studio's own Git operations go through public `projects` contracts and an authorized, path-validated Git adapter, with the Project's Deploy key.
- **Runs reach the Git host only through the agent account**: a separate account, not the operator's, whose token is limited to the managed repositories. The agent worker pushes only the run's own branch and opens a draft pull request; nothing is pushed for a failed, cancelled or timed-out run ([ADR 0002](../architecture/adr/0002-agent-run-isolation.md#run-decisions-2026-11-15)). Studio's Deploy keys never reach the agent.
- **Delivery (Issue #102).** The agent account's token lives only in the agent worker's own `.env` (`STUDIO_AGENT_GITHUB_TOKEN`); Studio stores none. The worker pushes with exactly `git push -- <remote> refs/heads/<run branch>:refs/heads/<run branch>` (no `--force`, so a remote run branch is updated only by a fast-forward) and hands the token to Git only for an HTTPS push, as an `http.extraHeader` in that one command's environment (`GIT_CONFIG_*`): never on the command line, in the working copy's configuration or in a log. SSH remotes use the agent user's own SSH setup. The push runs from a fresh repository the worker makes beside the working copy (no templates and no system configuration; an HTTPS push also reads no user configuration, while an SSH push keeps the agent user's own SSH setup), holding only the run branch, which must be this run's `agent/…-r<run id>` branch and never the integration branch; a delivery retry pushes the run branch Studio recorded. Files Studio places in a working copy (Studio's list in the claim, e.g. the Environment file; the run file and Studio's section of `.git/info/exclude` can only add to it) are never committed, and a run branch whose commits contain one is not pushed. A delivery retry goes only to the agent worker that started the run (its id is kept in its data directory).
- **Follow-ups and the pull request** ([ADR 0002](../architecture/adr/0002-agent-run-isolation.md#follow-up-decisions-2026-11-16), refinement of Epic #139, 2026-11-16). The agent worker reads pull request state, Pull request checks and Review comments through the agent account. Studio's side holds no Git host API credential for these reads; its one Git host API credential, the Merge credential, is used only for an operator's merge or close (next bullet). A run branch is brought up to date with the integration branch only when the operator asks, and only by merging the integration branch into it, never by rebasing or force-pushing. The agent account posts no replies or resolved marks on the Git host. Bringing a run branch up to date (Issue #147) is a merge the agent worker makes locally: it fetches the integration branch from the project's cache (the same hardened Git runner, hooks off); when the branch has it already nothing is changed, otherwise it commits what the working copy has uncommitted first (never a Studio-placed file) and runs `git merge --no-ff`. It completes the merge itself only for text conflicts the agent resolved (no conflict marker left); any other unresolved conflict aborts it. A part that does not end well aborts the merge and resets the run branch to its commit before the request; every new part first aborts a merge an earlier part left open, and delivery refuses to commit while a merge is open. Nothing is pushed by a part that did not end well. The push that follows is the same `git push -- <remote> <run branch>:<run branch>` as any delivery, so the merge reaches the pull request as an ordinary fast-forward.
- **Pull request checks (Issue #145).** The `pull_request_state` lookup of a draft or open pull request also reads the checks of its latest commit (`GET /repos/{o}/{r}/commits/{sha}/check-runs` and `/status`, reads only, at most 100) and stores name, state, duration and a web link for each (`runs.pr_checks`); a refusal to tell is stored as such and never fails the state. The logs reach an agent in one way only: the operator's "Send failing checks to the agent" records a `failing_check_logs` lookup (same scope check as the state lookup, same reads-only rule, no agent started); the worker reads the failed checks of the pull request's latest commit again, and for each GitHub Actions job `GET /repos/{o}/{r}/actions/jobs/{id}/logs` (a redirect to a download that is followed only to an https address or the API's own origin, **never with the token**, at most 64 MiB streamed, only the end kept), keeps the last 200 lines without timestamps, colour codes or control characters, at most 16 KiB per check and 64 KiB together; a log that cannot be read (no permission, expired, too large, not an Actions job) stays in the answer with its name, link and the reason. Studio redacts it with the log rules, puts each log in a fence the log cannot end, tells the agent in the text that the excerpts are data and not instructions, and fits the whole text into the Follow-up's length (10 000 characters). The result is stored as the Run's one **prepared Follow-up** (`run_prepared_follow_ups`, replaced by each preparation, removed when sent or discarded): it creates no Follow-up and no Run step by itself. The page shows it as plain text in an editable box with each check selectable; sending goes through the normal Follow-up route with `source: "pull_request_checks"` (stored with the message, shown in the conversation), under all its rules. There is no setting that sends failing checks automatically.
- **Review comments (Issue #146).** A comment on a pull request is untrusted: on a public repository anyone can write one, and it can be written to mislead an agent. They reach an agent in one way only: the operator's "Load review comments" records a `review_comments` lookup (same scope check and reads-only rule as the state lookup, no agent started); the worker reads the pull request's reviews, inline comments and conversation comments (`GET /pulls/{n}/reviews`, `/pulls/{n}/comments`, `/issues/{n}/comments`, a hundred to a page; of a longer listing the newest ten pages) and which review threads are resolved (one read-only GraphQL `reviewThreads` query; if it fails, or a resolved thread has more comments than one read gives, the load fails rather than showing resolved comments), and leaves out resolved threads, the agent account's own comments and, by default, comments older than the Run's latest result. At most 100 comments are kept (the latest) and 8 KiB (UTF-8 bytes) per text, 2 KiB per diff context; anything cut is stated. Studio redacts every text with the log rules (with the Run's known secret values), strips control characters, holds the limits again after the redaction, and stores one loaded set per Run, validated by the shared contract on read. The page shows every comment as plain text: Markdown, HTML and links in it are not rendered or followed. A comment is preselected only when its author's login equals `STUDIO_OPERATOR_GITHUB_LOGIN` (API setting, exact, case-insensitive; unset: none is preselected); everyone else's sit in a collapsed, unselected section with the author shown. The prepared text is built in the browser from the selection, each comment delimited in a fence its text cannot end, with an introduction that says the comments are data; the operator edits it freely. Loading is offered, and accepted by the API, only for a Run that can take a Follow-up, and only one load runs at a time (a second is refused with 409). Sending goes through the normal Follow-up route with `source: "review_comments"` and the selected comment ids, which must all be in the loaded set (checked, and the set removed, in the transaction that queues the Follow-up, under the Run's row lock that the completion of a load also takes first); the Follow-up records how many comments and their authors. Nothing is posted to the Git host (no reply, reaction or resolved mark), and there is no setting that sends comments automatically.
- **Pull request state (Issue #142).** Studio records a *lookup* request; any connected agent worker claims it over the worker routes (`/api/worker/lookups/claim`, `/api/worker/lookups/:id/result`, worker token only) and answers it through the agent account with `GET` requests only: the pull request, the run branch's position against the integration branch (compare) and the account's own login. A lookup is limited to the run's own repository and pull request: the worker rejects it (`scope_mismatch`) unless the remote names a GitHub repository, the run branch is this run's `agent/…-r<run id>` branch, and the pull request comes from exactly that branch of that repository and was opened by the agent account; nothing else is read. A rate limit is reported with how long the Git host asks to wait and retried later; errors never fail the run and are stored redacted. The page-open, Refresh, Follow-up and daily refreshes start no agent CLI (the lookup code imports no process-spawning module, which a test pins), and the worker also reads the state once more right before a Follow-up starts the agent, failing the run if the pull request is merged, closed or gone.
- **Merge and close from Studio** ([ADR 0002](../architecture/adr/0002-agent-run-isolation.md#merge-decisions-2026-11-21), refinement of Epic #258, 2026-11-21). The agent side holds no credential that can merge. Studio's side holds one, the **Merge credential**: a fine-grained token of the operator's Git host account, created by the operator, limited to the managed Repositories, with write access to pull requests and contents. It is the API setting `STUDIO_MERGE_TOKEN`, in the environment and never in the repository, a log, an answer or the agent side. It is used only for an operator's merge or close, never by a route the worker token can reach. While it is unset, merging and closing are refused and the Run page says why. The Agent account never merges, merge is never a worker privilege, and the operator stays the final merge gate. After a successful merge or a close without merging, Studio deletes that Run's own `agent/…` branch and no other.
- **Publishing a Draft: Studio's first write to a Repository** (Story #308, [ADR 0005](../architecture/adr/0005-agent-definitions-in-git.md)). Studio writes to exactly one Repository, the definitions Repository, and to one ref of it, its Integration branch. The limits and the layers that hold them:
  - **One Project, checked twice.** The `projects` public face `DEFINITIONS_PUBLISH` takes no Project: it resolves the definitions Project itself. The Git adapter's `publishCommit` takes the Project id and reads the Project's kind again through its settings right before the write, refusing any other Project (and refusing every write when it cannot tell); tests pin both layers. `agents` never touches Git.
  - **A fast-forward of one ref, never forced.** The push is `git push --porcelain --no-verify -- <remote> <commit>:refs/heads/<Integration branch>`: no `--force`, no `+` refspec, no other ref, no tag, no deletion, hooks and credential helpers off, the Deploy key written into the operation's private directory and used only by that process, with the same address policy, pinned host keys, memory bound and time limit as a fetch. A test records the Git calls and fails on any force flag or `+`. A rejection because the remote moved is `repository_moved`; the operator fetches, reviews and publishes again.
  - **The commit is built without a checkout.** A temporary index (`GIT_INDEX_FILE` in the operation's private directory) is read from the base commit, the changes are added as blobs (`hash-object --no-filters --stdin`, so no filter, attribute or line-ending conversion applies), and `write-tree` and `commit-tree -p <base>` make a commit with the base as its only parent. The Clone's working tree is never touched (it has none) and no hook, filter or driver of the Clone runs. A publish whose tree equals the base's is refused, and the Clone's branch must still be at the base.
  - **Author and committer come from Studio's settings only** (`STUDIO_DEFINITIONS_COMMIT_NAME` and `_EMAIL`, validated at start-up); the request cannot name them (its schema is strict), and a message cannot forge them. While they are unset, publishing is refused with 503 `publish-not-configured`.
  - **The write Deploy key.** The definitions Repository's Deploy key needs write access on the Git host, that Repository only; it is the Deploy key Studio already holds, stored and used like any other (never on the agent side, never in a response or a log). A host that refuses the write (a read-only key, a protected branch, a host rule) answers `write-refused`, whose message says the key needs write access and changes nothing in the Draft or the Clone.
  - **No remote text, no key material.** Git's output of a push is read only to classify the failure (moved, refused, other) and dropped: the answer and the log carry a fixed reason, never the host's lines, a path or a key. A test plants a key marker and a remote marker and asserts neither reaches an error or a log.
  - **Who can publish.** The route `POST /api/agents/definitions-repository/draft/publish` is an operator route: session and Origin only, and the route inventory and the token matrix refuse the worker and controller tokens, so no worker route leads to a publish. One publish runs at a time (an advisory lock taken without waiting); a second gets `publish-running`. The Merge credential is not used. A failed or refused push leaves the Clone's refs and the Draft as they were.
  - **Only `agents/` and `skills/`.** A publish refuses any changed path outside `agents/` and `skills/` with 422 `publish-path-outside-definitions` (the paths are listed), so Studio never writes a CI workflow or another file the Git host might run. The Operator makes such changes with their own Git.
  - **Not judged is refused.** The Draft's skill and agent folders (every skill it touches, every agent it touches or that names a touched skill) are judged again on the bytes that are pushed (the Draft's version must be the same before and after they are read, else 409 `agent-draft-conflict`), and a Clone that cannot be read for the judgement refuses with 503 `agent-files-unreadable`, never "no problem".
  - **What a publish changes for Runs.** A Run keeps the commit it started with, and its Follow-ups use that commit; only a Run started after the publish reads the new one.
- **Merge review** (Epic #258). The diff an operator reviews before a merge is computed on Studio's side, never taken from the agent worker. The API fetches the Integration branch and the Run's own `agent/…-r<run id>` branch (checked against the Run before Git starts) in one hardened fetch with the Project's own credentials into `refs/studio/review/<run id>`, a ref that is never checked out, then runs `git merge-tree --write-tree` and `git diff --no-ext-diff --no-textconv` in the bare Clone: no working tree, hook, filter, merge driver or external diff runs, under the same neutralised Git configuration and limits as every Git operation. The patches are repository text: redacted with the Run's secret values before they are stored, cut to the Run diff's limits, and shown as plain text. `GIT_ATTR_NOSYSTEM` is set and no `merge.*` or `diff.*` driver is configured in the Clone, so an attribute a branch carries names a driver that does not exist; `--attr-source` would pin attributes away from the tree but needs Git 2.40, above the minimum. The routes are operator routes only.
- Branch protection on each managed Repository keeps protected branches, including the integration branch (default `dev`), under the operator's approval: agents cannot merge, or push to them, directly. Merge stays with the operator, who merges from Studio with the Merge credential.
- A User Story normally lands through one integrated PR; subtasks normally produce commits; independent Technical Tasks may land separately when safe. `dev` is the GitHub default/integration branch; `main` is reserved for stable/release integration.
- Review the diff and relevant test results. Explicit authorization is required for approval/merge, force push, history rewrite, branch deletion, and repository credential changes. The one standing authorization: right after a successful merge or a close from Studio, Studio deletes that Run's own `agent/…` branch.
- CI and independent review are preconditions for merge. **The operator is the final manual merge gate**; agents have no unrestricted merge authority.

### Git adapter hardening baseline (connected Repositories)

Rules every Git operation Studio's Git adapter performs on a connected Repository follows, whatever the calling module. Git commands an agent runs in its working copy do not go through the adapter; the agent user's rights (§2) and the agent account's token limit them.

- **Linux only:** repository features run on Linux (containers, CI, the server); on non-Linux platforms they report an unsupported platform instead of running.
- **Transports:** in production configuration, only `ssh` and `https` remote URLs without embedded credentials; every other transport is rejected. Tests may allow local fixture remotes; production configuration refuses that setting.
- **No submodule recursion** and **no LFS smudge**: Studio downloads only the Repository's own objects.
- **Hooks never run**, from the Repository or from anywhere else.
- **No terminal prompts:** an operation that would need interactive input fails instead.
- **Isolated Git configuration:** the host's system, global and user Git configuration, credential helpers and SSH agents are never used; only Studio's fixed configuration and the Project's Deploy key apply.
- **Time and size limits:** cloning is stopped after 10 minutes, a Fetch after 2 minutes, and a Clone may not exceed 2 GB.
- **Memory bound:** every Git, `ssh` and `ssh-keyscan` process the adapter starts is limited to 2 GiB of address space **per process** (`maxProcessMemoryBytes`, next to the disk limit; not an environment variable). The adapter runs it as `prlimit --as=<bytes> -- <binary> …` (util-linux, no shell, from the same argument array). An unprivileged process may lower its own limits, so no capability is needed, and `RLIMIT_AS` is inherited by every child (`ssh`, `git-remote-https`, `index-pack`, `pack-objects`), so each process in the group is bounded on its own. Git's own memory settings (`core.packedGitWindowSize`, `core.packedGitLimit`, `core.deltaBaseCacheLimit`, `pack.windowMemory`, `pack.deltaCacheSize`, `core.bigFileThreshold`, `pack.threads=2`) and `MALLOC_ARENA_MAX=2` keep normal operations far below it; they are not the bound. A process that exits non-zero with its own out-of-memory diagnostic fails the operation with `size_limit`, like the disk limit (a failed clone is removed, a failed fetch removes the Clone). Only local diagnostic lines, anchored at the line start, count: `fatal:`/`error:` lines with `Out of memory, malloc failed`, `mmap failed`, `unable to create thread` or `cannot create async thread` (a thread stack that cannot be mapped fails this way under `RLIMIT_AS`; a process-count limit would print the same, and Studio sets none), lines starting with `xmalloc: `, and lines ending in `: Cannot allocate memory`. Every line starting with `remote:` is ignored, because it is the foreign server's text: a hostile or overloaded server must not be able to force `size_limit`, and neither can a ref name or URL that contains such a word. The adapter's start-up check refuses to run without a working `prlimit`, as it does for an old Git; the API image names `util-linux` explicitly.
- **Redacted output:** Git output is redacted before it is stored, logged or returned; private keys, credentials and secret-bearing URLs never appear.
- **Strict SSH host-key checking:** pinned host keys for the large Git hosts, an operator-confirmed fingerprint otherwise; an unknown or changed host key fails the operation.
- **Remote address policy (SSRF, Issue #69):** Studio never connects to link-local addresses (`169.254.0.0/16`, `fe80::/10`, with the cloud metadata service), other known metadata addresses (`100.100.100.200`, `192.0.0.192`, `168.63.129.16`, `fd00:ec2::254`, `fd20:ce::254`), `0.0.0.0/8`, `::`, multicast (`224.0.0.0/4`, `ff00::/8`) or reserved and broadcast addresses (`240.0.0.0/4`). Loopback (`127.0.0.0/8`, `::1`), private (`10/8`, `172.16/12`, `192.168/16`, `fc00::/7`, deprecated site-local `fec0::/10`) and CGNAT (`100.64/10`) addresses are allowed only with `STUDIO_GIT_ALLOW_PRIVATE_REMOTES=true` (default `false`), for a self-hosted Git server on the LAN. IPv4-mapped, IPv4-compatible, IPv4-translated, NAT64 (`64:ff9b::/96`) and 6to4 (`2002::/16`) IPv6 addresses count as the IPv4 address they carry; local-use NAT64 (`64:ff9b:1::/48`) and Teredo (`2001::/32`), whose IPv4 address cannot be read reliably, are refused; any non-address fails closed. Documentation and benchmarking ranges stay public: nothing internal answers there.
  - **Where:** an IP-literal URL is checked at Connect (numeric forms such as `0x7f.1` or `2130706433` normalized first; a numeric host that is no valid address is refused) and refused with a field error. Before every Git or `ssh-keyscan` process, the adapter resolves the host once, under the operation's time limit, and checks **every** address; a refused one fails the operation with `remote_not_allowed`, whose detail names the address and, for an opt-in range, the setting.
  - **DNS rebinding:** Git and ssh connect only to the checked addresses: HTTPS through `http.curloptResolve` (hence Git 2.37 or later; 2.38 for the merge review's `git merge-tree --write-tree`), SSH and `ssh-keyscan` through the checked IP (`HostName=<ip>`; host-key trust stays bound to the fixed host-key alias). Git never looks the name up again. **Limit:** `HostName` takes one address, so SSH pins a single one (the first IPv4 address, else the first): unlike plain ssh, it does not fall back to the host's other addresses when that one is unreachable.
  - **Redirects and proxies:** `http.followRedirects=false` for every operation; a redirect fails with `redirect_refused`. `fetch.uriProtocols=` (empty) keeps packfile URIs, which could send Git to another host, disabled. Proxy variables (`http_proxy`, `https_proxy`, `ALL_PROXY`) never reach Git: its environment is rebuilt from `PATH` only.
  - **Tests** whose fixtures listen on loopback opt in explicitly; a test pins the closed default.

### The agent worker's own Git commands

Rules for the Git commands the agent worker itself runs on a working copy, a cache or a remote (`apps/agent-worker/src/git.ts`). A working copy's own `.git/config`, an included file or an attributes file is repository- or agent-controlled, so none of them may make one of these commands run a program.

- **Allowlisted environment:** Git starts from `PATH`, `HOME` and `TMPDIR` only, plus the fixed variables the worker sets. A command that reaches a remote (the cache `clone` and `fetch`, the push) also keeps `SSH_AUTH_SOCK` and the proxy variables (`HTTP_PROXY`, `HTTPS_PROXY`, `NO_PROXY` and their lowercase forms). Studio's tokens (`STUDIO_*`) and provider keys never reach Git or a program it starts.
- **No global configuration in the working copy:** a command in a working copy, or one that creates or checks out into it, reads no user or system configuration. Cache commands and an SSH push keep the agent user's own configuration (its credentials).
- **Neutralised mechanisms:** on the command line (which beats every configuration file) the worker empties `diff.external`, the credential helper, the askpass and `core.alternateRefsCommand`, and sets the pager, editors, `gpg.program`, `core.sshCommand`, `core.attributesFile` and `uploadpack.packObjectsHook` to harmless values; hooks and the fsmonitor are off. Before every command in a working copy, whatever its subcommand, the worker lists the effective configuration keys (which runs no driver) and empties every `filter.<x>` clean, smudge and process command and every `diff.<x>` command and textconv, and replaces every `merge.<x>.driver` by Git's own text merge (`git merge-file`). Every `diff`, `log` and `show` passes `--no-ext-diff --no-textconv`. A nested (embedded) repository has its own configuration that no listing covers, so submodules are never inspected: `status` and `diff` pass `--ignore-submodules=all` (with `diff.ignoreSubmodules=all` and `status.submoduleSummary=false`), and `add` leaves out the index's gitlinks, so a submodule pointer change the agent did not commit itself is not staged or delivered (one the agent commits is still pushed). A `fetch` in a working copy passes `--upload-pack=git-upload-pack`, so `remote.<path>.uploadpack` is never used.
- **The push is unchanged:** one ref, no `--force`, the token only in the command's `GIT_CONFIG_*` environment for HTTPS.
- **Residual race:** the key listing and the command are two processes; a process that outlived the agent could add a driver between them. The environment allowlist does not depend on the listing, so such a race yields no Studio secret.
- **Verified** by Linux tests with real Git: each mechanism, written in the working copy's configuration, an included file and the agent user's global configuration, must never run; a program run through an explicit per-call setting shows only allowlisted environment names.
- **The agent's files are never pushed (Story #304).** Before it pushes, the worker fetches the Run's agent folder again and compares the Git blob ids (SHA-1 and SHA-256, since the object format is not known here) of its non-empty files with the blobs of every commit of every object the Run branch adds beyond its diff base (`git rev-list --objects`, so merge commits and a commit a later one reverted count). A match stops the delivery before any push: the Run fails `delivery_failed`, naming the file in the branch and the agent's file it copies. It fails closed: a folder that cannot be fetched or validated, a Git failure, or a list over 8 MiB (the process runner cuts a longer output silently) stops the delivery, so a push never goes unchecked. **What an exact-blob check cannot catch:** a copy with one byte changed, other line endings (an eol or clean filter in `.gitattributes`), another encoding, or content the agent re-typed is not an agent file by this test and is delivered; the guard stops carelessness, and the boundary stays the operating-system user. The Studio-paths check beside it lists changed files per commit and has the same blind spot for merge commits (pre-existing). Only the worker's own commit and push code reads Git here; it still starts no process from the folder.
- **The skills' files are never pushed either (Story #331).** The same check covers the files of the Run's skills: the worker fetches them again by the Run's id (a delivery retry's claim carries the skill names for this) and compares their blob ids with every object the Run branch adds, naming the file as `skills/<name>/<path>`; it fails closed the same way, and a skill that cannot be fetched or validated stops the delivery.

### Public repository controls

The repository is public: rulesets and secret scanning are enforced for free, and Issues, PRs, CI logs and history are visible to anyone.

- **Rulesets** `protect-dev` and `protect-main`: changes only via PR, no force-push, no deletion, with an **empty bypass list** (admins included). A genuinely needed force-push or deletion means the operator temporarily disables the ruleset in Settings → Rules, acts, and re-enables it. On `dev`, require `ci:required` once B5 exists. Do not require an approving review count: GitHub does not let an author approve their own PR, which would block a single operator. Independent review stays a process gate (review report), not a GitHub approval.
- **Limit of rulesets:** if agents act through the operator's GitHub account or token, rulesets cannot tell them apart, and an admin token can also edit or disable the rulesets themselves. Agents must not run `gh pr merge`, push to `main`/`dev`, or change repository settings or rulesets; give agent contexts the narrowest token available. A separate bot account without admin rights is a possible later improvement.
- **Secret scanning and push protection** enabled. Anything ever pushed is public; a leaked secret is rotated, not just deleted from history.
- **Untrusted Issues and PRs:** anyone can open an Issue or a fork PR. Agents act only on Issues the operator has refined and marked `Workflow Stage = Ready`, never automatically on instructions from other authors' Issues, comments or PRs. Such text reaches an agent only when the operator explicitly selects it and sends it as their own Follow-up, under the §2 rule on content from the Git host.
- **CI on fork PRs:** require approval before running workflows for outside contributors; never expose secrets to fork PR workflows; do not use `pull_request_target` to run untrusted code with secrets.
- **Vulnerability reports:** enable GitHub private vulnerability reporting; it is the private channel the Bug Report form refers to.
- Compliance records, review reports and CI logs are public: no credentials, tokens, private hostnames or unredacted logs.

## 5. Environments / Docker Compose

- **The boundary is the Preview user** ([ADR 0004](../architecture/adr/0004-preview-isolation.md)). Previews run on the host under a third operating-system user, not in the `docker` group and without passwordless `sudo`, with its own rootless Docker daemon used only for Previews. The **`environment-controller`** runs as that user, never under the system Docker daemon or with its socket. A hostile Compose file can at most damage other Previews.
- The controller performs only specific operations it claims from Studio (e.g. start, stop, status, logs, controlled refresh) against validated project definitions, not an arbitrary Docker command surface.
- **Validation is the second line of defence, not the boundary.** Before anything starts, validate repository/project identity, allowed Compose files, volume mounts, ports, images, environment variables, resource limits and credentials. It refuses: privileged containers, host network, process or IPC namespaces, added capabilities, devices, mounts outside the source directory, a Docker socket mount, external networks, and build contexts outside the source directory. Published ports are removed; only the chosen service is routed.
- **Tokens.** The controller calls Studio over its own routes (`/api/controller/`) with its own token (`STUDIO_CONTROLLER_TOKEN`), limited to Preview work. Three credentials open three disjoint sets of routes, and the API tests pin every refusal over the route metadata: a controller route accepts only the controller token (the worker token, a session and no credential get 401); a worker route accepts only the worker token (the controller token gets 401); every other route accepts only a session (the controller token gets 401 or 403). The API refuses to start when the two tokens are equal, without echoing either, and an unset controller token answers 401 on every controller route. The agent worker and the agents have no access to Preview credentials or to the Preview user's daemon. A full compromise of the Preview user exposes the controller token: with it an attacker can claim operations and receive the Environment files (test values only) of the Projects whose builds are queued. This is accepted because the boundary is the Preview user; the lease and audit fields record each claimed operation.
- **No Git credential on the Preview side.** The API hands the controller an archive of the Integration branch at the merged commit, with the Environment file's content (test values only). The controller never reads a Working copy.
- Preview code is **untrusted**: separate origin without administrative Studio cookies, restricted network access (see Network access), isolated storage access, restricted forwarded headers and ports.
- **Origin separation.** The preview domain is not Studio's hostname or a name under it, and Studio's session cookie stays bound to Studio's hostname only, so a Preview never receives it.
- **Preview password.** A Preview is protected by a Preview password at the reverse proxy, not by Studio's login. The operator sets one password for all Previews; the proxy holds only its bcrypt hash (`STUDIO_PREVIEW_PASSWORD_HASH` in the root-only `.env`, never readable on the agent side), checks it before anything else with one fixed user name, and never logs it. The password itself is kept outside Git. There is no rate limit on it (stock Caddy has none): a known gap, so use a long random value.
- **Network access (decided 2026-11-23).** Outbound internet access is allowed for builds and at run time. Studio's internal services (database, queue, the API's internal address) and the host's loopback are blocked, and a test proves the blocking. Accepted risk: Preview code can send anywhere whatever it can read, which is the Environment file's test values and its own data.
- **A failed build.** A failure before `up` leaves the previous Preview running. A failure at or after `up` makes the controller roll back, which removes every labelled container of the Project, the previous Preview included; the controller reports `previewRemoved`, and the page says so. The build log is redacted and capped like a Run log. Each Preview has a memory and a processor limit, each build a time limit.
- **The per-build bound (#278).** Compose has no key for the memory or the processor of a build step and BuildKit ignores `--memory`. A `RUN` step runs in a cgroup of its own directly below the Preview user's `app.slice` (measured on the CI VM: not in the daemon's unit, and the daemon's `cgroup-parent` is not honoured by builds), so `app.slice` holds the rootless daemon and the build steps only: Previews run in their own `preview-<id>.slice` and the controller in `agentic-studio-controller.slice`, both outside it. The controller runs one operation at a time, so before `compose build` it runs `systemctl --user set-property --runtime app.slice MemoryMax=<memory + 512>M MemorySwapMax=0 CPUQuota=<cpu percent>%`; the 512 MiB cover dockerd, containerd, rootlesskit and the shims. There is no `TasksMax` on it: the user slice's bounds forks. A failure of the command is `limits_failed`. The bound is not reset after a build: nothing else runs in `app.slice`. The bound stays after a build, so the daemon's shims and `slirp4netns` for Previews that keep running stay under the last build's bound, and running `agentic-studio-check-preview` during a build re-bounds `app.slice` for the length of its probe. The residual risk is that the kernel may pick the daemon instead of a build when the build is small and the daemon large: the server setup pins `OOMPolicy=continue` with `Restart=always` on the daemon, and the controller (which a build OOM cannot kill) resumes the Previews meant to run again.
- **Images and the build cache (#279).** Every service that builds gets `build.labels` with both ownership labels from the controller's override file, so the images it builds are labelled too (also with the short `build: .` syntax; a test on a real daemon proves it). After every build, succeeded or failed, the controller removes the Project's dangling labelled images, by id after an inspect; `remove_data` removes every labelled image of the Project, and Stop keeps them. Reset removes only labelled volumes, like every removal. Pulled base images are never removed (`docs/engineering/deployment.md` says how to prune them by hand). **The one stated exception to the label rule:** after every build the controller prunes the Docker build cache to `STUDIO_CONTROLLER_BUILD_CACHE_MAX_GB` (default 10) with `docker builder prune --all --force --keep-storage`, because the cache has no labels and the daemon serves only the controller.
- **Timeouts.** A build has its time limit (`STUDIO_PREVIEW_BUILD_MINUTES`, default 20), and the API fails a claimed build that has not reported an end 5 minutes after it as `report_overdue`, even when its heartbeat is fresh. A claimed operation without a report for the lease (`STUDIO_CONTROLLER_LEASE_SECONDS`, default 60) is `controller_lost`. A requested operation nobody claims fails as `not_claimed` after `STUDIO_PREVIEW_UNCLAIMED_MINUTES` (default 5), only while no controller has been seen for a lease or longer.
- **The link to a Preview** is a plain anchor in a new tab (`target="_blank"`, `rel="noopener noreferrer"`): no iframe, no prefetch, and Studio never fetches or renders a Preview's response.
- **Routing (#273, #277).** The reverse proxy reaches a Preview through a **static wildcard route**, not through configuration the Preview side writes ([`deploy/Caddyfile.preview`](../../deploy/Caddyfile.preview), trial record in [ADR 0004](../architecture/adr/0004-trial-preview-routing.md)):
  - Only a host that matches `^preview-[0-9a-f]{12}\.<preview domain>$` is routed, to the Unix socket `/run/preview-proxy/<label>.sock` (one socket per Preview, made by its bridge, #285). Only the captured label enters the path. Any other host answers 404 without a password prompt, and Studio's own site is a different, exact host. The proxy mounts the socket directory read-only and connects through a group; the Preview user never writes proxy configuration.
  - The password is asked before anything else, so "not running" never reveals which Previews exist. An absent or stale socket answers `404` "This Preview is not running." as plain text, never echoing the error; one upstream per request, no retry, so a request never falls through to another Preview.
  - The Preview gets no `Authorization` header (so it cannot use HTTP `Authorization` itself), no Studio session cookie (removed by name, under both names, as defence in depth: the cookie is host-only anyway) and no `X-Forwarded-For`, `Forwarded` or `X-Real-IP`. Only `X-Forwarded-Proto` and `X-Forwarded-Host`, set by the proxy, remain; `Host` passes unchanged. WebSocket upgrades follow the same rules.
  - The proxy checks that a request's Host matches the TLS server name (`strict_sni_host`, 421 otherwise). The Preview site uses the operator's wildcard certificate; on-demand certificates are refused (they would publish every Preview hostname in Certificate Transparency logs). Responses pass unchanged; Studio never fetches or renders them. No access log.
- One default shared Preview per project tracks approved changes in the project's integration branch (default `dev`). A run's working copy does not create a preview.
- Compose isolation is a pragmatic MVP baseline, **not** microVM-strength isolation. Stronger sandboxing may follow with appropriate server/KVM support.

## 6. MCP and external tools

- The `mcp` module owns the registry and bindings; secrets are stored outside Git. No generic unrestricted MCP gateway in MVP.
- Tool/server definitions and their outputs are **untrusted**. Approve connections, scopes and permissions; never grant broad filesystem/network access by default.
- Validate native CLI configuration generation; secrets must not be written into project-native config files or exposed to other agents.
- Negative tests must prove an agent cannot call an unbound or disallowed MCP tool.

## 7. Human approval boundaries

Explicit authorized approval is required for:

| Operation | Minimum policy |
| --- | --- |
| Merge into the project's integration branch (default `dev`) / protected branches | Passing applicable CI + independent review + operator approval |
| Merge of a Run's pull request from Studio | The same three, met as below, with no override |
| Deployment to production or external customer environment | Outside MVP; separate policy required |
| Secret creation/rotation/export | Authorized operator/controller; never arbitrary agent tooling |
| Destructive migrations or data deletion | Explicit operator review and tested recovery plan |
| Privileged Docker/Compose changes or broad network exposure | Authorized environment-controller + operator approval as appropriate |
| Repository access changes / Git credential changes | Operator approval |

For a Run's pull request merged from Studio, the three preconditions are met as follows:

- **Passing CI:** Studio reads the pull request's checks with the Merge credential at merge time. What the agent worker reported is not trusted.
- **Independent review:** the operator's review of the Studio-side diff of the exact commit to be merged. The author is the agent, so the operator is the independent reviewer.
- **Operator approval:** the stored Merge approval (who, when, the commit approved and the checks seen).

Merge is refused with a failing or running check, a conflict with the integration branch, an active Run or a Run branch that moved after the operator looked. There is no override. A Repository with no checks can be merged.

A prompt saying "ask for approval" is not an access control. The backend/runtime independently verifies an approval record and the acting principal.

## 8. Authentication and API authorization

- **Story 1 auth decision:** single operator, password-only login. The API verifies a strong operator password against an Argon2id hash supplied through the secret environment (`STUDIO_OPERATOR_PASSWORD_HASH`: an Argon2id PHC string, never the plaintext password). No public signup or user database yet. The API refuses to start unless the hash is Argon2id with at least the OWASP baseline (m=19 MiB, t=2, p=1). The local helper `pnpm --filter @agentic-studio/api run auth:hash-password` reads the password from stdin (hidden in a terminal) and prints only the hash.
- **Session:** opaque random session ID stored server-side in Redis with a bounded TTL (initial default: 12 hours of inactivity, subject to deployment testing), in an HttpOnly cookie. `Secure` and HTTPS in deployment, `SameSite=Lax` or stricter, invalidated on logout, identifier rotated on successful login. Development HTTP cookies are restricted to localhost and never presented as production-safe.
- **Session and cookie (implemented in B3, #14):**
  - The session ID is 32 bytes (256 bits) from a CSPRNG, base64url-encoded. Redis stores only its SHA-256 as the key, with a 12-hour sliding inactivity TTL that every authenticated request renews. Login deletes any session the request presents and issues a new ID; logout deletes the Redis key.
  - **Absolute lifetime** (operator decision on #24): a session is invalid 30 days after login (the `createdAt` stored in its Redis record), however active it is; the 12-hour inactivity TTL still applies. Session validation checks it on every authenticated request: an expired session, a record without a valid `createdAt`, or one whose `createdAt` lies more than 5 minutes in the future (clock-skew tolerance, `SESSION_CLOCK_SKEW_MS`, so a login on a fast clock cannot stretch the lifetime once the clock is corrected) gets the usual 401 and its Redis key is deleted. The limit is a constant (`SESSION_ABSOLUTE_LIFETIME_MS` in `apps/api/src/platform/auth/session-store.ts`), like the inactivity TTL, not an environment variable.
  - The cookie is `studio_session=<id>; Path=/; HttpOnly; SameSite=Lax`, with no `Max-Age` (a browser-session cookie; Redis enforces the TTL). When `STUDIO_ORIGIN` is https, the cookie adds `Secure` and is named `__Host-studio_session`. `STUDIO_ORIGIN` may use plain HTTP only for `localhost`, `127.0.0.1` or `[::1]`; any other HTTP origin fails start-up. Logout clears the cookie with the same attributes and an expiry in 1970.
- **Mutations** (including login/logout) are protected by same-origin/Origin checking, plus a CSRF token scheme if the deployment topology requires it; `SameSite` alone is not enough. Rate-limit login attempts; avoid account enumeration; never log password values. As implemented (Epic #8 decision 3, no CSRF token):
  - Every non-`GET`/`HEAD`/`OPTIONS` request needs `Origin` equal to `STUDIO_ORIGIN` (default `http://localhost:3000`). Without `Origin`, only `Sec-Fetch-Site: same-origin` is accepted. A foreign or `null` `Origin` is rejected even with `Sec-Fetch-Site: same-origin`. Rejection: 403.
  - A mutation that carries a body (any `Content-Type`, non-zero `Content-Length`, or chunked encoding) must be `Content-Type: application/json`, else 415. A bodyless mutation (e.g. logout) needs no `Content-Type`. The API parses JSON bodies only.
  - These checks run before the session guard, on public routes too.
- **Login rate limit** (Epic #8 decision 4): at most 5 failed logins per client IP (an IPv4 address or an IPv6 /64, see below) per 15 minutes and 50 failed logins per hour overall, as Redis counters. The next attempt over either limit gets 429 with `Retry-After` (seconds), even with the right password. A failure is reserved atomically before the password check, so concurrent attempts cannot overshoot; a successful login resets the IP counter and returns its global reservation.
  - **IPv6 aggregation** (operator decision on #24): the per-IP counter is keyed by the client's IPv6 /64 prefix, so one client cannot multiply its attempts by rotating through its own subnet. IPv4 stays per address. An IPv4-mapped IPv6 address (`::ffff:a.b.c.d`, dotted or hex) counts as its IPv4 address, and a zone ID (`%eth0`) is ignored. Logs keep the full client IP. Keys: `auth:login-failures:ip:203.0.113.7`, `auth:login-failures:ip:2001:db8:1:2::/64`.
  - **Lockout recovery** (#24): the global ceiling can lock the operator out for up to an hour during an attack from many IPs. First check the API logs for `Login rate limit reached` and `Login failed` warnings to see whether an attack is still running: clearing a counter during one only lets it continue. To lift the global lockout, delete the global failure counter in the Studio's Redis (`REDIS_URL`): `DEL auth:login-failures:global`. With the development Compose stack: `docker compose exec redis redis-cli DEL auth:login-failures:global`. A blocked IP stays blocked by its own counter, which is cleared the same way (`DEL auth:login-failures:ip:<key>`). Find the exact key with `redis-cli --scan --pattern 'auth:login-failures:*'` rather than typing it: an IPv6 /64 key keeps its zero groups uncompressed (`2001:db8:0:0::/64`, not `2001:db8::/64`). If `REDIS_URL` selects a database (`/<db>`) or uses `rediss://`, add `-n <db>` or `--tls` to every `redis-cli` command. Against a deployed Redis with a password, pass it through the `REDISCLI_AUTH` environment variable from the secret store, never on the command line or in a shell history. Deleting counters does not touch sessions.
- **Client IP:** `X-Forwarded-For` is honoured only when the socket peer is in `API_TRUSTED_PROXIES` (comma-separated IPs/CIDRs; default empty). The client IP is then the right-most address not in that list. With an empty list, the socket address is used. In local development, the `next dev` rewrite is the socket peer, so all browser traffic shares one IP bucket. The rewrite is not a trusted proxy unless listed. **Proxied deployments** (a reverse proxy, or the web app's production `/api` rewrite; rules in the [README](../../README.md#web-api-proxy)) must list the proxy's address(es) in `API_TRUSTED_PROXIES`; otherwise every client shares the proxy's IP and one rate-limit bucket. List only proxies that set `X-Forwarded-For` themselves, never a client-controlled hop. On the server, the Compose file sets it to the reverse proxy's fixed address only, never the container network's gateway, which every host process (the agent user included) shares ([Deployment](deployment.md#reverse-proxy-and-tls)).
- **Failures and logs:** every 401 is the same problem+json (`detail: "Not authenticated."`), whether the password is wrong or the session is missing, unknown, expired or logged out. Logs record login failures, successes and rate-limit hits with the client IP only. Server-side log redaction masks passwords, URL credentials, Argon2 hashes, cookies/session IDs, tokens and API keys, at any length and in linear time (no ReDoS).
- **Bind address:** the API listens on `API_HOST`, default `127.0.0.1` (localhost only). A deployment sets it explicitly. Express's `X-Powered-By` header is disabled.
- **Endpoints:**
  - `POST /api/auth/login`: receives `{ password }` over HTTPS (localhost HTTP is development only), verifies the hash, rotates the session, sets the cookie, rate-limits failures.
  - `GET /api/auth/session`: returns a non-secret authentication indication for the UI; requires a valid session.
  - `POST /api/auth/logout`: invalidates the Redis session and clears the cookie.
- All project endpoints and sensitive (including future SSE) endpoints are guarded at the API; anonymous calls get HTTP 401. Verify 401 with no session and after logout; authorization is never merely a UI redirect.
- The same public Studio origin routes `/api` to NestJS through a reverse proxy; no wildcard CORS; Next.js does not independently grant authorization. The web client sends requests with `credentials: 'same-origin'`, never reads the cookie or stores a token, and on 401 navigates to `/login`. External IdP/OAuth, MFA and multi-user accounts need a separate decision and are not part of Story 1.
- **Preview routes (session only).** `GET /api/projects/:id/preview`, `GET /api/previews`, `PUT` and `DELETE /api/projects/:id/preview/settings`, `POST /api/projects/:id/preview/builds`, `POST /api/projects/:id/preview/stop`, `POST /api/projects/:id/preview/reset-data` and `GET /api/projects/:id/preview/builds/:buildId/events` take a session and nothing else: the worker token and the controller token get 401, no credential gets 401, and the mutations (`PUT` and `DELETE` of the settings, `POST` of a build, of a stop and of a reset) also need the Origin. Reset removes data for good, so the web asks first; the API has no further check, and a stop or reset needs a connected controller. The answers carry no Environment file value: a build's log lines and failure detail are redacted with the snapshot's values before they are stored, and the three routes only read them. The tests pin both, with a secret in a log line and in a failure detail. The rebuild after a merge through Studio adds no route: the timer that carries it out only requests what a merge recorded, and the new `previewAfterMerge` field of the single-Run answer carries a Project id and a state, no secret.
- Validate all backend inputs, project identifiers, file paths, and resource ownership, even when the UI restricts options.
- **Bearer tokens (worker and controller).** Each is at least 32 characters; only its SHA-256 digest is kept, as a `KeyObject`, and compared in constant time; messages never echo it. An unset token rejects every route it guards. The worker token opens the worker routes only and the controller token the controller routes only; neither skips for the other, and both skip the Origin check, because no cookie authenticates them.
- API and worker permissions are narrowly scoped; never trust a client-supplied role, path, tool name, branch, or container target.
- Sensitive operations record actor/run, project, action, decision, result and correlation identifier, without leaking credentials.

## 9. Security verification — negative tests

Enforced controls must **reject** the following, evidenced by automated tests as each capability is implemented:

- A run reads or writes a file outside its working copy and assigned project scope, including via symlink/path traversal.
- Agent B reads Agent A's working copy or another project's files.
- A runner uses the system Docker daemon or its socket, or calls unauthorized environment-controller operations.
- A malicious `README.md` instructs the agent to output secrets or modify forbidden files.
- An unapproved MCP tool is invoked, or a tool response includes prompt-injection text.
- A run requests unauthorized branch merge, credential disclosure, or production DB access.
- A Run is started on the definitions Repository, a definition with a forbidden key is offered, a draft reaches the agent worker, a publish over a moved Repository succeeds, or the write Deploy key reaches the agent side or a log (Epic #298).
- A Preview accesses Studio cookies, admin APIs, internal DB/Redis or unapproved network destinations.

Also verify: a canceled or retried execution causes no duplicate irreversible effects.

**Run isolation model ([ADR 0002](../architecture/adr/0002-agent-run-isolation.md)).** The deployed model must pass these checks, run as the agent user. They are implemented by `deploy/check-boundary.sh` and set up by `deploy/setup-server.sh` (#107; [Deployment](deployment.md)):

- The agent user cannot read Studio's files.
- The agent user cannot reach the system Docker socket.
- The agent user cannot use `sudo` without a password.
- The agent user cannot reach Studio's database or Redis ports, nor the API and web containers directly: only the reverse proxy's worker port (#132).
- Rootless Docker works for the agent user: a Compose stack starts and stops.
- The agent user cannot start programs outside the Linux system or write to another operating system's drives. On WSL with default settings, interop runs Windows programs as the Windows user and the Windows drive mount is world-writable, so WSL is not an isolation boundary ([trial](../architecture/adr/0002-trial-rootless-docker.md#security-finding-wsl), 2026-11-15). The server is native Linux; a WSL host needs interop and automount disabled.
- Container resource limits apply to the agent user's rootless Docker: the server runs cgroup v2 with systemd (under WSL's cgroup v1 no limits applied).

The [rootless Docker trial](../architecture/adr/0002-trial-rootless-docker.md) (2026-11-15, WSL) showed the system socket, `sudo` and rootless Compose checks passing, and the WSL check and the resource-limit (cgroup) check failing under WSL with default settings; the server setup task (#107) runs all of them on the target server.

**Preview isolation model ([ADR 0004](../architecture/adr/0004-preview-isolation.md)).** The Preview side must pass these checks, run as the Preview user (`deploy/check-preview.sh`, installed as `agentic-studio-check-preview`; set up by `deploy/setup-server.sh`; [Deployment](deployment.md#preview-checks)), and the agent's part as the agent user (`check-boundary.sh`, group `preview`):

- The Preview user is in no `docker`, `lxd`, `sudo` or proxy group, cannot use `sudo`, has a private home and linger; it shares no group with the agent user.
- The Preview user cannot reach the system Docker socket, the agent's socket and data-root, the agent's home and worker `.env`, Studio's configuration and state, nor Studio's PostgreSQL, Redis, API and web; a third user cannot reach either user's socket or data-root; the agent user cannot reach the Preview user's socket, data-root or controller `.env`.
- The cgroup controllers `cpu memory pids` are delegated to the Preview user's manager, and a slice limit bites; a memory limit on the Preview user's `app.slice` (the daemon and the build steps) fails a build that exceeds it with an OOM kill and leaves the daemon running; the controller runs in a slice of its own.
- The egress rules are in place in the Preview daemon's network namespace (re-applied at every daemon start), and **from a Compose project network and from a build `RUN` step** the proxy, PostgreSQL, the host's non-loopback address and `10.0.2.2` are blocked while public HTTPS is reached.
- The controller runs as production under the rootless `DOCKER_HOST`, its `.env` is 0600, and `/run/preview-proxy` is `preview:previewproxy` with mode 2750 (setgid).
- The controller token works on the controller routes only (worker and operator routes answer 401); the worker token gets 401 on the controller's claim route.
- The agent user is not in the proxy group and cannot list `/run/preview-proxy` (it could otherwise connect to a Preview's socket and skip the Preview password); the setup refuses it.
- An absent runtime directory is a failed check, never a pass.

Residual risk: the egress script records the host's global IPv4 addresses when the rules are applied (at every daemon start, so also at boot). An address that appears later is rejected only after a restart of the Preview user's daemon; `verify` checks against the recorded list. The Preview user owns that list and the namespace's rules, so this does not change the trust boundary (ADR 0004).

All runs share the agent user, so user permissions alone do not separate runs or projects. For the first version the operator accepted guardrails only for that separation (ADR 0002, 2026-11-15): the cross-run and cross-project checks above show that the guardrails block ordinary attempts, not that a misled agent is contained. Dedicated host users per project are the recorded upgrade path for cross-project separation.

## 10. Security delivery gates

- **Before repository bootstrap:** document required approvals; commit no secrets.
- **Before real CLI execution:** enforce bounded working copies, credentials, tool access, timeouts and non-privileged worker behavior, and test denial of forbidden operations. A functional CLI demo alone is insufficient.
- **Before exposing Preview externally:** isolate origin, cookies, ports, network and resource scope; review untrusted code execution risks.
- **Before autonomous merge:** platform-enforced branch protection where supported, or the operator stays the manual merge gate; agents never self-approve.

Keep the initial scope small; improve isolation and test coverage as each risk-bearing capability ships. See [System](../architecture/system.md) and [Quality](quality.md).

## Intended use (what is validated)

- Started by Studio's agent worker on one Linux server, running as an ordinary (non-root) user.
- Each run is a sequence of non-interactive steps (`codex exec`) with streamed JSON events, a structured final result, and resume of the same session by id.
- Runs start only on the operator's action (later also from a workflow the operator started), never on a timer or an outside event.
- At most two runs at a time; runs continue while the operator is away.
- The operator's own projects; one operator; the operator's own everyday account.
- Authentication: ChatGPT plan login first; API key as the fallback.

## Authentication

### ChatGPT plan login (first choice)

Clearly permitted (by the Codex documentation):

- Signing in to the CLI with a ChatGPT plan is a supported method. Authentication: "Codex supports two ways for a person to sign in when using OpenAI models:" followed by the list items "Sign in with ChatGPT for subscription access" and "Sign in with an API key for usage-based access".
- Running `codex exec` unattended as one's own Codex account is documented. Non-interactive mode: "Read this if you need to run CI/CD jobs with a Codex user account instead of an API key, such as enterprise teams using ChatGPT-managed Codex access on trusted runners or users who need ChatGPT/Codex rate limits instead of API key usage."
- `codex exec` uses the stored login. Non-interactive mode: "`codex exec` reuses saved CLI authentication by default."
- Login on a server without a browser is documented. Authentication: "In these situations, prefer device code authentication (beta). In the interactive login UI, choose Sign in with Device Code, or run `codex login --device-auth` directly."
- Token refresh by the CLI itself is the documented path. CI/CD auth: "That means the supported CI/CD strategy is not “call the refresh API yourself.” It is “run Codex and persist the updated `auth.json`.”"

Conditions the documentation attaches to that use:

- It is the non-default path. CI/CD auth: "The right way to authenticate automation is with an API key. Use this guide only if you specifically need to run the workflow as your Codex account." Non-interactive mode: "API keys are the right default for automation because they are simpler to provision and rotate. Use this path only if you specifically need to run as your Codex account."
- Trusted private infrastructure only. CI/CD auth lists among its conditions: "the runner is trusted private infrastructure".
- Not for public repositories. Non-interactive mode: "Do not use this workflow for public or open-source repositories." The CI/CD auth page repeats it.
- One credential copy per serialized job stream. CI/CD auth: "Use one `auth.json` per runner or per serialized workflow stream." and "Do not share the same file across concurrent jobs or multiple machines."
- Programmatic use is steered to API keys. Authentication: "Use API key authentication for programmatic Codex CLI workflows, such as CI/CD jobs. Don’t expose Codex execution in untrusted or public environments."

Clearly not permitted: nothing found in the pages read. Not reviewed: the Terms of Use, Usage Policies and Help Center articles (see note above), which may contain account-sharing or automation restrictions.

Unclear:

- **Two concurrent runs on one login.** The intended use allows two runs at a time. The CI/CD auth guide says not to share one `auth.json` "across concurrent jobs". The guide is written for copied credentials on CI runners; whether two `codex exec` processes on one host under one `CODEX_HOME` count as "concurrent jobs" is not stated.
- **Public repositories.** The intended use covers the operator's own projects. If any of them is public, the "Do not use this workflow for public or open-source repositories" sentence applies at least to the copied-credential workflow. Whether it also applies when the server logs in directly with device code is not stated.
- **Unattended runs while the operator is away** are not addressed directly, beyond the CI/CD guide describing jobs that run without a person present.
- **Terms of Use / Usage Policies** — not read (see note).

### API key (fallback)

Clearly permitted (by the Codex documentation):

- Authentication: "Use API key authentication for programmatic Codex CLI workflows, such as CI/CD jobs."
- Pricing, under the heading "API Key": "Great for automation in shared environments like CI." and "Pay for Codex usage based on API pricing".
- Non-interactive mode: "For other automation environments, set `CODEX_API_KEY` only for the Codex invocation that needs it, and make sure no untrusted code runs in the same process environment."

Clearly not permitted: nothing found in the pages read. Exposing the key to repository code is warned against. Non-interactive mode: "Do not set `OPENAI_API_KEY` or `CODEX_API_KEY` as a job-level environment variable in workflows that check out or run repository-controlled code."

Unclear: the API Services Agreement and Usage Policies were not read (see note). Feature gaps: Authentication says "some features that rely on ChatGPT workspace access or cloud services are limited or unavailable" with an API key; none of the features the intended use needs is listed as missing.

### How credentials are provisioned to the worker

- The operator signs in **once on the server**, as the agent user, with `codex login --device-auth` (browser and one-time code on the operator's own device). The CLI stores and refreshes its own login under that user's `CODEX_HOME`.
- The worker never reads, copies, parses, logs or forwards the credential store. It only starts the official `codex` binary as the same user, which uses the stored login (`codex exec` "reuses saved CLI authentication by default").
- No proxying: no Studio component sits between the CLI and the provider. No sharing: one operator, one login, one server.
- The documented fallback of copying `auth.json` from another machine is **not** used; it would be credential transfer the worker must avoid.
- For the API key fallback, the operator stores the key in the worker's deployment secrets; the worker passes it only to the `codex exec` process (`CODEX_API_KEY`), never to commands the agent runs and never into logs. Whether the CLI strips it from child processes is not stated; see Technical findings (command environment).

## Permitted execution mode and restrictions

### CLI version and command

- Version examined: **0.169.0** (changelog entry "Codex CLI 0.169.0", dated 2026-11-13; same tag `rust-v0.169.0` on the provider's GitHub releases and on npm). Not installed or run for this record.
- Non-interactive command (Non-interactive mode): "Non-interactive mode lets you run Codex from scripts (for example, continuous integration (CI) jobs) without opening the interactive TUI. You invoke it with `codex exec`."
- Intended first step (options verified against the `codex exec` reference):

```text
codex exec --json \
  --cd <working-copy> \
  --sandbox workspace-write \
  -c approval_policy="never" \
  --output-schema <run-dir>/result.schema.json \
  --output-last-message <run-dir>/result.json \
  - < <run-dir>/prompt.md
```

- Intended resume step (answer to an agent question):

```text
codex exec --json --cd <working-copy> --sandbox workspace-write -c approval_policy="never" \
  resume <SESSION_ID> - < <run-dir>/answer.md
```

Options, each from the `codex exec` reference:

| Option | Reference text |
| --- | --- |
| `--json` | "Print newline-delimited JSON events instead of formatted text." |
| `--cd, -C` | "Set the workspace root before executing the task." |
| `--sandbox, -s` | "Sandbox policy for model-generated commands. Defaults to configuration." |
| `-c, --config` | "Inline configuration override for the non-interactive run (repeatable)." |
| `--output-schema` | "Path to a JSON Schema for the model's final response." |
| `--output-last-message, -o` | "Write the assistant’s final message to a file. Useful for downstream scripting." |
| `PROMPT` | "Initial instruction for the task. Use `-` to pipe the prompt from stdin." |
| `resume` | "Resume an exec session by ID or add `--last` to continue the most recent session from the current working directory. [...] Accepts an optional follow-up prompt." |
| `--ignore-user-config` | "Do not load `$CODEX_HOME/config.toml`. Authentication still uses `CODEX_HOME`." (candidate, see findings) |
| `--ignore-rules` | "Do not load user or project execpolicy `.rules` files for this run." (candidate, see findings) |

`approval_policy="never"` is set through `-c` because the reference documents `--ask-for-approval` as a global flag; whether it is accepted after `exec` is not stated. The headless test checks this.

### Event output, structured result and session id

- Events (Non-interactive mode): "When you enable `--json`, `stdout` becomes a JSON Lines (JSONL) stream so you can capture every event Codex emits while it’s running. Event types include `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.*`, and `error`."
- Items: "Item types include agent messages, reasoning, command executions, file changes, MCP tool calls, web searches, and plan updates."
- The documented sample starts with `{"type":"thread.started","thread_id":"..."}`, and `turn.completed` carries a `usage` object.
- Structured result: "use `--output-schema` to request a final response that conforms to a JSON Schema."
- Resume by id: "You can also target a specific session ID with `codex exec resume <SESSION_ID>`." The reference types `SESSION_ID` as "uuid | session name".
- **Unclear:** the docs do not state that the `thread_id` in `thread.started` is the `SESSION_ID` that `resume` accepts. The worker should capture `thread_id`; the headless test confirms it resumes.
- **Unclear:** the docs do not list exit codes for `codex exec`. The worker should treat `turn.failed` / `error` events as failure as well as a non-zero exit status.

### Restrictions

- Usage limits apply to plan login. Pricing: "The number of messages you can send depends on the model used, size and complexity of your tasks, and whether you run them locally or in the cloud." and "If you reach your usage limits during an active turn, the agent will be able to continue working on that turn, subject to fair use limits." A run can stop on a usage limit; the worker must report it as a failure, not retry in a loop.
- Plan login: no public repositories, trusted private infrastructure, one serialized stream per credential copy (see Authentication).
- API key: never exposed to repository-controlled code.
- Prohibited uses under the Usage Policies: **not reviewed** (see note).

## Technical findings that affect the design

1. **Sandbox and approvals in non-interactive runs.**
   - Default is read-only. Non-interactive mode: "By default, `codex exec` runs in a read-only sandbox." Edits need `--sandbox workspace-write`; Agent approvals & security: "For non-interactive runs, use `codex exec --sandbox workspace-write`."
   - Approval policy values are `on-request | never` (reference). With `never`, "The agent doesn’t stop for approval prompts" (Sandboxing). What `codex exec` does with an approval request under `on-request` with no person present is not stated; the record therefore intends `never`.
   - `--approve-for-me` routes eligible approvals to an automatic reviewer agent (reference: "Use automatic approval review with `on-request` approvals and the `workspace-write` sandbox."); it "uses extra model calls, so it can add to Codex usage". Not intended for the first version.
   - Linux enforcement needs bubblewrap. Sandboxing: "On Linux and WSL2, install `bubblewrap` with your package manager first". On Ubuntu 24.04 an extra AppArmor profile may be needed (same page). This is a server setup step.
   - **`.git` is read-only in `workspace-write`.** Agent approvals & security: "`<writable_root>/.git` is protected as read-only whether it appears as a directory or file." The same applies to `.agents`, `.codex` and `.aws`. The agent therefore cannot commit inside the sandbox. Design consequence: either the worker commits and pushes after each step, or the run uses a permission profile or `danger-full-access` and relies on the OS user boundary. Decision for the run stories.
   - Network is off by default. Agent approvals & security: "the default `workspace-write` sandbox mode keeps network access turned off unless you enable it in your configuration". Installing dependencies needs `sandbox_workspace_write.network_access = true` (optionally with the `network_proxy` domain allowlist).

2. **Combining with rootless Docker.**
   - Inside `workspace-write`, the agent reaches the rootless Docker daemon only through its Unix socket, and socket access is allowlist-based. Permissions: "Unix socket proxying is a local escape hatch for tools such as Docker. Use it sparingly". The setting `dangerously_allow_all_unix_sockets` is described as "a broad local escape hatch".
   - Socket access lets containers act with the agent user's full rights outside the Codex sandbox, so once Docker is allowed the Codex sandbox is no longer a meaningful boundary. This matches Epic #84: the OS user separation is the boundary, Codex settings are guardrails.
   - The docs describe an outer-boundary pattern. Agent approvals & security: "If the container is your intended security boundary, run Codex with `--sandbox danger-full-access` inside the container so Codex does not try to create a second sandbox layer." By analogy, with the dedicated host user as the boundary, `danger-full-access` (no sandbox, network on) with `approval_policy="never"` is an option; the docs warn that full access lets "a malicious project [...] exfiltrate anything available", including Codex credentials. Choosing between workspace-write with network and a Docker socket allowlist, and danger-full-access under the dedicated user, is a design decision for the run stories, informed by the rootless Docker trial.
   - Not tested here; the headless test does not use Docker.

3. **Project-level configuration a run loads automatically.**
   - `AGENTS.md`: "Codex reads `AGENTS.md` files before doing any work." It walks from the project root to the working directory and concatenates the files (up to 32 KiB by default). The page does not make this depend on project trust, so a project's `AGENTS.md` is treated as loaded in every run.
   - `.codex/` layers (config, hooks, rules) load only for trusted projects. Advanced config: "For security, Codex loads project-scoped config files only when the project is trusted. If the project is untrusted, Codex ignores project `.codex/` layers, including `.codex/config.toml`, project-local hooks, and project-local rules." Trust is set per path with `projects.<path>.trust_level` (`"trusted"` | `"untrusted"`) in the user config.
   - **Unclear:** the trust state of a never-seen path in a non-interactive run (no trust prompt) is not stated. The worker should set it explicitly for each working copy (`-c 'projects."<path>".trust_level="untrusted"'` or the user config) and the headless test checks which layers load.
   - Project config cannot redirect credentials: Advanced config lists keys ignored in project `.codex/config.toml`, including `openai_base_url`, `chatgpt_base_url`, `model_provider` and `model_providers`.
   - Hooks need persisted trust. Hooks: "Before a non-managed hook can run, Codex requires you to review and trust the exact hook definition." `--dangerously-bypass-hook-trust` disables that for one run; Studio should not use it.
   - User-level config, rules and hooks under `CODEX_HOME` always load unless `--ignore-user-config` / `--ignore-rules` is passed; Studio controls those files, so they are where Studio's own guardrail hooks and rules belong.
   - Feeds the Epic #84 open decision on agent configuration found in a project repository.

4. **Command environment.** Config basics: `ignore_default_excludes` "defaults to `true`, which skips automatic filtering for variable names containing `KEY`, `SECRET`, or `TOKEN`." By default, secrets in the worker's environment would reach commands the agent runs. The worker starts `codex` with a minimal environment and, for the API key path, sets the shell environment policy so the key is not forwarded.

5. **Codex home and session files.** Sessions are stored as rollout files under `CODEX_HOME` unless `--ephemeral` is used (Non-interactive mode: "Use `--ephemeral` when you don’t want to persist session rollout files to disk"). Resume needs those files, so Studio must not use `--ephemeral`. Network file systems: keep the Codex home "on the worker’s local disk". The session files sit outside the working copy and are never committed or attached to logs.

6. **Git repository check.** "Codex requires commands to run inside a Git repository to prevent destructive changes." Studio's working copy is a clone, so `--skip-git-repo-check` is not needed.
